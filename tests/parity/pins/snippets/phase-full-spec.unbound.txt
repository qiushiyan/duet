<snippet key="write-spec">
Now, write the spec to the location the framing's conventions name (where specs live is the project's call, not this template's). Ground the problem and the approach in actual code — read the relevant modules first if you haven't.

This one document carries the whole design: whoever builds executes from it, and a human reads it later to understand the change. Tight prose beats exhaustive sections, and every section earns its place.

## Read these first
Adapt each to this change — they are the bar for the shape you're about to commit, not optional background. If a path is missing, ask me rather than guessing.

**Read closely.** The spec decides module structure, interfaces, and where seams fall; these are the vocabulary those decisions are made in.
- `{{lessons_dir}}/codebase-design/deep-modules.md` — deep modules, seams, the deletion test, illegal states.
- `{{lessons_dir}}/codebase-design/design-it-twice.md` — how to arrive at an interface instead of settling for the first one. Read it when you write the target-shape section.
- `{{lessons_dir}}/codebase-design/deepening.md` — read it when the change restructures an existing cluster, or leans on a dependency across a seam you don't own: its dependency categories decide whether a seam needs a port at all.

**Skim the `## The bar` at the top of each of these.** You decide *which* behaviors matter and what gets faked where; the depth below the bar is for whoever writes the tests.
- `{{lessons_dir}}/testing/tdd-loop.md` — behavior through interfaces. Which behaviors matter is a product call to surface, not to assume.
- `{{lessons_dir}}/testing/mocking-and-fixtures.md` — mock only at boundaries. A mock of your own module is a design signal: fix the interface here rather than plan a mock later.

## The document's shape
The spec runs top-down, product to technical, each tier at its own altitude.

**A leader-facing summary, first.** Report the change the way you'd report it to your leader: what we're adding or fixing in product terms; the approach and the scope; and the boundary once it lands — what's fixed, what isn't, what's explicitly deferred (one line why each). Technical detail earns a place here only where it makes the problem or the solution easier to grasp. Someone who reads nothing else should still know what they're getting and not getting.

**Product sections** — the goals, the user-facing behaviors, the non-goals. Distinguish current from desired (what's preserved versus what's changing), and name the coupling decision: an extension of an existing concept, or intentionally independent?

A tree-style before/after often makes the change crisp — adapt the format (tree, prose, diagram) to what fits:

  Current:
    User submits form
    └─ Validation runs
       └─ Record saved
          └─ Confirmation shown

  Desired:
    User submits form
    └─ Validation runs
       └─ Record saved
          └─ Webhook fired
          └─ Confirmation shown

**Technical sections** — the shape of the build:
- *Module boundaries and seams* — which modules own the change, the interface each presents, and where the seam falls.
- *The foundation decision* — is the existing code a base this extends cleanly, or a structure that blocks the design you actually want? If it blocks, scope a bounded reshaping as the opening move — sized to this feature, not a module rewrite — and name what you're deliberately leaving alone.
- *The target shape* — the envisioned end-state; the next section says how.
- *Test standards* — the behaviors that must be tested, and for each the strategy: through which interface, what gets faked at which boundary, plus the gotchas worth flagging. What to test and how to think about testing it, never the cases themselves.

## The target shape
When the change reshapes structure or grows a surface, give the target shape its own section — the envisioned end-state, in the same before → after register. Include only the views where the change actually lives: a contained bug fix may need none; an SDK or a structural refactor may earn all three. This is the spec's highest-value handoff — whoever builds starts out holding your mental model of the shape instead of reverse-engineering one.

- **File/module structure** — where the pieces live once this lands: a directory tree with one-line roles, each entry a domain concept (a state, a kind of data, a responsibility), not a layer of plumbing. The structure is the spec's domain model made visible.
- **Public API or syntax** — what a caller writes once this exists: the exported functions, the config shape, the command line. The surface a user touches, never the bodies behind it.
- **Integration wiring** — how the new piece connects to what exists, and how data and control flow through the changed system: who calls it, what it replaces, which seams it plugs into. Prose or a diagram, with implementation anchors (modules, functions, files) attached to the flow rather than carrying it.

Sketches stay small — the shape, not the build:

  Structure — after:
    src/export/
      index.ts    # the one entry: exportReport()
      csv.ts      # CSV rendering — format quirks live here
      pdf.ts      # PDF rendering

  API — what a caller writes:
    exportReport(report, { format: "csv" })
    (one deep entry point — not exportCsv / exportPdf / exportXlsx each exported)

Shape each view with a deep-module mindset: small surfaces concentrating complexity behind them, the domain's states and data carved so wrong ones are hard to express, seams few and narrow rather than many and chatty. Mark them as the *envisioned* shape, not a contract — the build may drift for stated reasons when the code teaches better, never silently.

**Design it twice before you commit.** Your first interface idea is rarely your best, and the shape you settle here is the shape that gets built. Per `design-it-twice.md`:
- Sketch three shapes *different in kind*, each following one constraint further than feels comfortable: **minimal** (one to three entry points, maximum leverage each) · **flexible** (many use cases, room to extend) · **common case** (the default caller's path trivial, even at the rare one's expense) · **ports and adapters** (when a dependency crosses a seam you don't own).
- Write the three constraints down before developing any of them, and hold the others out of view while you work each. Sequential authorship converges, and that convergence is the failure this exercise exists to prevent.
- Compare on depth, locality, and seam placement — not taste.

What lands in the document is the winner, not the menu: the chosen structure / API / wiring, plus a short **Shapes considered** note — the constraint each alternative optimized and the one-line reason it lost, in that same vocabulary. Two or three lines, not three sections. It pays for itself twice: a reviewer can check whether the shape was *chosen* or merely *first*, and whoever builds from this document knows why *not* the other shape, so they don't quietly re-derive it halfway through.

## Before you finish

**Be concrete, not vague.** Vague verbs — improve, enhance, polish, better, optimize, streamline — name a *direction*, not a *decision*; they quietly defer the real choice to implementation, which defeats the point of writing a spec. Say what changes: the specific behavior, state, or outcome that differs, and the rule or shape that produces it. "Improve error handling" → "on a failed webhook, retry with backoff, then surface a dismissible banner instead of failing silently."

**Leave out what isn't yours to pin.** Two kinds. Details the code hasn't taught us yet — full code bodies, per-case test enumeration and fixtures, line-level edit plans, function renames, exact call-site changes, doc-update plans, commit order — belong to whoever plans or builds; the spec owes the *what*, the *why*, and the *shape*. And time or effort estimates ("2 days", "~3 hours") describe the work no better than the work itself does. Phases are fine; a precise commit order is not. Code appears only as the target shape's surface sketches.

**Hunt the rabbit holes.** Walk the approach end to end looking for what could quietly eat the build: a technical unknown nobody has proven, a design problem the spec gestures at but doesn't solve, an interdependency that reads simpler than it is. Solve each here, cut it out of scope explicitly, or name it in the open questions. An unnamed hole doesn't disappear — it resurfaces mid-build, where whoever builds has only this document to resolve it with.

If you have remaining product questions or major technical uncertainty, interview me before you write.
</snippet>
<snippet key="review-spec">
I've drafted a spec — the design document for this change. Review critically, and verify its problem statements and intended solutions against the actual code.

Background (skim as a lens, don't recite):
- `{{lessons_dir}}/codebase-design/deep-modules.md` — deep modules, seams, the deletion test
- `{{lessons_dir}}/testing/tdd-loop.md` — vertical slices, behavior-focused tests, when to mock

The spec runs top-down — product sections (goals, behaviors, non-goals) above technical sections (module boundaries, seams, the target shape, test standards) — and each tier reviews at its own altitude.

**Product sections — hold them to product altitude:**
- Vagueness on a behavior the feature must define (data flow, ordering, failure modes, scope, edge cases, current vs. desired) → a real gap; flag it.
- Module or test design pressed here → it lives in the spec's own technical sections. Judge it there, not as a product-section gap.

**Technical sections — hold them to design altitude:**
- Module boundaries, seams, the target shape, and the test strategy → fair game; propose better where a boundary is wrong, a module shallow, a seam misplaced, a test strategy weak, or the design over-built.
- The public API → hold it to surface altitude: interfaces and placement, not bodies.
- Vagueness on full code bodies, per-case test enumeration, fixtures, line-level edit plans, commit order → intentional; don't ask for them. Whoever plans or builds decides those, and pressing the spec down to that depth re-grows the review rounds this document exists to avoid.

**Push hard on:**
- Are we solving the right problem? Is the UX goal right?
- Does the approach hold up: data flow, state, ordering, failure modes, performance, backward compat, migrations?
- Spec ↔ code mismatches; cleaner alternative approaches.
- Whether the design deletes complexity or just rearranges it, and whether the resulting modules are deep or shallow.
- The target shape, where the spec proposes one: was it *chosen*, or merely *first*? Its "Shapes considered" note should name what each rejected alternative optimized and why it lost, on depth / locality / seam placement — check the reasoning holds and the winner really beats them. On a change big enough to warrant the section, a shape with no alternatives behind it is itself a finding.
- Foundation and preparatory refactoring: a feature bolted onto a structure that can't hold it (a missing prep step), or a cleanup disproportionate to the feature (scope creep).
- Over-building: defensive handling for states that could be made unrepresentable, speculative features or config nobody asked for, an abstraction pulled out too early. Flag these the way you'd flag a missing case.
- Test standards: do the named behaviors cover the critical paths, and are the strategies at the right altitude (behavior through interfaces, mocking only at boundaries)?
- Non-goals and open questions: anything in-scope that should defer? Anything missing from the uncertainty list?

**Run a pre-mortem before you write up findings.** It's a month from now: the build that came out of this spec stalled, or shipped subtly wrong — no crash, no failing test. Write down the two or three most plausible causes, then check whether the spec already defends against each; any it doesn't becomes a finding. Looking back from an assumed failure surfaces risks that reading forward misses.

**Per point:**
- Agree → add technical suggestions, caveats, or risks worth flagging.
- Disagree → give reasons and a concrete alternative. If architectural, say so and propose the structural fix.

Weigh technical merit and UX goals together. Challenge assumptions and propose alternatives rather than defaulting to politeness. When something is underspecified, name the unanswered concept and the section that owes it — "not specific enough" on its own gives the author nothing to act on.

**End with an "Optional polish" section**, separate from the findings above: wording-level fixes where you can supply the exact replacement and the meaning doesn't change. Write each as location plus replacement (before → after), ready to apply verbatim. If an imprecision changes behavior, scope, or a testable claim, it's a finding, not polish; if you can't write the exact replacement, it isn't polish either — raise it as a finding or drop it. When nothing qualifies, say so in a line rather than manufacturing items. Delivered as concerns, wording points cost the author a reread of the whole document; delivered as ready replacements, they cost nothing.

<snippet key="recover-context">
Your prior session was compacted unsuccessfully and reset, so you're in a fresh session with no memory of this run. Re-anchor before any work — this is a post-compact recovery from an empty session, not a routine reread of code you still hold in context: there's no prior context to lean on, so the orientation below has to carry the whole picture.

Orient from what's actually on disk and in git — fill each in concretely:
- What we're building: the change in a sentence or two, and where the authoritative design lives (the committed spec/plan, or the research decisions).
- What's committed and green: the work that already landed and passes tests, so you don't redo it.
- What's left: the next unit of work, plus any uncommitted in-flight edits.
- The load-bearing seams and files: the modules this change turns on, so you reread the right code first.

Then reread those files and rebuild your mental model from the actual code, not the summary — trace the real data and control flow and the constraints in play. No code yet: re-anchor first, then pick the work up from where it actually stands.

<snippet key="compact-inflight">
/compact This compaction lands mid-work — the same task continues in this session immediately after it, so compact for **continuing**, not for a stage transition: keep the work's live state, drop the journey.

**Preserve:**
- The work in flight and its exact state: what's in progress, files mid-edit, the next intended step.
- Every decision already made, with its reason.
- The concrete repo facts in use: paths, commands, test state, the working branch.

**Drop or summarize:**
- The exploration journey, superseded drafts, and old tool output — keep conclusions, not the path.

The committed artifacts survive on disk — cite their paths rather than restating them.

<snippet key="list-assumptions">
List every non-trivial assumption you're making — about the data, system state, my actual intent, failure modes, or what "done" looks like.

**Group as:**
- **Verified** — confirmed from code or my message
- **Likely** — reasonable inference, unconfirmed
- **Speculative** — guessing

Flag the speculative ones as questions for me before proceeding.

- what gets called, with what arguments

Use a concrete example input. **Stop and flag the moment behavior diverges from intent.** Don't summarize — actually trace.

<snippet key="technical-difficulty">
**Don't measure technical difficulty by lines changed.** Instead, consider:
- complexity of the problem being solved
- number of components affected
- potential for unintended consequences
- level of uncertainty involved

**Most importantly:** does this solve the core UX problem while maintaining a clean technical design?
