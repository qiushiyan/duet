## The document's shape
The doc runs top-down, product to technical, each tier at its own altitude.

**Product sections first — what and why.** Open with a leader-facing summary: what we're adding or fixing in product terms, the approach and its scope, and the boundary once it lands — what's fixed, what isn't, what's explicitly deferred (one-line why each). Then the goals, the user-facing behaviors, and the non-goals; distinguish current vs. desired — what's preserved vs. what's changing (a tree-style before/after often makes it crisp). Someone who reads only these sections should still know what they're getting and not getting.

**Technical sections below — the shape of the build:**
- **Module boundaries and seams:** which modules own the change, the interface each presents, and the coupling decision — an extension of an existing concept, or intentionally independent. Design deep modules: small interfaces, complexity concentrated behind them (the deletion test).
- **The foundation decision (preparatory refactoring):** is the existing code a base this extends cleanly, or a structure that blocks the design? If it blocks, scope a *bounded* reshaping as the opening move — sized to this feature, not a module rewrite — and name what you're deliberately leaving alone.
- **An architecture sketch:** how data and control flow through the changed system, in prose or a diagram — enough that the build starts oriented — with implementation anchors (modules, functions, files) attached to the flow, not as the main narrative.
- **Test standards:** the behaviors that must be tested, and for each the strategy — through which interface, what gets faked at which boundary — plus the gotchas worth flagging. Name *what to test and how to think about testing it*.

**Be concrete where you decide.** Vague verbs — "improve", "enhance", "polish", "streamline" — name a *direction*, not a *decision*; they quietly defer the real choice to the build. Say **what** changes: the specific behavior, state, or outcome that differs, and the rule or shape that produces it.

## What the build decides later
Leave these out — they're the build's to decide, and pinning them now would commit the design to details the code hasn't taught us yet: full code bodies, per-case test enumeration and fixtures, line-level edit plans, doc-update plans, and commit order. The design owes the *what* and the *shape*; the build owns the cases and the sequence.

**Do not include any time/effort estimates** ("2 days", "~3 hours") — describe the work itself.

If you have remaining product questions or major technical uncertainty, interview me before you write.

**Product sections — hold them to product altitude:**
- Vagueness on behaviors the feature must define (data flow, ordering, failure modes, scope, edge cases, current vs. desired) → **bug, flag it**.
- Module or test design pressed here → it lives in the doc's own technical sections; judge it there, not as a product-section gap.

**Technical sections — hold them to design altitude:**
- Module boundaries, seams, the architecture sketch, and the test strategy → **fair game; propose better** where a boundary is wrong, a module shallow, a seam misplaced, a test strategy weak, or the design over-built.
- Vagueness on full code bodies, per-case test enumeration, fixtures, line-level edit plans, commit order → **intentional, don't ask for them**: the build decides those, and pressing the doc down to that depth re-grows the review rounds this single document exists to avoid.

**Push hard on:**
- Are we solving the right problem? Is the UX goal right?
- Does the approach hold up: data flow, state, ordering, failure modes, performance, backward compat, migrations?
- Doc ↔ code mismatches; cleaner alternative approaches.
- **Whether the design deletes complexity or just rearranges it**, and whether the resulting modules are deep or shallow.
- **Foundation & preparatory refactoring:** a feature bolted onto a structure that can't hold it (a missing prep step), or a cleanup disproportionate to the feature (scope creep) — flag either.
- **Over-building** — defensive handling for states that could be made unrepresentable, speculative features or config nobody asked for, an abstraction pulled out too early. Flag these the way you'd flag a missing case.
- **Test standards:** do the named behaviors cover the critical paths, and are the strategies at the right altitude (behavior through interfaces, mocking only at boundaries)?
- Non-goals + open questions: anything in-scope that should defer? Anything missing from the uncertainty list?

**Per point:**
- Agree → add technical suggestions, caveats, or risks worth flagging.
- Disagree → give reasons and a concrete alternative. If architectural, say so and propose the structural fix.

Challenge assumptions and propose alternatives — don't default to politeness. Don't say "not specific enough" without naming the unanswered concept and the section that owes it.

**End with an "Optional polish" section**, separate from the findings above: wording-level fixes where you can supply the exact replacement and the meaning doesn't change. Write each as location plus replacement (before → after), ready to apply verbatim. If an imprecision changes behavior, scope, or a testable claim, it's a finding, not polish; if you can't write the exact replacement, it isn't polish either — raise it as a finding or drop it. When nothing qualifies, say so in a line rather than manufacturing items. Delivered as concerns, wording points cost the author a reread of the whole document; delivered as ready replacements, they cost nothing.

<snippet key="consultant-contract">
Your job this turn is to author an acceptance contract for the change specified below: a short, frozen list of falsifiable assertions that define what success MEANS for it — the runtime behaviors that, if they silently drift from the settled design, mean we shipped the wrong thing, and that the implementer's own tests would most plausibly miss.

You are the on-call engineer who will be paged at 3am when this ships broken. You don't trust a green test suite: tests confirm the author's understanding of their own code, and you are here for the other gap — the behavior the product actually depends on, pinned independently, before any code exists. You are reading the settled design document ONLY — the ratified spec, or the converged design doc — and you cannot see any implementation; no code for this change exists yet. That independence is the asset: a fresh read with no build in sight is what keeps this a definition of success rather than a description of whatever gets built.

Spend the whole contract on its reason to exist: assert only what is BOTH high-impact-if-wrong AND unlikely to be caught by the implementer's own tests. Their tests already cover "does my code do what I think"; the contract spends its budget on runtime behavior that can drift from the document's intent while every obvious test still passes.

Work in two moves, in this order — the order is load-bearing.

1. **Elicit the high-value behaviors — find them before you format them.** Scan the document for where being wrong is both costly and quiet. Strongest signals, in rough priority: the product's core promise; trust and permission boundaries; irreversibility and data loss; state-machine invariants and illegal transitions; idempotency, retry, concurrency, partial failure; the contract with callers (CLI flags, exit codes, output/schema stability); the error and failure envelope. Three techniques to surface them:
   - **Pre-mortem.** It is three months from now. This shipped and has been quietly wrong the whole time — no crash, no failing test. Write the post-mortem, then turn each cause into an assertion.
   - **Definition-of-wrong.** Don't list what it should do; list what would make it WRONG, not merely buggy.
   - **Red-team the tests.** Assume every obvious test passes. Describe an implementation that passes them all and still violates the intent — then write the assertion that closes that gap.

2. **Formalize the survivors into the template.** One observable behavior per line, each an ID'd, EARS-shaped assertion plus a mandatory evidence field:

   [A1] <When | While | If…then | Where | (ubiquitous, no keyword)> <trigger or condition>, the <system> SHALL <one observable response>.
     Verify by: <probe> → <exact expected observable>

   Discipline: SHALL / SHALL NOT only; one observable per line; explicit negations where the absence is the point; stable IDs, never renumbered; self-contained lines (no cross-references); binary pass/fail, no holistic score. Ban the quality-adjectives — "works", "correctly", "gracefully", "robust", "efficient" — they are unfalsifiable, so name the observable instead. Concreteness tracks the document: where it already fixes the surface (a flag, an exit code, a state field, a log line), make `Verify by:` concrete against it; where it defers to implementation, keep the probe behavioral ("the run RESUMES, not restarts"). You say WHAT to observe; the verifier resolves HOW in the built system — that division is what keeps the contract independent of the code yet still falsifiable.

Cap the contract to its altitude: a small fix earns 3–5 assertions, a normal feature 8–12. If you want more, the contract is at the wrong altitude — raise it. Do not restate the document as assertions, do not assert the obvious happy path the tests already own, and do not demand detail the document intentionally defers.

Write the contract to the path the orchestrator names, and do NOT commit it — duet freezes it when the human ratifies the design at its gate. Reproduce the full contract in your response as well, so the gate packet can carry it.
