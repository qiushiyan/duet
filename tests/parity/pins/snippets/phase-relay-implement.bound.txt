<snippet key="implement-design">
Build the change from the committed design doc — it is the authority for what we're building and why: its product sections carry the goal and the boundaries, its technical sections the module shapes, seams, and test standards the build must honor. Execute the design; don't re-decide it. This prompt carries the *how*.

## Read these first, then build
Read each one and adapt it to this change — they're the bar, not optional background; don't go hunting them mid-build, and ask me for a path if one's missing.
- `{{lessons_dir}}/codebase-design/deep-modules.md` — deep modules, seams, the deletion test, illegal states
- `{{lessons_dir}}/testing/tdd-loop.md` — vertical slices, red-green-refactor, the anti-patterns
- `{{lessons_dir}}/testing/mocking-and-fixtures.md` — mock only at boundaries; `test.extend` fixtures
- `{{lessons_dir}}/testing/test-quality.md` — what earns a place in the suite; assert tokens and relations, not prose
- `{{lessons_dir}}/testing/vitest.md` — Vitest APIs *(TS-Vitest projects only)*

## Before you write code
- **Re-read the design doc** — the goals and non-goals bound the scope; the module boundaries and seams are the target shape.
- **Re-read the code you're about to touch** — trace the real data/control flow and the existing patterns, so the change fits what's already there.

## How to build it

### Slicing
The design names the shape but deliberately not the build order — the slicing is yours. Build in **vertical slices** — one meaningful unit at a time (a behavior plus the wiring that belongs with it), each independently committable, one slice per commit. Lean larger; group related behavior rather than splitting mechanical steps into their own commits. **Prefer a shape that deletes a concept** — a branch, mode, or helper layer disappears — over one that just rearranges it. If the design called for reshaping the foundation first (*make the change easy, then make the easy change*), do it as the opening slice — **behavior-preserving**, kept green (pin uncovered code with a characterization test first), and proportionate; a prep slice that balloons into a rewrite is the failure mode.

### Right-size the code
The default failure here is too much code, not too little — defensive branches for cases that can't occur, and abstractions invented before the pattern is real. Build against it:
- **Make a bad state impossible to construct, don't guard against it.** Reach for a type, a narrow constructor, or an enum an invalid value can't inhabit, over runtime guards repeated at every call site. Validate untrusted input once at the boundary so everything downstream can trust it (*parse, don't validate*); where a state genuinely can't be made unrepresentable, validate at that **one** boundary. Let a real invariant violation fail loudly — not a fallback that hides the bug, or a local defense wherever it happened to surface.
- **Prefer a little duplication over the wrong abstraction.** Pull out a shared abstraction only when the pattern is real (around the third occurrence) and doing so *concentrates* complexity instead of just moving it (the deletion test).
- **Build only what the design settled** — no speculative features, config knobs, or extensibility seams it didn't ask for; each is maintenance forever.

### Build on the right layer
Where the design already settled a layer or dependency choice, follow it. Where a slice needs non-trivial, well-understood mechanical logic the design didn't settle — retries/backoff, concurrency limits, parsing, date/time math — decide deliberately between the platform's own primitives, a small specialized library, and writing it yourself. Hand-rolling a solved problem wastes effort; a new dependency is maintenance forever — take the lightest option that genuinely fits. Training data lags real releases, so ground the choice in what the stack offers *now*, not memory.
- **Prefer current stable platform primitives when they cover the need** — runtimes keep absorbing what libraries used to own (in TypeScript, `Intl` handles most date/time and number formatting without `date-fns`; native `fetch`, `structuredClone`, and `AbortController` replaced their old library equivalents). Confirm what's stable now rather than reaching for a dependency from habit.
- **Reach for a small, specialized library when it owns a genuinely tricky problem the platform doesn't** — retry/backoff and concurrency queues are the clear wins (e.g. `p-retry`, `p-queue`). Keep it specialized: a general-purpose giant pulled in for one function is its own cost.
- **When you adopt one**, check the repo doesn't already depend on something that covers it, then **confirm its current API with Context7** and **web-search for best practices, pitfalls, the latest version, and breaking changes**, and match how nearby code already wires its dependencies.

A dependency weighty enough to be an architecture decision in its own right is mine to weigh — flag it rather than committing the repo to it.

### Tests
The design's test standards name the behaviors that must be tested and the strategy for each — the specific cases are yours. Write each test against **real** behavior as you build its slice, not a batch up front against imagined shapes — behavior through the public interface, covering the critical paths and complex logic, not every edge case (skip UI tests unless asked). Before adding one, find where that behavior is already covered and assert only what's new: a second test proving what another already proves fails twice for one bug, and drifts when only one is updated. Skip the test that can't fail for a real reason — one pinning wording no caller depends on, or restating a constant — because coverage is feedback, never the goal. Apply red-green-refactor inside a slice when design is uncertain or behavior is subtle; test and code together is fine otherwise. Run them as you go and keep them green.

If the design turns out wrong or underspecified once you're in the code, **stop and flag it** rather than guessing your way past it.

<snippet key="midpoint-status">
Pausing mid-implementation for a checkpoint review. Summarize the current state so a reviewer can pick it up cold — **status snapshot, not a self-review**.

- **Where we are:** which slices are done and committed, and the slice you paused at (e.g. "4 of ~12").
- **What's done:** per completed slice, the behavior it added and any decision worth knowing — one line each, no code dumps.
- **What's left:** the remaining slices in planned order, briefly.
- **Test state:** what's covered so far and at what altitude, plus any test debt you've deferred (slices committed light on tests, placeholder mocks) — surface it rather than let it hide.
- **Deviations & surprises:** where the code diverged from the plan, what turned out harder or different than expected, and any plan assumption that didn't hold. **Be candid here — this is the highest-signal part.**
- **Open questions / risks** you're carrying into the rest of the work.

Ground it in the actual commits and code, not memory.
</snippet>
<snippet key="review-midpoint">
Implementation is **paused mid-way** — only some slices are done; the rest are intentionally not built yet. Review the work so far AND set up the rest to go well. **Read the actual code, not just the status report below.**

Two jobs:

**1. Review what's done.**
- **Correctness & tests** of completed slices — bugs, edge cases, test altitude.
- **Foundation soundness** — everything left builds on this. Are the abstractions, seams, and data structures chosen so far going to *hold* for the remaining slices, or will they need to be torn up later? Code-judo, spaghetti growth, thin abstractions, leaky boundaries, wrong canonical layer — flag them now while they're cheap.
- **Plan ↔ code tracking** — silent deviations, missing planned tests for *completed* slices.

**2. Guide the rest.**
- **Gotchas & traps** the remaining slices will hit given the current code — invariants to keep, sequencing hazards, places the existing shape fights what's coming.
- **Plan course-correction** — given what the code actually revealed, does the remaining plan still hold? Re-sequence, re-scope, or reshape a slice if warranted — say so explicitly. A remaining slice that could *delete* something already written is a win; call it out.
- **Tips** — existing helpers/patterns to reuse instead of reinventing.

**Time-axis altitude lens:**
- Slices not yet reached → **intentionally undone, do NOT flag as missing**.
- A foundational/structural problem that will **compound** across the remaining slices → **highest priority** — catching it at slice 4 is far cheaper than at slice 12. Flag loudly.
- A purely local nit in completed code that doesn't affect what's left → note briefly or leave it for the final review; **don't dwell**.

**Per issue:** mark **fix-before-continuing** vs **fine to defer to the final review**, and give a concrete fix with file/function references.

Status report from the implementer below for context.

<snippet key="implementation-handoff">
Implementation finished. Write a handoff that orients the reviewer fast — **report what changed and point them at what matters.** Ground it in the actual code and commits, not memory.

This is a guided map, **not a self-review** — don't grade your own work ("correct", "clean", "well-tested"); that's the reviewer's call. Do surface where the bodies are buried.

- **What & why:** the problem solved, tied back to the spec — a line or two.
- **Change map:** the files/modules touched, with the **load-bearing** ones marked. Skip trivial churn — the reviewer can read the diff; tell them where to start.
- **Key decisions & tradeoffs:** judgment calls made while implementing, especially structural ones (a boundary drawn here, a concept collapsed there), and any alternative you weighed and rejected.
- **Deviations from spec/plan:** where the code diverged and why. **Be candid.**
- **Tests:** what's covered and at what altitude (behavior vs. internals), plus what you deliberately left untested and why.
- **Where to look hardest:** the riskiest, most complex, or least-certain changes — anything you're unsure about or that fought you. This is the part that earns its keep.
</snippet>
<snippet key="review-and-fix">
Code-review this implementation — and resolve what you find. You review with write access: you didn't write this code, but you own getting it ship-ready. The bar is the committed design doc — its product sections carry the goal and the boundaries, its technical sections the module shapes, seams, and test standards the build was to honor. Review against the doc's intent, not a redesign of your own.

**First, understand what the builder did.** Read the actual code and commits, not just the handoff below. Where something looks wrong, work out what the builder was doing before judging it (Chesterton's fence: don't tear down what you don't yet know the purpose of) — an approach that reads oddly from outside often encodes a constraint you haven't hit yet, and where it is genuinely wrong, knowing the intent is what lets you fix it without breaking what the intent got right.

**Lens — everything is fair game:**
- **Correctness** — bugs, edge cases, failure modes.
- **Solves the problem** — does this achieve the goal behind the design, not just run?
- **Test quality** — right altitude (behavior, not internals), covers the real cases, survives plausible refactors, uses project patterns. Flag tests of *shape* that pass when behavior breaks, tests pinning wording or constants no caller depends on, a second test re-proving what an existing one already owns, and over-testing of edge cases instead of the critical paths. Deleting a low-quality test is a legitimate fix — make it, rather than keeping it for the coverage.
- **Structural quality — be ambitious, not just local:** a reframing that deletes whole branches/helpers/modes beats rearranging them; apply the **deletion test** to new modules; flag **shallow** ones (a thin pass-through wrapper, an interface nearly as complex as its implementation); keep logic in its canonical module.
- **Right-sizing — over-building is the likelier failure:** defensive branches for states that can't occur, fallbacks the invariants rule out, speculative config beyond the design, abstractions pulled out before the pattern is real.

**Then resolve each finding yourself — this round is review-and-fix, not review-and-file:**
1. **Assess validity honestly** — a finding you can't defend from the code or the doc isn't a finding. A test you'd add is held to the same bar: name the bug it catches and check nothing already covers it, since writing one is the cheapest move here and the one the suite pays for later.
2. **An ordinary valid issue: fix it directly**, and move the tests with the fix — add one for the corrected behavior, strengthen a weak one, delete what the fix makes obsolete. Keep the suite green; commit as you go.
3. **Where the code is right and your instinct was wrong: leave it**, and say why in your report.

**Escalate instead of fixing when a finding changes the substance:** a product or design disagreement (the doc said X, and X now looks wrong in the real code), intent you cannot reconstruct from the code and commits, or drift so broad that fixing it means re-deciding the build's direction. Fixing those directly would hide a pivot inside a review — flag them and leave that thread unresolved. Direct fixing is the default for ordinary issues, not a license to re-decide the work.

**Report when done:** the fixes you applied and the points you left as-is, each grounded in the actual commits, plus anything you escalated. This report travels into the summary the human decides to ship from, so it must reflect the final state of the code, not a plan for it.

<snippet key="ceo-summary">
Implementation and follow-up reviews are done. Write a CEO-facing summary of this PR — for me, and for explaining the work to a non-technical stakeholder without walking them through the code.

**Lead with the bottom line** — the one or two sentences you'd give the CEO in the elevator: what this ships, and why it matters to the product. Everything after supports that line:

1. **The outcomes, concretely** — the problems now solved, the bugs now fixed, the features now available. Product terms, not mechanisms.
2. **The technical side at CTO altitude** — the shape of the approach and the one or two decisions a CTO would care about. No file paths, no function names, no implementation play-by-play.

Answer first, support after: a reader who stops at any point should leave with the most important thing they could have gotten by then. Drop any section that's empty. Tight prose beats exhaustive sections.

<snippet key="consultant-verify">
Your job this turn is to verify the implemented change against its frozen acceptance contract — assertion by assertion, on observed behavior, never by reading the diff.

You are the on-call engineer who doesn't trust a green test suite. This contract was authored before any code existed, blind to the implementation, and ratified by the human; it is the independent definition of success. Your task is to find out whether the built system actually satisfies it by RUNNING the system and citing what you observed — because reasoning from the code is exactly where this kind of check goes wrong.

Work each assertion in ID order:
1. **Gather evidence by exercising the system.** Run the relevant tests, run the CLI or binary, hit the endpoint, read the logs and output — whatever the assertion's `Verify by:` calls for. You may read anything and run observational, read-only commands; you must NOT edit tracked source, commit, push, install packages, reach external networks, or touch the orchestrator's own run state (do not invoke duet itself, and do not write under .duet/). If a probe is underspecified for the built system, resolve a reasonable concrete observation and state how you observed it.
2. **Return a binary verdict grounded in the evidence.** For each assertion: `[A1] PASS` or `[A1] FAIL`, followed by the exact command and observation that grounds it — the output you saw, the log line, the exit code. No holistic score; each line stands on its own evidence. A FAIL means the OBSERVED behavior contradicts the assertion; quote the contradiction.

Then, briefly: **residual concerns** — anything the assertions don't capture that you believe undercuts the bet now that it is real code. Grade each low/high. This is the room for what a frozen list couldn't have foreseen; keep it short.

Grade the finding the human reads:
- **high** — one or more assertions FAILED, or a residual concern that should hold the ship. A failed assertion is load-bearing: report each as its own high so the run stops for the human rather than shipping past a broken target.
- **low** — every assertion holds; a residual concern worth the human's eyes but not blocking.

"Every assertion holds — ship" is a first-class, expected outcome; say so plainly when the evidence shows it.
