# Future directions

The product-direction ledger: where duet goes next, what's shelved with a revisit trigger, and what was considered and declined. Companion to `docs/open-questions.md` (design decisions inside the current product); this doc tracks candidate *changes to what the product is*. Directions here were weighed against the product goals in `CLAUDE.md` and a user interview (2026-06-12) on actual usage: during AFK stretches the human is variously at the machine on other work, away with a phone, or asleep; mid-phase steering urges arise "sometimes"; at gates the packet text reads fine but composing substantial feedback in shell flags is the friction; remote reach matters.

**Standing constraint for anything remote:** duet never builds its own mobile/remote/notification layer. Either a direction works local-first, or it rides an existing product's remote surface (Claude Code remote control, Tailscale). Hand-rolled remote infrastructure is out of scope permanently.

## Active: Claude Code as the interaction layer

The gap it closes: the run can talk to the human (notification, packet, queued question) but the human couldn't talk back except at quiescent stops, from the terminal, through shell-flag strings. The interaction asymmetry was the biggest product gap after run-1. Two variants, sequenced deliberately: the concierge first, then the in-CC orchestrator — now built over the planning stage, with the first live session still ahead.

**B — concierge: built** (spec: `docs/specs/2026-06-12-concierge-package.md`; plan: `docs/plans/2026-06-12-concierge-package.md`). Three pieces ride existing seams, and Claude Code's native remote control, mobile push, and `/loop` supervision become duet's remote layer for free:

- `duet steer "<note>"` — the human's mid-phase voice: file-per-steer staging, delivered verbatim on the orchestrator's next phase-continuing tool result, carried into the next harness prompt when it misses the phase; at a quiescent stop it refuses toward that stop's own channel. Design detail: automation-design §"The steer channel".
- `duet status --json` — the status model under both renderers; the discriminated `stop` (running / gate / flag / crashed / done) carries the command that acts at each position, making the concierge's channel translation mechanical. Schema additive-only, pinned by test.
- `skills/duet-concierge/` — the shipped skill (repo-owned `skills/`, distinct from dev-time `.claude/skills/`; install by symlink or copy, the user's choice): verbatim relay, relay-not-fourth-engineer, turn-ending stop reports (what fires CC's mobile push), Sonnet-class session recommended in prose, never pinned. Read verbs are the only pre-approvals; the recommended `ask` rule on `duet continue*` makes a gate crossing take the human twice, phone included — even a rogue concierge cannot cross alone. Full envelope: it reads, steers, continues, and starts runs from dictation; only `takeover` stays terminal-only by nature.
- **run-operations (2026-06-19)** — supervising from outside gained the *health* half to match the position half: `duet doctor` (per-voice verdict + connectivity), a health-enriched heartbeat, the signal-only `humanDecisions` / `cause` triage fields that make hold-vs-relay mechanical, a lean `status --brief`, a hardened non-TTY write path, and opt-in bounded infra retry. All ride existing seams; implemented and test-verified, awaiting the same first-live-session evidence (spec: `docs/specs/2026-06-19-concierge-run-operations.md`).

The harness gained no daemon, no server, no machine events — the concierge is interaction glue, killable without consequence (augment-never-lock-in holds). CC capabilities were verified against docs 2026-06-12: remote control (`/remote-control`, outbound-HTTPS, Mac stays awake — already true for any duet run), mobile push on turn-ending reports, `/loop`/Monitor supervision, permission `ask` prompts surfacing on mobile. Deferred utilities, until publishing turns real: a `duet skills install` convenience, a `.claude-plugin/plugin.json`, `duet runs --json`. One hazard to respect: never build on duet's own harness as a duet run — workers would edit the source live drivers re-spawn from. **What remains is evidence, not code: the first live remote session (phone + `/remote-control` + a real run), and the first overnight run that uses steers.**

**A — orchestrator in CC: built over the planning stage; live verification is what remains.** The orchestrator becomes an interactive CC session talking to the human directly — steering, triage, and gate conversation native, from anywhere.

The foundation (the host-neutral kernel) was proven first: the event-driven `phase.*`/`human.*` statechart, the persisted terminal marker with its crash-recovery guard, crash=flag, and nudge-once all behave identically whether the orchestrator runs in-process or over a real stdio MCP boundary — so re-homing the orchestrator into a separate process, once feared as the hard cost, is a settled property, not a rewrite. On that foundation the **user-visible orchestrator is now built** (spec/plan: `docs/specs/claude-as-orchestrator.md`, `docs/plans/claude-as-orchestrator-stage1.md`): the human's interactive CC session drives a run over FRAME → SPEC → PLAN and hands off to the headless driver at plan approval. The pieces — a `duet orchestrate` / `duet new --interactive` launcher that seeds a first turn so the session opens working rather than blank, a run-scoped MCP server the session connects to for the whole attended stretch — on which `send_prompt` is fire-and-collect, so the session stays live and steerable while a worker turn runs instead of freezing inside the call for minutes (`docs/specs/2026-06-21-async-interactive-send-prompt.md`; test-verified, live end-to-end + smoke tests pending) — the launcher-fed `prompts/orchestrator-identity.md` system prompt (the identity is wired at launch — there is no `/duet` slash command), inline `duet continue` crossings until the plan-gate handoff — all carry the read-only conductor identity across compaction and reconnect. Its single safety setup is one `ask` permission rule on `duet continue` that survives the human's bypass-permissions default; no tool can emit `human.*`, so even a Bash-equipped session cannot cross a gate alone. Both ends of a run are now CC sessions: a shipped `skills/duet-frame/` skill authors the *framing* (a rough problem sharpened into a clean framing — real names, structure, gate posture — without changing intent or proposing solutions, then emitting the `duet new --interactive` command), and the interactive orchestrator drives it.

**What remains is evidence, not code** (mirroring B): the first live interactive orchestrator session — a real CC session driving a real run — the human's environment smoke tests, and a check that the launcher's seeded kickoff actually auto-submits in the interactive TUI (it's pinned in the launch argv but unverified live); nothing here has been exercised live yet. The direction also forecloses codex-as-orchestrator (the launcher is claude-specific) and deepens CC dependency — a one-way door, acceptable under the standing constraint. **B (concierge) remains a strict stepping stone**: its primitives, steer, and relay discipline carry over, and living with B is the evidence for whether talking-to-the-orchestrator beats relaying by enough to fund living on A.

**Deferred — direct human→worker steering (the "targeted steer" seed).** A recurring idea on top of A: from the interactive session, let the human push a prompt straight to one worker (especially the builder) for an end-game cleanup nudge — skipping the orchestrator relay, lighter than `takeover` (no terminal, no driver stop), more pointed than `steer` (no orchestrator interpretation). Researched 2026-06-23 (the short run that built the tmux-polish bundle); **deferred, not built** — two findings sink the literal proposal. (1) *The mechanism and the scenario never co-exist in time:* the interactive session ends at the stage boundary (`enterAfk`/`crossInteractive` clear `orchestrationHost`, and the run-scoped MCP server then refuses every call — `mcp-server.ts`), but "end-game cleanup" (build convergence, docs, PR) is entirely delivery-stage work, so a direct send "from the interactive session, for end-game" describes two states that don't overlap — and on short the cleanup is the headless `implement` and `finish` phases — the docs reconcile and the PR opens in delivery like everything else here, so the interactive session can't reach it either. (2) *A direct write reopens four load-bearing invariants:* the **two-writer guard** (the interactive MCP refuses calls once a headless `_drive` owns the run), the **single-writer lease** (`mcp-owner.json`), the **same-duty in-flight guard** (one worker session is one conversation — a direct send races a turn the human can't see, the exact thing `takeover` refuses), and **sole-commander / auditability** (bypassing the orchestrator's model loses the "why this snippet, why this adaptation" trail, success-criterion 3). The cost saved is one relay hop; the price is those four — a bad trade.

The seed worth keeping is the race-free 20%: a **targeted steer** — `duet steer --to <duty> "<note>"`, an optional recipient *hint* on the existing steer payload, still delivered *through* the orchestrator on its next tool result. The orchestrator stays the commander that schedules delivery when that duty is free, so all four invariants hold and the concierge's relay discipline is intact; it removes only the human's felt overhead of explaining who they meant — an enrichment of `steer`, not a new socket. A *truly* direct push, if ever wanted, should fire only under `takeover`'s own precondition (target duty idle/parked, no orchestrator turn in flight) — at which point it has nearly rebuilt `takeover`, suggesting the real gap, if any, is "make `takeover` lighter," not "add a fourth channel." **Trigger:** the first live interactive-orchestrator run — on the *full* workflow, during planning — shows that relaying a finishing-move to a worker is genuinely high-friction; that observation also defines the right seam, so build from it, not before it.

## Shipped from this ledger

**External workflow definitions — shipped 2026-07-05 as a TypeScript SDK** (`duet/workflows`; the design now lives in `automation-design.md` §"The workflow vocabulary"). The original `.toml` guess became an SDK the standard library itself dogfoods, and the compile-and-freeze kernel is the load-bearing part: compiled once at `duet new`, frozen into the run, source files never read again. The grammar remains non-composable (gates, one branch per run, read-only orchestrator, framing as the project-knowledge seam); only the closed block vocabulary is authorable. Follow-ups stay deliberately separate, each waiting on its own evidence: project-snippet membership by custom phase, a TOML adapter if TypeScript chafes, and the first composition that needs a new prose world (open-questions.md §"Settled, still watched").

## Shelved — interesting, with revisit triggers

**Interactive Claude worker transport: production hardening** (built as a spike — [`docs/interactive-transport.md`](interactive-transport.md)). A claude maker duty (the architect or builder) can already opt into driving the interactive `claude` TUI (`transport = "interactive"`) so its turns bill the flat subscription quota instead of the metered Agent-SDK credit pool — the maker lane is the cost driver (~$85 of the ~$93 first real run). The spike is tmux-driven, proven over fakes, with one live-auth gate still open. What's shelved is the *production* path, all of it carried by the same seam: an owned-pty transport behind `PaneController` (the transcript parser reused unchanged — no rework), failure isolation, phase-scoped pane reuse to kill the per-turn cold-start, a read-only variant so a claude checker can also bill the subscription, and the default flip. **Trigger:** the spike clears its live-auth gate *and* a real run strains the metered credit pool enough to be worth the native pty dependency — or the unattended heuristics (screen-polled readiness, fire-and-forget injection) actually misfire overnight.

**Project profile: a default-loaded pre-context (`.duet/` "CLAUDE.md-for-duet").** *The trigger fired and the scaffold half shipped (2026-06-16).* The copying it predicted showed up — two byte-identical planlab framings — so `duet new --template <name>` now seeds the editor draft from a project's own `.duet/templates/<name>.md` (bare `duet new` prefers `.duet/templates/default.md`); the common framing is written once and only the run-specific problem is filled in per run (`src/surfaces/framing.ts`, `resolveTemplateSeed`). A template is **pre-baked framing** — parsed and archived like any framing — so the single-entry-seam property holds untouched and no new config surface appears. What stays shelved is the heavier **merge** model the original entry described: a durable profile auto-loaded into every run as pre-context, with the framing shrinking to the run-specific *delta* rather than carrying the whole (scaffolded) text each time, plus the optional layer where the orchestrator proposes profile additions at run end (human-gated like snippet edits). **Revisit trigger:** when the scaffold's copy-per-run cost starts to bite — a template drifts from the framings older runs archived, or you want one edit to reach every future run without re-templating. The templates already sit where a profile would grow, so the upgrade is a template gaining a `profile:` reference, not a rewrite.

**Eval/replay harness.** Re-run a recorded phase's orchestrator against scripted workers (voice logs replayed through the `WorkerProvider` seam; the SDK boundary is already injectable) and diff routing choices — snippets picked, adaptations, triage calls, convergence judgment — against the original. Turns prompt changes from faith into A/B evidence without $93 runs; the open calibration questions (triage precision, run-level budget, the overnight watch) all currently wait on real runs as the only eval. **Trigger:** the first prompt change that makes a run worse and we can't tell why. Compounds every other direction.

**Multi-run attention queue.** Worktrees already give parallel runs separate cwds; nothing manages the human side — which run needs me next, notification collisions, one combined gate queue. Concurrent worktree sessions are observed behavior (planlab Jun 10, `2c6a7f46` + `d531410e`). Strong synergy with the concierge: one chat session supervising N runs. **Trigger:** the first missed gate during parallel runs.

**Successor relay: a run stages its follow-on run's framing.** The chain is live manual practice in one project: planlab's migration series ran five full runs back-to-back (2026-06-23 → 07-01, each idling 9–17 h at overnight gates before the next began), and each PR ends with a project handoff skill (`pl-loopy-infra-handoff`) that reconciles the as-built docs, passes commander's intent forward, pressure-tests the next PR's scope against the as-built, and emits the next run's kickstart — staged as complete duet framings, frontmatter and all, in the project's `.duet/` **(observed)**. The duet-native form, designed 2026-07-02 and deliberately unbuilt: an opt-in finishing-tail step (a framing key or flag, off by default — plugin-shaped, never core) where the worker that owns the finishing tail — the builder; relay's judge — holding the as-built context a cold session would have to rebuild, authors the successor framing, its method resolved by the same precedence `reconcile-docs` uses (framing-named handoff skill → project convention → a shipped generic snippet carrying the two-register handoff discipline). The result is **staged, never started**: a plain framing file surfaced by `duet status` and the final packet, launched only by the human's own `duet new` — no daemon, no new authority, and ignoring the file costs nothing (augment-never-lock-in holds). Worktree-agnostic; stacked-run rebaselining and the human-side supervision belong to the multi-run attention queue above, not this entry. Why shelved rather than built: the pipeline shape fits sequenced-PR migration work, but most projects ship separated features that don't build on one another — and framing *prose* already delivers the behavior for the one project that wants it (instruct the finish phase to run the project's handoff skill and write the staged framing; no duet change needed). **Trigger:** a second project grows the staged-framing chain by hand, or the framing-prose form becomes routine and its missing surface — status visibility, a one-tap launch — is the observed friction.

## Considered, not pursued

- **Local browser dashboard.** The original candidate; the interview removed its rationale — packet text reads fine (no rendering need), remote must not be hand-built (no act-from-anywhere), and the comfortable-input need is met by the concierge's chat box. What remains (buttons in a local browser) doesn't beat tmux + CLI. Recorded so it isn't re-proposed on the same grounds.
- **Workflow presets** (lighter workflows for small fixes) — *shipped 2026-06-21 as the workflow now named short*, reversing the earlier "duet stays epic-shaped" stance. A run now picks its workflow; the lighter `research → implement → finish` shape lives beside full (`docs/automation-design.md` §"Phases and gates").
- **Environment-proxy ergonomics** (pre-composed command requests at flags). Generic `ask_human` suffices at current run volume.
- **Third *specialist* worker.** A third *maker* — a domain worker owning a slice of the build — still cuts against the two-worker-per-stage legibility (one maker, one checker); specialization belongs in snippets, not new duties. Distinct from the **consultant** (shipped 2026-06-22, `docs/automation-design.md` §"The voices"): that is an *optional advisor voice*, not a specialist maker — additive, read-only, ephemeral, off by default. It widens the checking altitude; it does not add a maker, so the two-worker legibility this entry protects still holds.
- **Snippet customization for non-authors** — *shipped 2026-06-25.* The user-facing form of "specialization belongs in snippets": two opt-in per-key override layers — a user `~/.config/duet/snippets.toml` and a project `<repo>/.duet/snippets.toml` — replace individual snippet bodies over the shipped defaults (last-wins, fail-closed on an unknown key, byte-identical when absent; `duet snippets` inspects provenance), so an adopter reshapes duet's *opinion* without forking. Distinct from the shelved **project profile** above: it customizes the *tool's* prompts, never injects project knowledge, so framing stays the single seam (`docs/automation-design.md` §"What the MVP should *not* do"; README §"Customizing the snippets"). Extends the snippet-library ownership decision from "duet owns `snippets.toml`" to "duet owns the *default* library; users may layer overrides."
- **Multi-PR pivots inside one run.** Observed in the corpus, but "finish the run, start a new one" is cheaper than machine support.
- **OSS-ification** — *superseded 2026-07-03 by the workflow-vocabulary repositioning* (`automation-design.md` §"The workflow vocabulary"): "personal tool first" softened to **opinionated defaults, built for publication** — duet is a composition vocabulary with an opinionated standard library, and its shipped artifacts are written for any user. What did not change: augment-never-lock-in, the human owns substance, semi-AFK, no daemon, framing as the single knowledge seam, exactly two providers — and publishing remains a kept-open option with no community roadmap, so the *pace* of the old stance survives even though its rationale is retired.
