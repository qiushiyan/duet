# Run operations — CLI, lifecycle, viewing, supervision

The operational surface of a run: every command, the framing input and templates, run state on disk, the viewers, and how a run is supervised from outside. `docs/automation-design.md` (the spine) carries the process model (per-phase driver, gates as process exits) and the gate-posture semantics; `docs/afk-resilience.md` carries the failure modes the supervision machinery exists for.

## Invocation

CLI surface (implemented in `src/surfaces/cli.ts` across every workflow):

| Command | What it does |
|---|---|
| `greenflag new [--workflow <name>] [--spec <draft-path>] [--framing <file>] [--template <name>] [--gates-at <phases\|preset>] [--gateless] [--interactive\|--no-interactive] [--resume-session <id>] [--bind <address>=<p[:m][@effort]> …] [--no-consultant] [--retry-infra <n>] [--budget <off\|default\|N>] [--tmux]` | Starts a run. With neither `--spec` nor `--framing`, opens `$VISUAL`/`$EDITOR` on `.greenflag/framing-draft.md` (seeded from the built-in template, the project's `.greenflag/templates/default.md`, or — with `--template <name>` — `.greenflag/templates/<name>.md`, a typo'd name aborting with the available list; GUI editors like VS Code get `--wait` injected; the draft is archived into the run dir as `framing.md` on creation) and starts framing-only from what the user saves — an empty or untouched file aborts. `--template` is the bare-entry path only; it conflicts with `--spec`/`--framing`, which supply the framing directly. With a draft spec, enters at the spec review rounds; framing-only entry runs the FRAME phase first. `--gates-at` (or the framing frontmatter's `gates_at:`) pre-authorizes the unlisted gates. `--retry-infra <n>` (or `retry_infra:`, flag-wins) sets the headless run's bounded auto-retry budget for transient infra failures (§"Supervising a run from outside"); **default 3** for a new run (materialized at creation), `0` the explicit opt-out, an old/absent value off byte-for-byte. `--budget <off\|default\|N>` (or the config `budget` key, flag-wins) sets the opt-in per-turn cost caps; absent ⇒ off (unbounded). `--gateless` (or `gateless:`) is the walk-away-from-the-start posture; it conflicts with `--gates-at` and an *explicit* `--interactive`/`interactive:` — a bare gateless launch simply runs headless, overriding the terminal's interactive default. Interactive orchestration is the **default on a live terminal** (2026-07-11): with neither flag nor `interactive:` key stated, a TTY launch brings up the interactive orchestrator, a gateless or non-TTY launch defaults headless. `--interactive` forces it, `--no-interactive` forces headless (flag wins over frontmatter); an *explicit* `interactive:` framing run from a non-TTY host fails loudly rather than stranding. `--resume-session <id>` warm-starts the interactive orchestrator from an existing Claude Code session instead of a fresh one; it needs an interactive run, and the framing author (`/greenflag-frame`) captures the id (`CLAUDE_CODE_SESSION_ID`) and bakes it into the emitted command. `--bind <address>=<provider[:model][@effort]>` (repeatable, or the framing's `bind.*` keys — flag wins per key) binds a duty or run-long voice for this run; on creation the resolved manifest is echoed — workflow, each stage's duty bindings, consultant, degraded continuity edges, gate posture (`docs/voices-and-providers.md`). A headless launch returns immediately, the phase running in a detached driver to its next attended stop; an interactive launch hands the terminal to the orchestrator session until the handoff gate. |
| `greenflag continue [run_id] [--approve ["rider"] \| --reject ["…"] \| --answer "…"] [--edit] [--tmux]` | Resumes past the current gate or answers a queued `ask_human` flag; defaults to the latest run. An approval may carry a **rider** — agreement plus adjustments, delivered into the next phase as gate feedback in approving form — passed inline or composed in `$EDITOR` with `--approve --edit`. The editor tracks whether the human content is *required*: reject and answer need it, so a bare `--reject`/`--answer` opens `$EDITOR` on a TTY (an empty save aborts) and off a TTY fails fast naming the inline / file / stdin forms; an approval's rider is *optional*, so a bare `--approve` approves with no rider. `--reject-file <path>` / `--answer-file <path>` (with `-` for stdin) relay the human's exact words — apostrophes, newlines, em-dashes — byte-for-byte, past shell quoting. Returns immediately (detached driver); refused while the run's phase is still driving. With no flags: status if waiting at a stop, crash recovery if a phase died mid-flight (the run-position probe says which, and re-utters the crossing the run state evidences). `--tmux` opens or reuses the run's viewer. |
| `greenflag steer "<note>" [run_id]` | Stages a mid-phase note for the orchestrator — the human's voice, delivered verbatim on the next phase-continuing tool result (spine §"The steer channel"). Legal only while a phase is live or died mid-flight; at a gate, flag, or finished run the refusal names that stop's own channel. |
| `greenflag afk [preset] [run_id] [--gateless]` | The mid-session AFK handoff: from any **interactive** gate parked on the approve path — *including a pre-authorized one* — re-set the downstream gate posture (bare = attend nothing; a preset/list otherwise) and drop the run to the detached headless driver in one tap. `--gateless` is the interactive→gateless bridge — attend nothing downstream *and* narrow the consultant to its non-holding work (frame + backstop, bet audits off); it crosses the bet/product `high`s at this gate (the explicit full-send, like `--approve`) but still refuses to hand off when the contract backstop is missing, and conflicts with a posture argument. Legality keys on the gate *position* (`probeRunPosition` kind `gate`), not `gateAttended`, so it works from a pre-authorized interactive gate too. Posture is written first, the gate crossed, the interactive marker cleared; the printed attended/pre-authorized split makes the single tap informed consent. After it runs the run is an ordinary headless run, auto-crossing the now-pre-authorized gates and stopping only at a still-attended gate, a queued question, or done. |
| `greenflag view [run_id] [--here]` | Opens (or reuses) the tmux viewer for a run and prints the raw log paths; the window is inserted after the current one. `--here` replaces the current pane with the viewer instead (ephemeral, needs tmux). |
| `greenflag logs [run_id]` | Streams the driver narration inline (replay + follow of `driver.log`). Ctrl-C detaches; the run is unaffected. |
| `greenflag takeover <voice> [run_id]` | Hands a voice's session to the human — a duty, the `orchestrator`, or the `consultant`: opens the provider's interactive CLI (`claude --resume <id>` / `codex resume <id>`) on that voice's session (a duty resolves its own slot or its live continuity edge's; a refusal names the run's *real* duties — a full run has no judge). Refused while the phase driver is alive (a manual turn would race the orchestrator); at a gate or flag it's the augmentation principle as a command — manual turns land in the same transcript greenflag later continues from. |
| `greenflag abandon [run_id] [--purge]` | Stops a run for good: kills the live driver if one is running (SIGTERM→SIGKILL — only the driver pid, so an in-flight worker turn finishes into its own transcript) and marks the run abandoned, so the position probe reads a deliberate stop, not a crash. The transcripts stay, so `continue` revives it (clearing the marker) and `takeover` is unaffected. `--purge` also deletes the run dir and every session transcript (the orchestrator's and each duty's, by exact session id — `src/voices/sessions.ts`): the one place greenflag reaches outside `.greenflag/` into the user's `~/.claude`/`~/.codex`, so it echoes every path it removes, and it doubles as the post-PR cleanup. |
| `greenflag status [run_id] [--json] [--brief] [--wait]` | Current state, queued flags, phase summaries, round counts vs. caps, costs, queued snippet proposals, pending steers, gates auto-crossed while you were away, next command. `--json` emits the status model verbatim: one derivation under both renderers, whose discriminated `stop` (running / gate / flag / crashed / abandoned / done) carries the exact command that acts at each position. The schema is additive-only — it is what the concierge skill reads, so a field rename is a breaking change to the shipped skill (pinned by test). `--wait` blocks until the next stop, then prints — the one deterministic supervision cycle, owned by the CLI so watchers never reinvent polling. `--brief` is a lean projection — position, a one-line headline, the next command, pending steers, auto-approvals, and the gate's `humanDecisions` — for fast polling; the three flags compose on orthogonal axes (projection × renderer × timing). The model also carries `sessions[]` (each persisted slot with provider and session id), `context` entries per `{voice, …}`, `pendingTurns` entries per `{duty, …}`, and, on the relevant stop, the gate packet's `humanDecisions[]` and the flag's `cause` (`human` / `infra` / `budget`) and `errorClass` (infra-only) — all additive. |
| `greenflag doctor [run_id] [--json]` | Per-voice **health**, not position: each voice's verdict (`idle` / `working` / `long-inference` / `retrying` / `silent-stuck` / `crashed`), last-activity age, retry count, recent classified errors, and a one-shot connectivity probe (network-down vs. reachable-but-auth-rejected). Reads the workers' own transcripts and the network — heavier than `status`, so it is its own verb and strictly the health renderer. `--json` emits rows keyed `voices`, each with its resolved transcript path. Fail-soft: every transcript/network read degrades to a note, never throws. |
| `greenflag runs` | Lists known runs in the project. |
| `greenflag workflows [check <name> \| init <name>] [--json]` | Pre-run inspector for the workflow-definition layer (spine §"The workflow vocabulary"), the read-only sibling of `greenflag snippets` for compositions. Bare: lists every definition across the shipped/project/user layers, collisions surfaced in their own section. `check <name>`: resolves and compiles one, printing its phases, stage duty-pairs, default gates, consultant checkpoints, bindings, and acceptance-contract placement — loader/compiler errors surfaced unwrapped, no run started. `init <name>`: scaffolds a typed project starter that refuses any name resolving in any layer. Executes nothing on the bare list and writes nothing under `.greenflag/runs/`. |
| `greenflag graph [--workflow <name> \| runId] [--json] [--mermaid]` | The structural viewer (§"The graph surface"). |
| `greenflag stats [runId] [--trace] [--json]` | Per-run cost/log stats; `--trace` renders the interleaved execution timeline (§"The graph surface"). |

## The framing input

A single markdown file: an optional machine-parsed frontmatter block — the run manifest's framing tier, parsed deterministically by the CLI and stripped before the orchestrator sees the framing (the key list and the boundary rule live in one home: spine §"Gate pre-authorization") — followed by prose sent verbatim, structure by convention not contract. The prose is also the orchestrator's project briefing — the only place the project's own *knowledge* enters the system, as distinct from the tool-customization artifacts (seed templates, snippet override layers) that tune greenflag's prompts across runs without telling it about the project. A shipped `/greenflag-frame` skill authors this framing — a CC session that sharpens a rough problem into the framing document without changing intent or proposing solutions, then emits the `greenflag new --interactive` command (coherence-pinned by `tests/skill.test.ts`).

**Seed templates.** The framing is mostly project-stable — onboarding skill, conventions, verification, doc rules — and only the problem changes run to run, so a project can pre-bake framings under `.greenflag/templates/` and seed the editor draft from one. `greenflag new --template <name>` reads `.greenflag/templates/<name>.md`; a bare `greenflag new` prefers `.greenflag/templates/default.md` over the built-in skeleton. A template is a *full framing* — the same frontmatter-plus-prose shape — so each kind of work can carry its own posture: a `feature.md` that pre-sets `gates_at: skip-plan`, a `bug.md` that names a different onboarding skill, with `# Problem` left as the per-run blank. A typo'd `--template` aborts with the available list. A template is pre-baked framing, not config: it is parsed and archived as the framing itself, so the framing turn stays the single entry seam for project knowledge (spine §"What the MVP should *not* do").

## Ending a run

Between quiescent stops no greenflag process exists, so a run never *needs* terminating — leaving it is simply never calling `greenflag continue` again; the run dir stays an inert record (keep `notes.md`, the dogfooding evidence) and a later `greenflag new` supersedes it as the default. `greenflag abandon` is the explicit form (table above); abandonment stays reversible until `--purge`.

## State on disk

The run dir `.greenflag/runs/<run_id>/` holds `state.json` (the human-readable hint: state value, session ids, queued flags, rounds, costs, proposals, auto-crossed gates), `machine.json` (the statechart snapshot, written **only at quiescent states** — gates, flag-waits, done), `framing.md` (the verbatim framing archive), one append-only log per voice, `driver.log` + `driver.pid` (the detached phase driver's stdout and liveness), and `notes.md`. The JSONL transcripts are the source of truth.

Greenflag's runtime artifacts live under `.greenflag/`, never at the repo root: the directory self-ignores (`.greenflag/.gitignore` containing `*`, written on first creation — the user's own `.gitignore` is never touched, and `git add -f` still allows committing a run record deliberately), the bare-`new` framing draft edits at `.greenflag/framing-draft.md`, a project's seed templates live in `.greenflag/templates/<name>.md` (self-ignored — carve `!/templates/` into `.greenflag/.gitignore` to share them across worktrees), and the `implement` entry prompt points workers at this run's own scratch dir (`.greenflag/runs/<id>/scratch/`, gitignored and torn down with the run) for throwaway verification harnesses — and forbids deleting anything under `.greenflag/`, which holds the live run state (a worker's `rm -rf .greenflag` while cleaning scratch once killed a run mid-build; `ensureRunDir` now self-heals a vanished run dir on the next harness write, so a stray deletion degrades to a recovered write, not a silent death). Specs, plans, and docs are project files and never live here.

## Visualization: tmux is a viewer, never the runtime

Settled 2026-06-11. Greenflag owns its subprocesses and writes **one append-only log file per voice** — `orchestrator.log`, one per duty, `consultant.log` when bound — under `.greenflag/runs/<run_id>/`, with a harness-written boundary line where a continuity edge carries a session forward. Without tmux, the same lines stream to greenflag's stdout with colored `[tag]` prefixes (picocolors auto-disables off-TTY). With `--tmux` on `greenflag new` / `greenflag continue` — or `greenflag view` for a run already going (`src/surfaces/view/tmux.ts`) — greenflag shells out tmux commands via execa (no library) to open **one titled pane per voice** — the orchestrator plus the *current stage's* duty pair (and the consultant when bound), derived from the registry enumeration and retitled at the stage boundary — each running `tail -n +1 -F` on its voice's log (full replay in a late-opened pane; waits for logs that don't exist yet). Wide displays get a 2-column layout (orchestrator over the checker left, the maker full-height right — it produces the longest content); narrow stacks every voice full-width. Three render targets: inside tmux, a `greenflag-<run_id>` window inserted after the current one without stealing focus; `greenflag view --here` replaces the current pane (ephemeral); outside tmux, a detached session with a printed attach command. Re-invocations reuse the viewer; any tmux failure degrades to a one-line note (`src/view/notify.ts` philosophy — a viewer must never affect the run).

**Context fill is first-class run telemetry.** Each voice's context-window percentage is captured at turn boundaries — never polled: claude-bound voices report usage in-band (the same formula Claude Code's own statusline uses), codex turns end with one tail-read of the session rollout. The reading lands in `state.json` (a hint — stale after manual takeover turns, refreshed on the next driven turn), in the voice-log response headers (`· context 41%`), in `greenflag status` and the `--json` model's `context` field, and in the tmux pane titles via a plain-text sidecar (`.greenflag/runs/<id>/context/<voice>`). Numeric percentages only, by decision; capture is best-effort and fail-soft — a missing reading is an absent line, never a failed turn.

**Color is view-time only** (2026-06-12): the log files stay plain text — the inspectable-without-greenflag artifacts — and each pane pipes its tail through `greenflag _colorize <voice>` (`src/view/colorize.ts`), which localizes timestamps (the stored log keeps raw UTC), paints header lines in the voice's color (orchestrator cyan ◆; maker lane blue ■, checker lane yellow ●; consultant magenta; errors red — lanes share glyph and color across stages), and promotes the live-activity line to a `[read|edit|search|run] <subject> <HH:MM>` form, bodies passing through untouched. Because worker turns are non-streaming and can run 30+ minutes, `send_prompt` keeps its pane alive on two cadences (`startHeartbeat`): every 5 minutes a `⏳` heartbeat (elapsed + transcript recency/retries; mirrored onto the orchestrator pane during a blocking headless turn) so a pane never looks hung, and every 30 seconds a `⋯` **live-activity line** naming the worker's current action (`⋯ reading src/foo.ts`, `⋯ running git diff`) so a healthy worker grinding for 30 minutes reads differently from a stalled one. The activity is read from the transcript tail located by *this turn's* session id, announced at/near turn start by both providers (`RunTurnOptions.onSessionId`) — the early id is what makes the trace universal, covering first turns and ephemeral consultant turns; extraction is a pure, tested parser (`src/voices/activity.ts` `latestActivity`) with a bounded read/search/run vocabulary — honest-but-low-fidelity liveness, never the raw command, emitted only when the action changed, fail-soft like every viewer concern. No changed-line count — neither provider hands one over for free. A *full* streaming sink (message text, tool inputs, diffs) remains the eventual fix; this is the lightweight slice of it.

The properties this buys: killing tmux doesn't kill agents; killing greenflag doesn't corrupt tmux; one code path produces lines and two dumb sinks consume them; and the log files are themselves inspectable-without-greenflag artifacts. The rejected alternative is the claude-squad architecture (agents live *inside* tmux sessions, state read back by screen-scraping) — vendored as the anti-model at `references/claude-squad/` (AGPL — read-only inspiration, no code reuse).

Separately from the viewer, every quiescent stop fires a best-effort macOS notification (`src/view/notify.ts`) — gate reached, question queued, or run complete — because the AFK phase's whole point is that the human is elsewhere when those land. Notification failure is silently swallowed; `greenflag status` carries the same information.

## The graph surface

The structural viewer over the compiled workflow — shipped 2026-07-07, view-only, render-on-demand (no server, watcher, or auto-refresh; the declined local-dashboard direction stays declined). One shared spine composer feeds every view, so blueprint and run views can't drift from the resolvers they read (`src/surfaces/graph-model.ts` + `graph.ts`):

- **`greenflag graph --workflow <name>`** — the **blueprint**: the compiled workflow before any run — stages, phases, gates with default postures, duty pairs with config-resolved default bindings (labeled as defaults; a real run re-resolves and freezes at creation), round caps, continuity edges (and any that would degrade under the resolved bindings), per-phase consultant checkpoints by kind. `--mermaid` emits a static flowchart (plain text, the docs/PR artifact); `--json` the model verbatim.
- **`greenflag graph [runId]`** — the **run view**: the frozen workflow with live position overlaid — done/current/future phases, each gate's posture and crossing authority (`auto-crossed` when ledgered in `autoApprovals`, else `crossed` — the view never claims "attended" for a past gate, since state doesn't attest explicit approvals), loop rounds used/cap, the current stop with its exact next command (read from `StatusModel.stop`, so the two never diverge), and **per-phase drift flags** from state-attributed signals only (an unowned snippet tag, rounds past cap, a phase-attributed auto-retry or steer). Context interventions render as a run/voice-level summary — `ContextEvent` carries no phase, and the run view reads no logs.
- **`greenflag stats [runId] --trace`** — the **interleaved execution timeline**: per phase, the actual turn sequence (duty, snippet tag, duration) with compactions, retries, and steers overlaid, and conservative ordering-drift detection. Lives in `stats` because that surface owns the log format.
- **`greenflag workflows check <name>`** renders the same blueprint spine (consultant checkpoints and bindings included).

The related **framings browser** (`greenflag framings`, `src/surfaces/framings.ts`) lists past runs' framings over the `run/repo.ts` identity stamp — the corpus-side entry to "what did I ask for last time".

## Supervising a run from outside

Supervising a run — by the human, the concierge, or the interactive orchestrator — is mostly answering one recurring question: **is this run healthy, waiting on my decision, or recoverably broken — and if it's waiting, what do I type?** The *position* half is the `status` model and its discriminated `stop`. The *health* half is a pure substrate (`src/voices/health.ts`): an error taxonomy (first-match-wins: login-required → quota-billing → auth → rate-limit → network → dns → server) and a per-voice probe that reads each voice's own transcript and returns a verdict. Three read-only surfaces share it — never three parsers: `greenflag doctor`, the `send_prompt` heartbeat, and the driver's crash classification. Two liveness sources feed the verdict — the duty workers via a persisted `activeTurns` hint reconciled against driver liveness, the orchestrator via driver + phase state — and every read is fail-soft.

Two triage outcomes are promoted from prose to fields, so a supervisor decides mechanically rather than re-reading paragraphs — both **signal-only**, neither touching gate-crossing:

- **`humanDecisions[]` on a gate packet** — the orchestrator's structured echo of the genuine human decisions it surfaced, each `severity: low | high`. Empty or all-`low` → safe to relay an approve; any `high` → hold and escalate. The statechart cannot see it; only the human's tap crosses a gate.
- **`cause` + `errorClass` on a queued question** — an `ask_human` flag is `cause: 'human'` (escalate); an infra-caught failure is `cause: 'infra'` plus the taxonomy `errorClass` (resume / retry territory). The `crashed` *position* (driver death, observed by `probeRunPosition`) is a separate, unchanged signal.

**The default-on auto-retry policy.** A new run's **headless** driver retries transient infrastructure failures within a bounded budget (`--retry-infra <n>` / `retry_infra:`, **default 3**): on a caught failure the driver classifies via the same taxonomy and, for a recoverable class (`network`, `server`, `rate-limit`), re-enters the phase through the existing session-resume path after a capped backoff rather than flagging. `auth` retries once, then a second consecutive `auth` escalates as `login-required`; `login-required`, `quota-billing`, `dns`, and `unknown` never retry; exhaustion always falls back to a flag (every stop still has a next command). The policy lives in exactly one place — the headless driver; the classification taxonomy reaches two — the driver and the stdio interactive host — but the interactive host only classifies, never auto-retries, because a human is present to resume. Every auto-retry is **recorded**, never silent: an `autoRetries` ledger surfaces in `greenflag status`'s "while you were away" section and as `auto-retried: …` in `--brief`, so a degrading environment shows up in the morning review instead of churning invisibly (the visibility is what makes default-on safe).

## Remote interaction: Claude Code is the concierge layer

Greenflag never builds its own remote, mobile, or notification infrastructure (the standing constraint in `docs/future-directions.md`); Claude Code is the remote layer. `skills/greenflag-concierge/` ships a skill that teaches any CC session to drive the greenflag CLI on the human's behalf — so CC's native remote control, mobile push, and `/loop` supervision become greenflag's reach-from-anywhere for free. The concierge is interaction glue with zero runtime: killable without consequence, and the run is exactly as operable from the terminal as without it.

The skill's substance is discipline, in priority order: **identity** — a relay, not a fourth engineer; it reports, translates, and executes intent, never opines on artifacts. **Verbatim relay** — the human's words cross unparaphrased into `--reject`, `--answer`, and `steer`; summarize toward the human freely, never editorialize from them. **Channel translation** — `status --json`'s `stop.kind` keys a mechanical table from intent to command. **Turn-ending stop reports** — when a gate, flag, crash, or completion lands, the concierge ends its turn with the report, which is what reliably fires CC's mobile push. **Double-gated gates** — the skill pre-approves read verbs only; the recommended permission `ask` rule on `greenflag continue` means crossing a gate takes the human twice — chat intent plus the permission prompt, on the phone too. The skill is invoked explicitly (`/greenflag-concierge`), never auto-triggered: a session that merely mentions runs and gates — a session developing greenflag itself is the standing example — must not inherit the relay identity. A coherence test (`tests/skill.test.ts`) pins every verb and flag the skill names to the real command table, and asserts both deliberate frontmatter properties.

`greenflag takeover` stays terminal-only by nature (it opens an interactive CLI); multi-run supervision is tracked in `docs/future-directions.md`.
