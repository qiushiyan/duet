# The consultant

The optional advisor voice: checkpoint kinds, the acceptance contract, and the verify chain. `docs/automation-design.md` (the spine) carries what a consultant is and how a `high` holds a gate; this doc carries the mechanism. Binding one is `docs/automation-design.md` §"Voices are decoupled from providers"; the value question stays open (`docs/open-questions.md` §"The consultant's value").

## Why it exists

The consultant answers the question the embedded checker is structurally blind to. A persistent checker accumulates the whole run's context — full's critic continues its analyst's planning session over a continuity edge — which is what makes it strong on *is this well-built* and invested in the framing it helped shape, so it rarely challenges the *bet*. The consultant supplies that missing altitude: a deliberately **low-context**, **ephemeral** (a fresh seeded session each time, so it never decays into a second embedded checker), **read-only**, **cross-family** voice — a different model family being the one thing a single checker working harder can never provide. It is **additive, never substitutive**: it never counts as a review round and never replaces the embedded checker. Its three asymmetries — ephemeral session, read-only, discard-and-reseed on an orphaned turn — live as data in one policy table (`src/voices/policy.ts`; `docs/engineering.md`), not as scattered conditionals. Implemented and test-verified (663 tests at its landing); first live exercise came on the composed `deep-relay` run — gateless, so the framing read and the contract/verify backstop ran while the bet audits stayed off **(observed: run `20260705-1731-58a5`)**.

## Checkpoints

When a consultant is bound, the workflow consults it at **gate-adjacent checkpoints**, encoded as registry data (`src/registry/workflows.ts`) so "where it fires" stays in the single source, never scattered through prompts. Each workflow maps the modes onto its own phases: every workflow opens with a **third independent analysis** at framing (`frame`/`research`); full adds a **bet audit** before the Commit-spec gate (`spec`) and short one before its Ship gate (`implement`); the document-bearing workflows (full, blueprint, relay) carry the acceptance-contract pair below. blueprint and relay have **no bet audit anywhere** — a stance, not a gap: those workflows exist for work where the owner trusts the direction after framing and wants only the correctness floor kept. At framing the consultant's read is a synthesis input to the direction, handed to the architect as one of *two anonymized peers* (the architect never learns which is the analyst; the embedded checker and the consultant stay blind to each other — information hiding holds both ways). At a bet-audit checkpoint the orchestrator folds the consultant's findings into its gate packet and echoes each finding's severity into `advance_phase`'s `human_decisions`, where a `high` can hold the crossing (spine §"Gate pre-authorization"). It runs through the existing worker `send_prompt` seam with a fresh seeded session each time, and never counts as a review round — so a review-loop phase still owes its embedded checker's round regardless.

**Three kinds, by walk-away compatibility.** Each checkpoint has a *kind* (registry data, `CHECKPOINT_KIND` in `src/registry/workflows.ts`) that decides whether a walk-away keeps it — and the cut is *holding* vs *non-holding*, not *questions-the-bet* vs not. The `generative` frame (`frame`/`research`) questions the bet but never *holds*: it has no severity echo into `human_decisions` (unlike a bet audit), so it can only enrich the direction, and a walk-away loses nothing by keeping it — a free perspective at the moment before any code. The `challenge` bet audit (`spec`, short's `implement`) holds via a `high`, and is the friction a walk-away opts out of. The `backstop` (the run-spanning `contract`+`verify` modes below) also holds, but it's the correctness floor a walk-away wants kept. The split is registry-derived, not scattered: one predicate — `consultantCheckpointLive(phase, {consultant, gateless})` — answers "does this checkpoint fire for this run?", read by **both** the orchestrator briefs and the `list_snippets` surface, so they can never disagree about what runs. A **gateless** run keys on exactly this: the owner has pre-decided the bet, so it drops only the holding `challenge` (`survivesGateless` = `kind !== 'challenge'`) — the `generative` frame still enriches the direction and the `backstop` still guards the build.

## The acceptance contract

On the document-bearing workflows (full, blueprint, relay) the backstop is a frozen, consultant-verified definition of success — two further checkpoint modes (`contract` at the workflow's contract-author phase — full's `plan`, blueprint's and relay's `spec` — and `verify` at `implement`, registry data like the others; short authors no contract). The consultant *authors* an **acceptance contract** — a short list of falsifiable, EARS-shaped behavioral assertions, each with a `Verify by:` probe. Its job is to catch runtime drift from the settled design that the builder's own tests would miss, not to re-judge "the right thing".

**Placement is derived from topology, and it trades one blindness deliberately.** A contract-author phase with a *committed document upstream* authors **early** — dispatched immediately after that document commits, before the phase drafts its own artifact, seeded with the upstream document only. Full's `plan` is the case: the contract is blind to the plan's tactics and to the code. A phase whose own artifact is the *only* document has nothing upstream to seed from and no phase between its gate and the build, so it authors **late** — the final step after its review loop converges, seeded with the near-final spec (the same runs-last pattern verify uses). Blueprint and relay are that case. What late authoring gives up is blindness to the technical approach; what it keeps is blindness to the code (nothing is built yet), the fresh independent session, and author-never-commits — and it gains a contract that is **human-ratified by default**, since that spec gate is the workflow's one attended stop (full's `overnight` freeze happens at an auto-crossed plan gate nobody read). The blindness full retains is narrower than it sounds: its spec already carries the module shape, the target shape, and the test standards, so an early-authored contract is blind to the *plan*, not to the technical approach.

Either way the consultant *writes* the file (a sibling of the spec-slot document, `<stem>.acceptance.md`) but **never commits** it — single-writer-by-construction holds (the discard-and-reseed orphan premise needs the consultant to touch no git history). A consultant turn at the contract checkpoint records a durable **draft marker** (`acceptanceContractDraft`, set in `settleTurn`) — the proof *this run* authored, which freeze and the rail below both require, so a stale contract file from a prior run is never silently ratified (a late-author phase records the marker before the document's path is even registered; the freeze verifies the file at the path it derives at crossing time). Crossing the **contract gate** *freezes* it: a harness step (`freezeContractAt`, keyed on the registry's contract-author phase) commits the file path-scoped — capturing any edits the human made while ratifying it at that gate, and recording `{path, commit}` on the run state — and this happens even on a pre-authorized (auto-crossed, unratified) gate.

At **implement**, the `verify` mode supplants the open-ended bet audit: a fresh session re-reads the frozen contract and verifies it by **running the built system and citing evidence per assertion** (execute-to-observe — run tests/CLI/curl, read logs; never edit, commit, or re-enter greenflag), returning a per-assertion pass/fail. It runs as the phase's **final step, after `reconcile-docs` and the CEO summary** (both code/doc-changing worker turns), so it certifies the exact state being shipped and no later turn leaves the verification stale. A **failed** assertion routes to the workflow's **fixer duty first** (`fixerDutyFor` — the builder everywhere but relay, whose writing judge owns fixes) — fix → a *fresh* consultant session re-verifies → a bounded loop — and is recorded as a `high` `human_decision` (riding the severity hold) **only if it still fails after that**, or if verification could not run at all. This **self-heal is universal** (attended and gateless alike): the human sees a summary of what self-healed, not every fix, and the still-stuck `high` is the load-bearing AFK protection that stops a run rather than shipping past a broken target. The conscious softening of "a failed assertion holds" degrades safely — worst case is still a hold, never a silent ship — because the re-verify is an *independent* session the fixer cannot game (an assertion it wrongly judges "wrong" and leaves unfixed simply re-fails and holds at the bound — and the inverse is live-observed: an assertion the fixer *rightly* judged mis-authored re-failed and held the gate for the human **(observed: run `20260705-1731-58a5`)**).

## The chain is enforced mechanically, not by prompt

(`advance_phase` rails, the same shape as the review-round rail): on a consultant run of a contract-bearing workflow, the contract-author phase will not advance without an authored contract (a draft marker) *or* a recorded `high`, and `implement` will not advance past a frozen-but-unverified contract without a `verifiedAt` stamp (set when a verify turn settles) *or* a `high`. The rail enforces that verify **ran and is fresh**: a code-changing (non-read-only) worker turn at `implement` — a self-heal fix, but also `reconcile-docs` or the CEO summary — *clears* `verifiedAt` (`settleTurn`), which is why verify runs last (after docs and the packet); a routed fix then structurally forces a fresh, independent re-verify before advance — the loop's "re-verify after the fix" is structure, not prompt-trust. What stays orchestrator-recorded is whether that final verify *passed*: a still-failing assertion is a `high` on the gate packet — the same trust model as triage everywhere — and the re-verify is always an independent consultant session (never the worker that fixed). The `high` escape-hatch itself holds the AFK crossing, so the run can never *silently* proceed past the chain — the worst case is a flagged stop, never a no-op. If authoring genuinely failed and the human proceeded on a `high`, the `implement` checkpoint is a *noted skip* (no frozen contract to verify).

The whole feature is **workflow-scoped**: short authors no contract, and a bound short run sees no contract/verify text at any tool surface (identity prompt, `list_snippets`). Read-only relaxation here is **prompt-level**, like the checkers': the author write and the execute-to-observe surface are scoped by the `consultant-contract` / `consultant-verify` snippets, not an OS sandbox (which the codebase deliberately omits — the integrity that *is* structural is the path-scoped freeze, which commits only the contract regardless of what else the author touched).

On **relay**, verify matters more than anywhere: under the fixer posture the maker-vs-checker adversariality collapses into sequential build-then-judge, and the judge grades work it then edits — so the contract verify (a fresh session, neither builder nor judge) is the one fully independent pass, and binding a consultant on relay buys more than on any other workflow.
