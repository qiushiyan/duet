# Automation design

This document describes the duet design as of the **2026-06-11 pivot**, in the vocabulary ratified by the **2026-07-04 domain remodel** (`CONTEXT.md`, the glossary that tiebreaks every naming question): an intelligent, read-only LLM **orchestrator** routes the snippet protocol between each stage's two duty **workers** — planning's architect and analyst, delivery's builder and critic or judge — inside a deterministic phase-and-gate skeleton enforced in code. It supersedes the dumb-router design of 2026-05-26. The reversal and its rationale are recorded in §"Design history" below; the decision ledger (`docs/open-questions.md`) tracks what the pivot settled and what it opened.

This is the **spine** — the mental model every session reads. The mechanism lives in four satellites, loaded when the work goes there: `docs/run-operations.md` (CLI, lifecycle, viewers, supervision), `docs/afk-resilience.md` (the resilience design + worker compaction), `docs/consultant.md` (checkpoints, the acceptance contract, the verify chain), `docs/voices-and-providers.md` (binding and worker-driving mechanics).

**Status** — what's built, test-verified, and live-verified — lives in two honest places, the README's verified-vs-not line and `docs/open-questions.md`, not here: this document describes the design as built, in present tense. The one piece designed but deliberately unbuilt is codex-as-orchestrator (`open-questions.md` §"Codex as the orchestrator").

## Design principles

These shape every other choice. Re-read before adding scope.

### Augment, don't replace

Duet drives the same `claude` and `codex` CLIs the user already uses, with the same snippet protocol, against the same codebase. Every artifact duet produces is also producible by the manual workflow — JSONL transcripts in the standard locations, branches with regular names, commits with regular messages. The pivot *extends* this principle rather than weakening it: the orchestrator is itself an LLM session with its own JSONL transcript, so every routing decision it makes is inspectable and auditable the same way the workers' turns are. There is no "duet mode" the user is locked into.

### Stop anytime

A run can be paused indefinitely. The state file at `.duet/runs/<run_id>/state.json` is a fast-access hint; the source of truth is the JSONL transcripts of **every voice's** session — the orchestrator's and each duty's. The user can stop at any gate, switch to manual `claude --resume <id>` / `codex exec resume <id>`, add turns by hand, and either resume duet later or never. On resume, the harness re-reads JSONL tails; the orchestrator re-derives position from the transcripts, not from cached offsets.

### Personal tool first, publish-ready

Built for one developer's use across their own projects. The CLI is project-agnostic: no project conventions hardcoded, no skill registry, no `.duetrc`, no codebase introspection. Project-specific knowledge — which skills exist, where specs go, branch conventions, model choices — flows in through the user's framing turn at `duet new`. (The optional snippet-override and seed-template files customize duet's *own* prompts, not convey project knowledge — reconciled in §"What the MVP should *not* do".) When the framing references something that doesn't exist, the orchestrator flags it to the human rather than inventing fallbacks.

Publishing (npm / public repo) is a kept-open option, not a goal (2026-06-12): the design constraints above don't soften for hypothetical users, but shipped artifacts — the `skills/` folder, the README — are written for any user and never reference the author's personal setup. No community roadmap.

One shipped artifact carries duet's *own* methodology this way: the PLAN-phase snippets — and short's `implement-direct`, which carries the same discipline into the workflow that has no plan — cite design and testing lessons, vendored into `lessons/` and resolved at serve time through a `{{lessons_dir}}` token (`src/orchestrator/library.ts`). This is not the skill registry the first paragraph rules out — no catalogue, discovery, or config, only the dependency closure of the worker-facing snippets: duet owns and ships its quality opinion. The line that keeps it honest is what a *worker reads at runtime*: that must ship (vendor it); a reference used only to *author* duet's prose stays out. Re-vendoring from the author's `~/.config/lessons` is a deliberate manual step (`pnpm vendor-lessons`), the mirror of the snippets ⟷ tabtype hand-sync.

### Not a daemon — but alive through a phase

*Amended from the 2026-05-26 "per-gate process" rule.* The process model is **per-phase, not per-gate**: each phase (which may take 1–3 hours during AFK implementation) is driven by a detached child process that exits at the next gate or queued exception, persisting state. The invoking `duet new` / `duet continue` returns immediately — it stages the human's input, spawns the driver (`_drive`, stdout to `.duet/runs/<id>/driver.log`, pid in `driver.pid`), and frees the terminal for follow-up duet commands; a pid guard refuses to start a second driver for a run whose phase is still running. With gate pre-authorization (§"Gate pre-authorization") the driver lives through the whole pre-authorized stretch — several phases, crossing each recorded gate on the human's standing authority — and exits at the next attended stop. Nothing runs when no phase is active; there is still no resident daemon, no GUI, no webhook listener. An intelligent orchestrator must hold its session open *across* the many routed turns inside a phase — but gates remain process exits, which is what keeps the semi-AFK shape (answer a gate from any terminal, hours later). An **interactively-orchestrated** run has no `_drive` during the planning stage at all — the human's interactive orchestrator session holds it open and `duet continue` crosses the gate inline; the detached driver starts only at the stage boundary (planning's last gate, derived rather than declared — `handoffGateOf`) into the AFK delivery stage.

## Design history — the 2026-06-11 pivot

The 2026-05-26 design stated, as an explicit non-goal: *"Use an LLM as the routing judge. The orchestrator is a state machine… not a third agent."* That decision is reversed. Three strands of evidence drove it:

1. **The old design was already approximating judgment with mechanism** — `needs_human`/`disagree` schema fields, `disagree.point` string-matching across rounds, fixed iteration caps, the resume token: each compensating for a router with no judgment. **(observed in this repo's own design docs)**
2. **The real workflow has variance a fixed state machine cannot absorb.** A 22-session corpus scan of the user's planlab project (`docs/observed-pattern.md` §"Corpus scan: planlab") found multi-PR pivots inside one session, a parallel worktree session, review polling started and stopped by hand, a recurring human-as-environment-proxy loop, and the user evolving the snippet library itself mid-session. **(observed)**
3. **The routing tax is heaviest exactly where judgment is needed.** The same scan: 41 `/copy` invocations, ~84 sub-60-char glue messages, keyboard touches every 7–15 minutes during spec/plan loops. **(observed)**

**The cost of the reversal, named:** routing becomes nondeterministic (mitigated: every sent prompt is logged with its source snippet tag and delta; gates are un-skippable in code); token cost rises materially (mitigated: budget caps, orchestrator self-compaction); debugging "why did it route that" is harder than reading a state machine (mitigated: the orchestrator's transcript *is* the explanation); and v1 is larger than the old Slice 1.

What did **not** change: the human gate list, the snippet protocol as the substance of the workflow, every augmentation principle, the worker plumbing (CLI resume, JSONL transcripts), and the personal-tool non-goals.

## The voices

A **voice** is any speaking party of a run — the umbrella noun for the mechanical surfaces (bindings, sessions, logs, panes, health). Three kinds, deliberately not equivalent:

| Voice | Writes? | Job |
|---|---|---|
| **Orchestrator** | **Never** — enforced by tool surface, not instruction | The machinery's voice — carries no duty, never a `send_prompt` target. Drives the protocol: picks the next snippet, adapts it, routes worker output, judges loop exits, triages questions, flags the human |
| **Workers** — each stage's two **duty** voices: planning's **architect** (maker) + **analyst** (checker); delivery's **builder** (maker) + **critic** or **judge** (checker, per the workflow's review posture) | Makers yes — the architect writes the documents, the builder the code. Checkers review only (a prompt-level convention, not a sandbox) — except relay's **judge**, whose fixer posture grants **action-scoped** write authority (`writeAuthorityFor`: the `review-and-fix` round and the tails it owns, never a midpoint read) | The commanded, artifact-producing voices: specs, plans, code, handoffs, summaries on the maker lane; critique at the right altitude on the checker lane (relay's judge also fixes findings in place) |
| **Consultant** *(optional)* | No (review only) | An optional advisor — a low-context, cross-family voice that questions the *bet* (assumptions, product fit), not the build. Off by default; bound per run. Checkpoint kinds, never a duty. |

**Duties are the protocol addresses and the runtime keys.** The vocabulary is closed and globally stage-unique — a duty alone names its stage — and it is what every mechanical surface speaks: `send_prompt(duty, …)`, `duet takeover <duty>`, the `<duty>.log` files, sessions keyed `"stage.duty"`, bindings per duty. The orchestrator carries no duty and is never addressable, yet stays a full operational voice — its log, session, status row, and takeover work like any voice's (the augmentation principle). The consultant is addressable but ephemeral: checkpoint-scoped, never a duty. Cross-stage statements use the **lane** words — every stage pairs a **maker** and a **checker** — while per-stage statements name the concrete duty.

The orchestrator is not a worker and not a tiebreaker: **it does triage, never substance**. It never answers a product, design, or technical question with its own opinion — it decides *who* should answer (the worker itself, per protocol, or the human, via a flag). The structure anticipated a fourth voice, and the **consultant** realizes a bounded form of it — *one optional advisor*, not arbitrary specialists; a third *maker* duty stays out of scope (`docs/future-directions.md`).

The **consultant** answers the question the embedded checker is structurally blind to: a persistent checker accumulates the whole run's context — full's critic continues its analyst's planning session over a continuity edge — which makes it strong on *is this well-built* and invested in the framing it helped shape, so it rarely challenges the *bet*. The consultant is the missing altitude: deliberately **low-context**, **ephemeral** (a fresh seeded session each time), **read-only**, **cross-family** — and **additive, never substitutive**: it never counts as a review round and never replaces the embedded checker. It fires at gate-adjacent checkpoints (§"Consultant checkpoints"), is bound per run, and a `high` finding it surfaces can **hold** a pre-authorized crossing (§"Gate pre-authorization"). The full rationale, kinds, and mechanism: `docs/consultant.md`; the value question stays open (`open-questions.md` §"The consultant's value").

### Voices are decoupled from providers

Settled 2026-06-11, restated by the remodel: **a duty is a capability contract; a provider is an implementation that can serve one or more of them.** No voice is hardcoded to a vendor — orchestrator-on-codex with the checkers on claude is a legal configuration, not a fork. Exactly two providers exist — **claude** (the model named per binding, because choosing the Anthropic model per voice is a knob the user actually turns) and **codex** (the model inherited from the user's `~/.codex/config.toml`, inline-pinnable per binding) — and the binding vocabulary is symmetric: any voice may pin a model, a normalized **effort**, and provider-native passthrough. The discipline: duet validates its *own* vocabulary (model default, effort enum) **fail-closed at the manifest freeze**, passes the *provider's* vocabulary through as a pure conduit, and runs a create-time **preflight** on explicitly-configured bindings — so a bad binding fails at `duet new` with the human present, never hours later mid-build. The knobs, the validation line, the capability contract per voice, and the config file: `docs/voices-and-providers.md` (the file's shape and shipped defaults: `README.md` §"Configure").

**Bindings resolve into the run manifest, once, and freeze.** The sources — `--bind` flags, the framing's `bind.*` keys, config, shipped defaults — resolve **per key** at `createRun` (flags > framing > config > defaults), freeze on the run state, and `duet new` **echoes the result** — workflow, each stage's duty bindings, consultant, degraded continuity edges, gate posture — so a run can never freeze bindings nobody saw **(observed: run `20260703-1444-717d`, created with silently-frozen defaults and abandoned)**. The shipped default posture: the maker lanes and both run-long voices on claude/Opus 4.8, the checker lanes on codex — the cross-family review out of the box.

What connects the two stages is not a binding band but a **continuity edge** — registry data on each workflow declaring that a delivery duty *continues* a planning duty's session, with the seed ritual that carries it. full, blueprint, and short declare both lanes: `builder ← architect` carries the planning session across via the build's entry seed (full's boundary compact; blueprint's compact plus its doc re-anchor; short's direct entry from the decisions), and `critic ← analyst` continues directly — the checker persists across the whole run, kept deliberately. relay declares **no edges**: its whole delivery stage is born fresh, whatever the bindings. A duty with no inbound edge simply starts fresh — nothing resets, because nothing was shared. Because a session can never resume across providers, an edge whose two duties' *frozen bindings* cross providers **degrades to fresh at manifest freeze** — never an error (binding `builder=codex` on full is a legitimate plan-on-claude / build-on-codex run), never silent (echoed by `duet new`, recorded on the run state), and the ritual adapts: a degraded edge seeds from the committed document instead of compacting a session the duty doesn't have. `voiceBindingFor` is the **one** "who runs this turn" resolver — a frozen-manifest lookup by address, no band logic — read alike by worker construction, session identity, the context-pressure scope, stats, and takeover (`docs/voices-and-providers.md`).

## Architecture: three layers

### Layer 1 — Harness (deterministic code)

A statechart: each **phase** is a state that runs the orchestrator agent; each **gate** is a state in which no agent runs and which transitions only on human events. The two event vocabularies are kept disjoint: a phase completes by emitting an internal `phase.advance`/`phase.flag`, while a gate transitions only on a `human.*` authority event. A gate has no `phase.*` handler, so `advance_phase` can park a run at a gate but can never cross it — gate-skipping is unrepresentable, not merely forbidden. No tool emits `human.*` — whether the orchestrator runs in-process or in a separate process over the tool boundary — so that guarantee holds across the process boundary too. (Implemented in XState v5 at `src/run/machine.ts`; the states are built from the run's **compiled workflow** — frozen at creation, the shipped standard library at `src/registry/workflows.ts` — the single source for its stages, duties, continuity edges, phase order, caps, budgets, and gate copy. How the code uses XState: `docs/engineering.md` §"XState usage".)

The harness also owns:

- **Worker subprocess plumbing** — spawn/resume worker sessions, completion detection, output capture, graceful kill (SIGTERM→SIGKILL escalation). Prior art is vendored at `references/sandcastle/` (MIT); see `references/README.md` for the per-repo borrowing guide.
- **Read-only enforcement** — the orchestrator's tool surface contains no write/edit/bash tools. Its read-only nature is a property of the harness, not a promise in a prompt.
- **Gate interception** — `ask_human` and `advance_phase` are harness-owned tool handlers: the handler persists the question/phase-exit at the moment of the call (the human-visible artifact exists before the model regains control), then instructs the orchestrator to end its turn; the harness exits when the turn ends. The interception is the handler side effect, not the permission system — the SDK's mechanical pauses corrupt resume (repros: `src/spike/repro-*.ts`).
- **State persistence** — the machine snapshot is written **only at quiescent states** (gates, flag-waits, done — states with no live actors). Mid-phase crash recovery comes from the JSONL transcripts, which is where it always came from.

### Layer 2 — Orchestrator (LLM agent)

A read-only agent whose system prompt is the workflow protocol operationalized — phases, snippet usage rules, altitude lenses, compaction discipline, triage rules — plus the per-run framing the user supplies. The voice is provider-decoupled; when bound to the **claude provider** — the default, and the only orchestrator-capable provider in v1 — the substrate is the Claude Agent SDK (read-only via tool configuration; session JSONL on disk in the standard location, so the orchestrator's session stays manually resumable with `claude --resume`), **with one correction** from the substrate spike: the AFK pause at `ask_human` is *cooperative*, not mechanical — the tool handler queues the question, persists state, and instructs the orchestrator to end its turn; the SDK's mechanical pause options both corrupt session resume (repros at `src/spike/repro-*.ts`).

The tool surface is **host-neutral**: the base tools live in one registry independent of any SDK, hosted by thin adapters — the in-process Agent SDK server (the default), a standard stdio MCP server, and the run-scoped server the interactive orchestrator connects to (`docs/engineering.md`, the "Host-neutral kernel" and "Interactive orchestrator host" patterns). On that footing the **interactive CC session is itself an orchestrator host** over the planning stage (`duet orchestrate` / `duet new --interactive` — and since 2026-07-11 the default `duet new` posture on a live terminal): the human's own session drives the planning phases up to the stage boundary, steering and gate conversation happen in chat, and the run hands off to the headless driver there. That session is opened fresh by default or **warm-started** from the session the framing grew out of (`--resume-session <id>`), and its id is persisted, so a dropped session reconnects to the *same* one (`duet orchestrate`) rather than restarting cold. On this host `send_prompt` is **fire-and-collect** — it dispatches the worker turn into the background and returns at once, and a ninth tool, `check_turns`, delivers the result when it lands — so the session never freezes for the minutes a turn runs; the headless driver keeps its blocking `send_prompt` and has no `check_turns`, a host switch in the one registry, not a fork. A single-writer lease on the run-scoped server stops a superseded session from writing over the live one, and a turn orphaned by a session quit is detected on disk and recovered with `duet takeover`. (Live-verified — the interactive host is the author's daily driver for planning stages **(observed: daily use, 2026-07)**.) Gates are still structural — `advance_phase` only parks — and the one safety setup is a single `ask` permission rule on `duet continue`, since no tool can emit `human.*` regardless of host.

**Tool surface** (definitions and the rails they enforce: `src/orchestrator/tools.ts`):

| Tool | What it does |
|---|---|
| `get_task()` | Read the current phase's entry brief — documents in scope, branch policy, attendance, worked examples — returned in full every call. The interactive host's way in: read at phase start, after a gate, or to re-anchor after compaction; it folds a staged human input (approval rider / reject feedback / answer) in once. Not read-only — marks the phase started on first call; reports the park (no side effects) once the phase is at its gate/flag. |
| `list_snippets(all?)` | Read the **effective** snippet library (the shipped defaults with any user/project overrides merged in — §"What the MVP should *not* do"), **phase-focused by default**: this phase's templates and the anytime helpers in full, other phases indexed by key, annotated with what's already been sent this phase. `all: true` returns every body — the cross-phase escape hatch. |
| `send_prompt(duty, tag, body)` | Send a prompt to a worker — one `duty` (the enum is the phase's live duties plus `consultant`), or a **duty array** to fan one identical body to several at once. `tag` names the source snippet (`"custom"` when composed from scratch); `body` is the final text, logged with the tag so adaptation drift is auditable. The array is the framing analysis pass — one address-neutral read to `["architect","analyst"]`, each analyzing independently and in parallel; independent single-duty turns to different duties also overlap, and a second turn to a duty in flight is refused (one session is one conversation). **Host-divergent completion:** headless blocks and returns the worker's response; the interactive host dispatches into the background and returns at once, collected later with `check_turns`. |
| `check_turns()` | **Interactive host only.** Collect the results of turns dispatched by `send_prompt` — the worker's text (or a failed turn's prescribed recovery), with the same bookkeeping a blocking turn would have done, plus any pending steers. Instant: it delivers whatever has settled, names any duty still running, and reopens a collected duty; a phase cannot advance while a dispatched turn is uncollected. (`duet status --wait` wakes the moment a turn settles.) |
| `ask_human(question, context?)` | Flag something for the human. Always the cooperative pause: the handler persists the question, the run exits at quiescence, and the human answers via `duet continue --answer` — in attended phases they're at the terminal and answer in minutes; during AFK the question waits. |
| `advance_phase(summary, artifacts, spec_path?)` | Declare the phase complete. Legal only when the phase's exit criteria are plausible; lands on the phase's human gate (every workflow gates every phase, so an advance always parks at one). `spec_path` reports where the spec file landed when the phase produced it. |
| `create_branch(name)` | Create and switch to the run's working branch (§"Branch policy"). Harness-executed; structurally legal only before the first worker prompt. |
| `propose_snippet_edit(snippet_key, proposed_body, rationale)` | Queue a persistent snippet-library change for the human's end-of-run review. Never applied mid-run. |
| `write_note(observation)` | Append a friction observation to `.duet/runs/<run_id>/notes.md` — the dogfooding journal, written by both the human and the orchestrator. Allowed even while parked at a gate or flag: a pure append has no statechart effect, so an observation gets recorded the moment it crystallizes. |

#### Prompting and tool-surface conventions

Every prompt, tool definition, and tool result follows **`docs/prompting-and-tool-design.md`** — duet's house patterns and observed evidence over the general rulebook (adopted 2026-06-11 from Anthropic's published guidance, first applied in the substrate spike). Consult it whenever writing or revising model-facing text; it carries the binding rules — artifacts-first prompt shape, thinking-framework-over-prohibition, the single-world rule, the familiar-term test — with their evidence.

### Layer 3 — Workers

Resumed CLI sessions, transcripts in the standard locations, invoked per turn by the harness on the orchestrator's instruction — unchanged in shape from the 2026-05-26 design. Workers run with **full permissions** (claude headless via `--permission-mode bypassPermissions`; codex deferring entirely to the user's `~/.codex/config.toml`, no `--sandbox` flag) — duet's coding agents are no more restricted than the user's own manual workflow, and a checker's review-only behavior is a **prompt-level convention**, not a sandbox (the OS-sandbox reversal and its evidence: `docs/voices-and-providers.md`). Per-provider driving mechanics, the resume verbs, the gotchas, and the opt-in interactive transport live there too (+ `docs/interactive-transport.md`).

### Worker compaction

Two maker-lane `/compact` moves, each at a boundary: **plan→build** (`compact-for-impl`, the seed ritual of the `builder ← architect` continuity edge — the `implement` phase's first act after the plan commits) and **build→review** (`compact-for-review`, orchestrator-timed by the context gauge). Either way **the plan must be a repo file**: compaction drops the journey, so the committed plan + spec are the re-anchor. Timing is instrumented, not felt — compaction is due from 75% fill, structural past 85%. Per-provider mechanics and the full context-pressure design: `docs/afk-resilience.md`.

## Question triage

The orchestrator's flagging rules, stated as instructions it must follow. Questions from workers come in three kinds:

1. **Product / direction questions** ("should this be billing-gated?", "is breaking compatibility acceptable?") — **always flag** via `ask_human`. No exceptions.
2. **Environment questions** ("do you need me to run the migration?", anything touching DB/Slack/deploy credentials) — **always flag**; only the human can act. **(observed: planlab b7487993 12:10:23Z, e9607005 10:34:53Z)**
3. **Tactical questions the worker can answer itself** ("do I need a migration step for this schema change?") — the orchestrator answers with **process, not substance**: "decide per the plan and record the decision; if it's actually a product call, say so and I'll flag it."

The orchestrator never supplies a technical opinion of its own — answering would make it an invisible third opinion-holder whose influence bypasses the human gates. Triage decides *whether* a question reaches the human; *what they read when it does* is the presentation discipline — every surfaced decision decidable from its text alone, the substance relayed from the workers rather than invented (`docs/prompting-and-tool-design.md` §"Presenting to the human"). Whether these rules over-flag or under-flag in practice is an open calibration question (open-questions.md §"Triage precision"). The triage outcomes are also surfaced as structured signals for a supervisor reading from outside — a gate packet's `humanDecisions[]` and a queued question's `cause` — so the concierge or interactive orchestrator decides hold-vs-relay mechanically (`docs/run-operations.md` §"Supervising a run from outside").

## Phases and gates

duet is **workflow-aware**: a run picks one workflow at start (`--workflow`, default `full`; a `workflow:` framing key by another door) and carries its compiled spec from creation on (§"The workflow vocabulary" — the freeze), so every workflow-shaped fact resolves through one source per run. Four workflows ship, and a project can compose more from the same vocabulary. Three of the shipped set form a ladder by how much ceremony the work warrants — **full** (spec and plan each get their own loop and gate), **blueprint** (full minus the plan phase — the spec is the whole design), **short** (no document at all — the research decisions are the design) — and the fourth, **relay**, redistributes the *duties* rather than the ceremony: blueprint's shape with a criss-crossed build, where a cheap builder executes and a strong judge fixes findings directly and owns the finishing tails.

### The workflow vocabulary

The workflows are not four hand-built machines. Each is an **expression in a small composition vocabulary** — the hierarchy **workflow → stage → phase → duty** — and the shipped set is an opinionated standard library over it. A workflow is an ordered list of **stages**; every workflow has two, **planning** and **delivery**, partitioning its phase list. Planning is the attended thinking stretch — a workflow with no document still has one (short's research alone is its planning); delivery is the AFK stretch; and the **stage boundary** between them is where continuity edges apply and where an interactive run hands off to the headless driver (its gate is *derived* as planning's last phase — `handoffGateOf`, one source, no stored field). A stage is one holistic thinking flow carried by two **duty** voices, a maker and a checker; which checker duty a workflow uses is its review-posture knob (relay uses `judge`). The duty vocabulary is closed and globally stage-unique, growing only with a shipping workflow. Inside a stage, each **phase** is an instance of a **block** with knobs. The split that keeps composition safe:

**Grammar — fixed rules of the language, never composable.** Every phase exits through a human gate and only `human.*` crosses it; cooperative pause, the terminal-marker discipline, state-file-is-a-hint; one branch per run; framing as the single project-knowledge seam; the orchestrator does triage, never substance, read-only by tool surface; prompts are duet-authored (the per-key snippet overrides stay the one sanctioned customization channel — composition selects and arranges blocks, it never authors prose). `machineFor` builds any phase list into the same loop/flag/gate idiom, so the grammar is composition-independent by construction — a composed workflow cannot compose its way past a gate.

**Vocabulary — the composable inventory, closed by rule.** Four blocks — **frame** (parallel analysis → synthesis), **doc-loop** (draft/review rounds on one artifact), **build** (the AFK implementation), **finish** (the PR open) — each with the knobs the shipped workflows actually need and no more: the doc-loop's artifact kind, round cap, and consultant checkpoint; the build's entry seed, review posture (critique | writable | fixer), midpoint, verify checkpoint, ship packet, and build-tail owner; the finish owner. **A workflow's documents are ordered** — the first is always the spec, any later one a plan — checked at load, so a plan that would reread a spec nobody wrote is unrepresentable. Everything else a doc-loop needs, the compiler *derives from position* rather than from the artifact's name. Stages carry the rest of the registry data: each stage's duty pair and the workflow's **continuity edges**. A knob value exists only when duet ships hand-written prompt support for it *and* a shipped workflow exercises it — enforced at load, not by convention: `validateRegistry` rejects a combination whose snippet family or brief fragments don't exist (and checks the topology), and each block's snippet lists are *derived* from the knob values rather than hand-listed per phase (`docs/engineering.md` §"Patterns that carry the design"). Speculative knobs — parameterizing anything that doesn't vary across the shipped workflows — are refused on sight.

Two consequences bind everything downstream. **Every rendered prompt describes exactly one world**: a worker or orchestrator never reads knob-conditional prose — the compiled semantics decide and the renderer selects dedicated fragments per value (the single-world rule, binding in `docs/prompting-and-tool-design.md`). And **a new workflow is an expression, not code**: relay landed as one composition plus its snippets — no statechart change, no contract-machinery change.

**The authoring surface is a TypeScript SDK, and the standard library dogfoods it.** A workflow definition is `defineWorkflow({ name, title, phases, attend?, presets? })` over four block constructors — `frame`, `doc`, `build`, `finish`, imported from `duet/workflows` — and the shipped four are themselves these expressions (`src/registry/workflows.ts`), so a user composes in exactly the grammar the standard library is written in (each shipped workflow's SDK rebuild compiles byte-identical to its registry row, pinned by test). The author states only the phase list and the gate posture; the compiler (`src/registry/define.ts`) derives everything else from the phase semantics and validates the result against the closed vocabulary, so a composition outside shipped prompt support is rejected at load with the valid worlds named, never briefed vaguely at run time.

**Definitions resolve from two authoring layers and freeze per run.** `duet new --workflow <name>` resolves the name across shipped / project (`.duet/workflows/<name>.ts`) / user (`~/.config/duet/workflows/<name>.ts`) — a name defined in more than one layer is a collision error, never a silent shadow — compiles it once, and `createRun` freezes the compiled workflow to `.duet/runs/<id>/workflow.json`; every later process reads that artifact (`workflowFor(state)`), so a live run cannot be corrupted by editing any workflow source. Structure and membership freeze; prose stays live by key (snippets and brief worlds), so a snippet-library improvement still reaches a mid-flight run. The pre-run `duet workflows` inspector lists, compiles-and-checks, and scaffolds definitions without starting a run (`docs/run-operations.md`); worked definitions ship with the duet-frame skill (`skills/duet-frame/references/workflow-definitions.md`). The path is live-verified end to end: a project-composed workflow ran gateless to an open PR **(observed: run `20260705-1731-58a5`)**.

The **full** workflow — the thorough path: a three-phase planning stage, a two-phase delivery:

```
PLANNING (the attended stage — architect + analyst)
  onboard → frame (both, parallel) → synthesize
    ── GATE: Direction ──
  spec draft → review/update rounds
    ── GATE: Commit spec ──
  plan draft → review/update rounds   (planning keeps full spec-exploration context)
    ── GATE: Plan approval ──            ← the stage boundary: interactive→headless handoff; under the default `overnight` posture the human has already walked away (after the spec)
DELIVERY (AFK — builder + critic; both continue the planning sessions over the continuity edges)
  implement: commit plan → compact-for-impl + reread → single implementation pass (one midpoint checkpoint only if large)
  → compact-for-review (judgment) → implementation-handoff
  → review/respond rounds → fixes → re-review
  → reconcile-docs (update + commit — the last build step, so Ship reviews code + docs)
  → ceo-summary (builder drafts) → [consultant verify, last]
    ── GATE: Ship ──                     ← auto-crosses by default (overnight); env verification shifts to PR-review time. Attended (skip-plan) → human returns, verifies, approves
  finish: pr-description → open the PR   (docs already on the branch; finish is PR-only)
    ── GATE: Open PR ──                  ← AFTER the open. Auto-crosses to done by default; gates_at: finish adds a post-open review stop
```

| Gate | Boundary | What the human decides |
|---|---|---|
| **Opening framing** | start of run | Provides issue text, product context, scope. The input, not a pause. |
| **Direction** | inside PLANNING | "Does this direction match what I meant?" |
| **Commit spec** | inside PLANNING | "Spec is solid; commit and move on." |
| **Plan approval** | planning → delivery (the stage boundary) | "Plan is workable." The interactive→headless handoff — though under the default `overnight` the human already walked away after the spec. |
| **Ship** | inside DELIVERY (implement → finish) | Reads the final-gate packet (below); runs environment verification (migrations, smoke tests — the human as environment proxy acts *here*); "ship" / "another round" / specific changes. |
| **Open PR** | end of `finish` (end of run) | **The PR is already open** when this gate is reached: `finish` writes the description and runs `gh pr create` *before* advancing, so the gate reviews an opened PR (open-then-review). The open is idempotent — a pre-existing PR on the branch is amended, never re-created. Auto-crosses to done by default (opening is non-destructive; the human owns the merge); the run ends with the PR URL leading its summary, and the PR body leads with a `Verification (pending)` checklist — the standing pre-merge reminder when the Ship gate auto-crossed unverified. List `finish` in `gates_at` for a post-open review stop: approve (done), or reject with feedback, which re-enters `finish` to *amend* (`gh pr edit` / more commits), never to re-open. The merge is the human's either way; it is never automated. |

Plus **in-phase exception gates** whenever the orchestrator calls `ask_human`. The machinery is identical in every phase — the question is persisted, the process exits at quiescence, `duet continue --answer` resumes. What differs is the human: attended means they're at the terminal and the pause lasts minutes; AFK means the question waits hours until they return (with a desktop notification fired either way).

The **blueprint** workflow — **full minus the plan phase**, for serious work on a trusted frontier-model builder, where a separate plan would overlap the spec heavily and two review loops buy little over one:

```
frame (attended machinery, auto-crossed by default)
  onboard → think-holistic (both, parallel) → compare-notes synthesis
    ── GATE: Direction ──                  ← auto-crosses under the default posture (severity hold intact)
spec
  spec draft → one review loop (section-scoped altitude) → [consultant authors the contract, last]
    ── GATE: Commit-spec ──                ← the workflow's one attended stop by default; ratification + the stage boundary; contract freeze
implement (AFK)  — full's implement, reused: build (implement-spec seeds it) → review loop → reconcile-docs → ceo-summary → [verify, last]
    ── GATE: Ship ──                       ← auto-crosses by default
finish — full's finish, byte-for-byte:  pr-description → open the PR
    ── GATE: Open-PR ──                    ← after the open; auto-crosses to done
```

Nothing about the spec changes because the plan is gone: every workflow's spec is the same half-technical document with the same internal altitude gradient — product sections on top, technical sections below; full code bodies, test-case lists, fixtures, and commit order are deferred. What changes is who inherits the deferred detail: full hands it to the plan, blueprint hands it to the build. The document's structure is the review lens's structure — `review-spec` holds each section to its own tier, so a loop can't re-grow the plan-depth rounds this workflow deletes; its cap is an explicit `rounds: 2`, the fast-convergence premise made a rail. Because the spec is every workflow's first document, `--spec` enters here with a draft spec and the contract path derives unchanged. The build seeds from `implement-spec` — the committed spec is the authority for *what and why*, the snippet carries the *how* — not short's `implement-direct`, whose body assumes no document exists. The default posture is the workflow's product promise: **one interruption** — the human reads one document, taps once at the Commit-spec gate, and walks away (§"Gate pre-authorization").

The **relay** workflow — blueprint's shape with the build criss-crossed, for the plan-smart / build-cheap / judge-strong economy: expensive judgment at the ends, fast labor in the middle, and a judge that *acts* on its findings rather than filing critiques back:

```
frame → ── GATE: Direction ── → spec → ── GATE: Commit-spec ──   (identical to blueprint,
                                          ↑ the one attended stop; the stage boundary; contract freeze)
implement (AFK)  — the whole delivery stage is born fresh: relay declares NO continuity edges
  builder starts FRESH from the committed spec (implement-spec seeds a new session)
  → implementation-handoff (the builder authors the map)
  → ONE review-and-fix round: the judge critiques AND fixes in place
  → judge: reconcile-docs → ceo-summary → [consultant verify, last]
    ── GATE: Ship ──                       ← auto-crosses by default
finish (AFK) — the JUDGE opens the PR:  pr-description → gh pr create
    ── GATE: Open-PR ──                    ← after the open; auto-crosses to done
```

What distinguishes it, piece by piece:

- **The criss-cross is four bindings and zero edges.** The economics come from per-duty bindings: planning runs architect=claude vs analyst=codex; delivery binds `--bind builder=codex --bind judge=claude[:model]` — fast labor, strong judgment. The freshness is registry data, not a binding side effect: relay declares **no continuity edges**, so both delivery duties seed fresh from the committed spec whatever the providers — and the accepted cost is that the judge never saw the planning loop; the document is its authority.
- **The fixer's discipline** is one dedicated snippet, `review-and-fix`: the full review lens plus the assess-validity / fix-in-place / push-back-with-reasons discipline, with an **escalation valve** — ordinary valid findings are fixed directly, but a product or design disagreement, unclear intent, or broad directional drift escalates via the orchestrator (`ask_human`), because a direct fix must never hide a pivot. Self-fix is the default, not an absolute. `implementation-handoff` stays with the builder — whoever wrote the code authors the map.
- **Write authority is action-scoped, never a phase blanket** (`writeAuthorityFor`): `review-and-fix` and the tail actions may write; a `review-midpoint` turn under the fixer posture stays guidance-only — mid-build the builder is the sole writer.
- **One writable round** (cap 1, short's discipline): the review-and-fix round is the loop. A follow-up fix request into the same judge session — a failed verify assertion routed back — steers by delta and needs no new round.
- **Verify matters more here.** Under the fixer posture the maker-vs-checker adversariality collapses into sequential build-then-judge, so the consultant's contract verify is the one fully independent pass — binding a consultant on relay buys more than on any other workflow (`docs/consultant.md`).

The **short** workflow — the lighter path, for small, well-understood work where the spec-and-plan ceremony costs more than it returns:

```
research (attended)
  onboard → think-holistic (both, parallel) → compare-notes synthesis
    ── GATE: Direction ──                  ← the research decisions ARE the design; the stage boundary — human walks away / hands off here
implement (AFK)
  build directly from the decisions → implementation-handoff
  → ONE writable review round (review-direct → apply-review, fixes applied in place)
  → reconcile-docs (update + commit — the last build step, so Ship reviews code + docs)
    ── GATE: Ship ──                       ← auto-crosses by default
finish (AFK)
  pr-description → gh pr create            (docs already on the branch; finish is PR-only)
    ── GATE: Open-PR ──                    ← AFTER the open; auto-crosses to done by default, run ends at the open PR
```

It drops spec and plan, not the PR: the synthesized research decisions stand in for the spec, so the builder builds from them directly — and because there is no plan phase to carry it, `implement-direct` itself carries the plan's engineering discipline (vertical slices, deep modules, what-to-test, the same vendored methodology), so the lighter workflow is not a lower bar. Its planning stage is `research` alone — no document, but still a stage, with both continuity edges declared like full's. Its review loop is a single **writable** round (the critic critiques once, the builder fixes in place). The walk-away-after-research flow that returns to a finished run with the PR open *is* the default (attend Direction only, 2026-07-11); `gates_at: research,implement` brings the Ship gate back for a run the human wants to verify before it ships.

The workflows share their machinery: the same gate/flag/steer idiom, the same statechart skeleton built per workflow (`machineFor`), the same registry-derived per-phase facts, and the shared `implement`/`finish` phase names (workflow-scoped identity). Docs reconcile at the tail of `implement` in every workflow — the last build step, reviewed at the Ship gate — and ride the branch, so `finish` opens the PR and touches no docs. The review-loop phases (`spec`, `plan`, each workflow's `implement`) must run at least one review round before `advance_phase`; the others (`frame`, `research`, `finish`) may advance without one — their substance is synthesis or mechanics. Backstop caps stay tight, near the round counts real runs need: spec 3 (blueprint and relay pin an explicit 2 — the fast-convergence premise), plan 3, full/blueprint `implement` 3, frame/research/finish 2, short's and relay's `implement` 1 — the single writable round *is* the loop (the registry, `src/registry/workflows.ts`, is the source).

Inside a phase the orchestrator drives; the human's channels in are the gates, the `ask_human` flags, and — into a live phase — the steer channel below.

### Consultant checkpoints

When a consultant is bound, the workflow consults it at **gate-adjacent checkpoints** — registry data (`src/registry/workflows.ts`), never scattered through prompts. Three kinds, cut by walk-away compatibility (holding vs non-holding): the `generative` framing read enriches the direction as one of two anonymized peers and never holds; the `challenge` bet audit (full's spec, short's implement — blueprint and relay have none, a stance not a gap) can hold a pre-authorized gate via a `high`; and the `backstop` pair — the consultant-authored **acceptance contract**, frozen at its gate, then **verified against the running system** as `implement`'s final step, self-healing failures through the workflow's fixer duty and holding the gate only when still failing — is the correctness floor a walk-away wants kept. A gateless run drops only the `challenge` (`survivesGateless`). One predicate — `consultantCheckpointLive` — answers "does this checkpoint fire for this run?" for briefs and `list_snippets` alike, so they can never disagree. The mechanism — placement topology, draft markers, the path-scoped freeze, `verifiedAt` and the mechanically-enforced author/verify chain — is `docs/consultant.md`.

### The steer channel

The human's voice has a channel for every run condition: gates take decisions (an approval may carry a rider — agreement plus adjustments, gate feedback in approving form), flags take answers, and a **live phase takes steers** — `duet steer "<note>"`, the editor-in-chief's voice mid-flight. A steer is processed, not answered: it reaches the orchestrator appended to its next *phase-continuing* tool result (tool results arrive every few minutes all phase long and are already the harness's steering surface), tagged as human guidance that outranks a checker's opinions and counts toward no cap; the orchestrator folds it into its routing, and a steer is never by itself a reason to `ask_human` — the human chose the non-pausing channel deliberately. Two boundaries keep the channel honest: results that end the orchestrator's turn never carry steers (guidance delivered into a dying turn lands and dies — those wait and ride the next harness prompt, staleness judged by the orchestrator, carried never dropped), and at a quiescent stop the CLI refuses the steer outright, naming that stop's own channel. Storage is file-per-steer, consumed by rename, deliver-then-consume — a crash redelivers a steer rather than losing one (`docs/engineering.md` §"Steer channel"); staging and delivery land in the voice logs and `duet status` lists what's pending, so the channel is auditable end to end.

### Gate pre-authorization (`gates_at`)

Added 2026-06-12, after the first real run. A gate bundles three functions — the human's **authority**, **steering** (early-correction leverage), and a **quiescent stop** — and pre-authorization gives up only the steering: the authority is granted in advance, the stop still happens and is recorded.

A run pre-authorizes a subset of its gates at `duet new`: `--gates-at <list|preset>` or a `gates_at:` frontmatter key (the flag wins) names the phases whose gates the human will attend — the rest auto-cross. The gate set, the presets, the **default posture**, and the force-attended gates are all **workflow-scoped** registry data. full's presets, named for the human's posture: `overnight` (= `frame,spec`), `skip-plan` (= `frame,spec,implement`), and `afk` (= attend nothing), completing the launch ladder `overnight → skip-plan → afk → gateless`. **`overnight` is full's default** (2026-06-26): plan, Ship, and Open-PR auto-cross unless listed — the sleep posture out of the box, the env-verification forcing function relocated into the opened PR's `Verification (pending)` checklist (an advisory pre-merge reminder; the merge is the human's manual act regardless). blueprint and relay default to **attend the spec gate only** (a new run materializes `gatesAt: [spec]`) — the one-interruption promise those workflows exist for, with the severity hold below still converting a contentious direction into an attended stop; each one's `afk` preset attends nothing. short defaults to **attend the Direction gate only** (`gatesAt: [research]`, flipped 2026-07-11 from attend-all — every live short run had re-set the posture by hand). At an auto-crossed gate the harness persists the gate packet, fires the notification, sends `human.approve` on the standing authority, and records the crossing (`autoApprovals`); `duet status` lists the crossings in a "while you were away" section for the morning review. Force-attended gates can never be pre-authorized — but currently *no* workflow force-attends anything: opening a PR is non-destructive, so every workflow's Open-PR gate is pre-authorized by default, attended only when `finish` is listed. The statechart is untouched — gates still transition only on `human.*` events; pre-authorization changes *when* the approval is uttered, never *who* may utter it.

**The severity hold.** A gate packet may carry `human_decisions` — a structured echo of genuine product calls the orchestrator deliberately did *not* make (each a title + severity). A `high` decision **withholds a non-explicit crossing**: a pre-authorized gate will not auto-cross over it, and a one-tap `duet afk` handoff is refused — both convert to an attended stop so the human weighs the call before it ships. An **explicit** human approval always crosses; blocking the human's own tap would fight the gate model. This is the channel through which a bound consultant's bet audit can stop an overnight run — a `high` finding rides the packet and holds the gate — but the mechanism is general: any `high` entry holds, consultant-sourced or not. The one deliberate exception is **`duet afk --gateless`** (the explicit walk-away-from-here full-send): it crosses the bet/product `high`s the owner has pre-decided, as an explicit approval would — but still preserves the correctness backstop, refusing to hand off at the contract gate when no contract was authored, so a *missing* backstop is never crossed unattended.

Two facts about the posture itself bite if forgotten. **`gates_at` is the complete attend set, not a delta**: it names every gate the human attends and the rest auto-cross — `--gates-at finish` attends *only* the Open-PR gate; to keep the usual stops *and* add one, list the whole set. And a new run **materializes** its posture at creation: a default full run persists an explicit `gatesAt = frame,spec`, a default blueprint/relay run `gatesAt = spec`, a default short run `gatesAt = research`, and the gate-posture line rides the `duet new` manifest echo — while a workflow with nothing pre-authorized by default leaves `gatesAt` absent, byte-for-byte the pre-feature attend-all. An **empty** `gatesAt: []` is distinct from absent: it is attend-*none*, where absent is attend-*all* — the `afk` preset and bare `duet afk` produce it. Posture is otherwise fixed at `duet new`; the lone mid-run exception is `duet afk` (`docs/run-operations.md`), which re-sets the downstream posture as it hands an interactive run off to the headless driver.

**Gateless** is the walk-away-*from-the-start* posture (`--gateless` or `gateless: true`), sugar over two orthogonal axes for an owner who has pre-decided the direction: the **posture axis** materializes `gatesAt: []`, and the **consultant axis** narrows the checkpoints by *kind* (§"Consultant checkpoints") — dropping the holding `challenge` bet audit while keeping the `generative` frame and the `backstop`. It needs no change to the severity hold itself: it changes *what produces holds*, plus the one `enterAfk` backstop-preserving refusal above. So the only stops left are a verify-stuck `high`, a missing-contract `high`, or a genuine `ask_human` — and the merge, never automated. Gateless conflicts with a non-empty `gates_at` and with `--interactive` (which drives the planning gates in-session — the opposite of walking away from the start); with no consultant bound it is simply attend-none.

The orchestrator never interprets gate posture from prose. Frontmatter is parsed deterministically by the CLI, stripped from the framing body, and rendered into the phase entry prompts and the `advance_phase` result as harness-authored instructions — including the escape hatch: product calls that would have waited for a live gate are encoded as recommendations and carried forward, *unless* proceeding unanswered would make most downstream work throwaway, in which case `ask_human` (pre-authorized ≠ uninterruptible).

The rework path deliberately compresses: a deep error discovered at the next attended gate is handled by reject-with-feedback there (the orchestrator routes the rework) or by abandoning the run — no re-open-an-earlier-phase machinery. Whether overnight runs' encoded recommendations hold up is watched in each run's notes (open-questions.md §"Settled, still watched").

**The frontmatter boundary rule** (also at `src/surfaces/framing.ts`): a key earns frontmatter only when its practical expression is a **fixed value** and the **harness consumes it without judgment** — if either side is soft, it stays prose. The frontmatter is the machine-parsed half of the **run manifest**: with the flags and config it resolves — per key, flags > framing > config > shipped defaults, once at `createRun` — into the frozen answer to "what run will this be", echoed back by `duet new`. Current keys (this list's one home): `gates_at`; `spec` (a draft-spec path); `workflow`; `retry_infra`; `gateless` and `interactive`; the `bind.<address>` keys — the framing tier of the binding resolution; and a `consultant` **on/off toggle**. Admitting `bind.*` deliberately **reversed the 2026-06-22 toggle-vs-binding line** (which kept bindings config-only): a binding is *workflow intent*, not only billing posture — relay's criss-cross is part of what the run *is* — while the boundary rule survives, because a binding spec is a fixed value deterministically consumed. The toggle and the binding compose: `consultant: off` beats any `bind.consultant`; both in *one* source is a rejected contradiction; `bind.consultant` alone implies bound. Each key also has a CLI flag, which wins. Pre-approved if a run-level budget model lands: `budget_usd` (open-questions.md §"Run-level budget"). Spec/plan locations, verification posture, skills: prose, always — the planlab run's framing gave a spec dir that was wrong relative to the worktree root and judgment resolved it; a deterministic consumer would have enforced the error.

### Branch policy

A run works on **exactly one branch, fixed before the first worker prompt** — created either by the human before `duet new`, or by the orchestrator. The harness reports the repo's current branch in the first phase's entry prompt; the orchestrator judges whether it already looks like the working branch for this problem and proceeds on it, or calls `create_branch` with a name it chooses. The git side (`git switch -c`) is harness-executed; the tool is structurally legal only before any worker session exists, so mid-run branch switches are unrepresentable.

Workers take the branch as given: the orchestrator names the working branch in its first prompt to each worker, with the instruction that branch management is settled outside their sessions. Branch creation has exactly two owners — the human before the run, or the orchestrator before the first routed prompt — and is never a worker's call.

### The final-gate packet and the CEO summary

When the AFK phase's review loops converge, the orchestrator reconciles the docs (`reconcile-docs`) and then drafts the packet — sending the `ceo-summary` snippet to the tail's owner (the builder; relay's judge owns these tails). On a consultant run the `verify` checkpoint runs after both, as the last step before `advance_phase`. The Ship gate then presents, in order: the **CEO summary** — the lead artifact, product-first (what the PR does, bugs fixed, problems solved; then the technical approach at CEO/CTO altitude), written for the human *and* for explaining the PR to a colleague without walking the diff — a recurring free-form move in the observed corpus **(observed: planlab b7487993 07:22:37Z, a463ad80 07:12:21Z, e9607005 05:12:52Z)**; the **implementation handoff** (the review-aligned map: what/why, change map, decisions, deviations, tests, where-to-look-hardest); the **review history** (rounds run, points raised/resolved/disputed); and **diff stats and round counts vs. backstop caps**. `ceo-summary` is distinct from `pr-description`: the former is for the human gate and colleague-facing explanation, the latter for the PR body (a technical colleague who won't read the diff); both run, `pr-description` inside `finish`. The planning-stage variant of the same reframe is folded into `write-spec` as its mandatory leader-facing opening section (2026-06-12). The bodies live in the shipped library (`snippets/build.toml`); any tabtype twin stays in sync by hand.

## Prompt agency

Two-tier, settled 2026-06-11:

- **Per-turn: free.** Each routed turn, the orchestrator adapts the snippet to the run at hand — collapsing the template's deliberate generality onto the actual task while keeping its discipline intact, never steering the solution (`docs/prompting-and-tool-design.md` §"Snippet adaptation") — or composes a custom prompt when nothing fits. Every `send_prompt` logs the source tag and the delta from the template — drift is auditable in the orchestrator's transcript.
- **Library: gated.** Persistent snippet changes are proposals (`propose_snippet_edit`), accumulated and presented at the end-of-run gate for human approval. The library only changes with the user's editorial sign-off.

Rationale: the user already evolves snippets mid-session by hand **(observed: planlab b7487993 08:10–08:28Z)** — so evolution is a real workflow behavior, but a bad adaptation that persists silently would compound across every later run.

### Template economy

A snippet is a durable **behavioral frame** plus an ephemeral **per-turn payload**, and worker sessions are persistent — so a full template goes to a given worker **once per phase**, with every later turn steered by the delta (`-again` variants for review loops; short frame-referencing follow-ups otherwise). Re-sending a full template makes the worker restart the exercise instead of continuing it **(observed: the first planlab run re-sent `think-holistic` after gate feedback)**. Enforced at three altitudes, none a hard block: the principle in the orchestrator's system prompt, per-phase send-history annotations on `list_snippets`, and a **warn-once-then-allow** gate on `send_prompt` — a duplicate base-template send gets one steering refusal naming the delta alternatives; repeating the identical call passes, so judgment can override deliberately and auditably.

## Loop semantics

Loop exit (another review round vs. converged) is **orchestrator judgment** — the thing the human currently does by reading the checker's response and feeling whether the remaining points are minor. Two deterministic backstops remain in the harness:

- **Hard per-phase round caps** as runaway protection, not as the exit mechanism (the values live with the walkthroughs above and in the registry). Hitting a backstop is itself an `ask_human` event.
- **Budget caps** are **opt-in and off by default** (the `--budget` flag or config `budget` key): absent ⇒ no cap (the flat-quota maintainer's posture); on ⇒ the per-phase profile scaled by a frozen multiplier. One resolver, `budgetFor`, feeds every cap site. The caps stay **per worker turn** — a fresh `send_prompt` carries a fresh ceiling — and the prompts say so explicitly, after the first real run showed the rail silently shaping a scope decision. A hit cap is a **resumable checkpoint, not a crash**: a settled turn is flagged budget-truncated (resume for the remainder), a session-less cutoff is a typed `BudgetCutoffError` (never the infra-retry path), and an orchestrator cap queues a `cause: 'budget'` stop — not an infra failure, not a product question. Whether a **run-level** budget model is needed is open (open-questions.md §"Run-level budget").

The old mechanisms this replaces: severity-label parsing (never built), `disagree.point` string-matching across rounds (the orchestrator now *reads* the disagreement and judges whether it's persistent and substantive), and fixed caps as the primary exit rule.

Implementation runs as a **single pass** by default: the orchestrator instructs the builder to build the whole settled design end to end, and crosses worker turns only because a turn is budget/time-bounded (resumption, not a review rhythm) — the review loop runs once, after the full implementation, never between slices. Splitting the build into implement-a-slice → review → implement-more cycles is the waste this guards against **(observed in the first runs: a 3-slice plan driven as two implement turns with a needless inter-turn hold)**. The **midpoint checkpoint** is the one judgment-gated exception, for a genuinely large build — more than ~6 slices is a rough signal, but the orchestrator judges by real size and structural risk, not the count. It is a *single* pause: the builder takes the checker's midpoint guidance, applies the now-fixes, and folds the rest into the remaining slices, then continues to the handoff — skipped entirely for small or moderate work. It is *not* a mandatory human gate; if the midpoint triage surfaces a product question, that flags like any other.

## Operating a run

The full operational surface lives in `docs/run-operations.md`: every CLI verb and flag, the framing input and seed templates, run state on disk, the tmux viewer and context telemetry, the graph surface, supervision from outside (position vs. health, the auto-retry policy), and the concierge. The resilience machinery behind the AFK window — the forced watchdog, the wall-clock backstop, the honest failure split, the context-pressure loop — lives in `docs/afk-resilience.md`. Two operating invariants belong in the spine: **position and health are different questions with different surfaces** (`duet status` answers "where is the run and what do I type"; `duet doctor` answers "is each voice alive"), and **every stop has a next command** — gate, flag, crash, budget stop, or exhausted retry, the run always parks with the exact command that acts on it.

## What the MVP should *not* do

- **Auto-*merge* the PR.** Never — merging is the irreversible handoff to human product judgment, and it stays the human's. Auto-*opening* it, by contrast, is the default (reversed 2026-06-22): opening a PR is non-destructive, so a finished run reconciles docs, writes the description, pushes the branch, and runs `gh pr create` on the standing authority — all inside `finish`. The Open-PR gate sits *after* the open; the env-verification reminder rides the PR body as a `Verification (pending)` checklist. Gate-crossing stays un-forgeable (§"Gate pre-authorization").
- **Let the orchestrator write.** No write/edit/bash tools in its surface — a property of the harness. It commands workers; it never touches artifact content. The single, deliberate exception is `create_branch` (§"Branch policy"): a harness-executed ref creation before any work exists, structurally unavailable once a worker has been prompted.
- **Let the orchestrator answer substance.** Triage only. Product, environment → human; tactical → bounced to the worker.
- **Apply snippet-library edits mid-run.** Proposals queue to the end-of-run gate.
- **Run a daemon or concurrent runs per repo.** The process lives through a phase, exits at gates; runs stay serial.
- **Support more than two providers.** *(Reworded 2026-06-11 from "be agent-agnostic".)* A third provider means forking the code — an explicit choice, not a gap. No vendor-abstraction layer.
- **Bundle project conventions in config.** One config file exists — the voice-bindings file (`docs/voices-and-providers.md`) — scoped to account-level binding defaults **plus account/billing posture** (`transport`, `budget`, `[corpus]`) and nothing else; a run's manifest may re-bind per run, which is workflow intent, not project knowledge. Spec paths, skill names, branch conventions, doc-update rules: framing-turn territory, never config. If a key that isn't a voice binding or billing posture is about to land in the config file, that's the design failing. *(Two artifacts are the apparent exception that proves the rule — both customize the **tool**, neither carries project knowledge: framing seed templates are **pre-baked framing**, parsed and archived as the framing itself, and the snippet override layers replace duet's own prompt bodies per key — the project's knowledge still enters only through the framing (`docs/run-operations.md`; README §"Customizing the snippets"). The heavier "project profile" that would auto-merge such pre-context stays shelved; `docs/future-directions.md`.)*

(Removed from this list, by reversal: "Use an LLM as the routing judge" — see §"Design history".)

## Success criteria

The founding bar — met on real runs across the shipped workflows (the README's verified-vs-not line carries the current evidence) — and the standing bar new scope must not regress:

1. **Planning:** a fully attended planning stage where the human's only keyboard touches are the framing, the gates, and `ask_human` answers — zero copy-paste routing.
2. **AFK:** a delivery stage the human leaves for 1–3 hours, returning to either a Ship-gate packet (CEO summary on top) or a well-formed queued question — never a silently stuck or runaway loop.
3. **Auditability:** for any routed turn, the orchestrator's transcript answers "why this snippet, why this adaptation" without asking anyone.
