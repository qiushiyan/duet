# Automation design

This document describes the duet design as of the **2026-06-11 pivot**, in the vocabulary ratified by the **2026-07-04 domain remodel** (`CONTEXT.md`, the glossary that tiebreaks every naming question): an intelligent, read-only LLM **orchestrator** routes the snippet protocol between each stage's two duty **workers** — planning's architect and analyst, delivery's builder and critic or judge — inside a deterministic phase-and-gate skeleton enforced in code. It supersedes the dumb-router design of 2026-05-26. The reversal and its rationale are recorded in §"Design history" below; the decision ledger (`docs/open-questions.md`) tracks what the pivot settled and what it opened.

**Status** — what's built, test-verified, and live-verified — lives in two honest places, the README's verified-vs-not line and `docs/open-questions.md`, not here: this document describes the design as built, in present tense. The one piece designed but deliberately unbuilt is codex-as-orchestrator (`open-questions.md` §"Codex as the orchestrator").

## Design principles

These shape every other choice. Re-read before adding scope.

### Augment, don't replace

Duet drives the same `claude` and `codex` CLIs the user already uses, with the same snippet protocol, against the same codebase. Every artifact duet produces is also producible by the manual workflow — JSONL transcripts in the standard locations, branches with regular names, commits with regular messages. The pivot *extends* this principle rather than weakening it: the orchestrator is itself an LLM session with its own JSONL transcript, so every routing decision it makes is inspectable and auditable the same way the workers' turns are. There is no "duet mode" the user is locked into.

### Stop anytime

A run can be paused indefinitely. The state file at `.duet/runs/<run_id>/state.json` is a fast-access hint; the source of truth is the JSONL transcripts of **every voice's** session — the orchestrator's and each duty's. The user can stop at any gate, switch to manual `claude --resume <id>` / `codex exec resume <id>`, add turns by hand, and either resume duet later or never. On resume, the harness re-reads JSONL tails; the orchestrator re-derives position from the transcripts, not from cached offsets.

### Personal tool first, publish-ready

Built for one developer's use across their own projects. The CLI is project-agnostic: no project conventions hardcoded, no skill registry, no `.duetrc`, no codebase introspection. Project-specific knowledge — which skills exist, where specs go, branch conventions, model choices — flows in through the user's framing turn at `duet new`. (The optional snippet-override and seed-template files customize duet's *own* prompts, not convey project knowledge — a separate matter, reconciled in §"What the MVP should *not* do".) When the framing references something that doesn't exist, the orchestrator flags it to the human rather than inventing fallbacks.

Publishing (npm / public repo) is a kept-open option, not a goal (2026-06-12): the design constraints above don't soften for hypothetical users, but shipped artifacts — the `skills/` folder, the README — are written for any user and never reference the author's personal setup. No community roadmap.

One shipped artifact carries duet's *own* methodology this way: the PLAN-phase snippets — and short's `implement-direct`, which carries the same discipline into the workflow that has no plan — cite design and testing lessons, vendored into `lessons/` (two topics, `codebase-design/` + `testing/`) and resolved at serve time through a `{{lessons_dir}}` token (`src/orchestrator/library.ts`). This is not the skill registry the first paragraph rules out — there is no catalogue, discovery, or config, only the dependency closure of the worker-facing snippets (today two topics) — and it is the same ownership move already made for the tabtype-seeded snippet library: duet owns and ships its quality opinion. The line that keeps it honest is what a *worker reads at runtime*: that must ship (vendor it); a reference used only to *author* duet's prose — e.g. the `prompt-engineering` skill the specs are written against — stays out. Re-vendoring from the author's `~/.config/lessons` — a Stow-managed, forked-and-consolidated lessons dir in its own right — is a deliberate manual step (`pnpm vendor-lessons`), the mirror of the snippets ⟷ tabtype hand-sync.

### Not a daemon — but alive through a phase

*Amended from the 2026-05-26 "per-gate process" rule.* The process model is **per-phase, not per-gate**: each phase (which may take 1–3 hours during AFK implementation) is driven by a detached child process that exits at the next gate or queued exception, persisting state. The invoking `duet new` / `duet continue` returns immediately — it stages the human's input, spawns the driver (`_drive`, stdout to `.duet/runs/<id>/driver.log`, pid in `driver.pid`), and frees the terminal for follow-up duet commands; a pid guard refuses to start a second driver for a run whose phase is still running. With gate pre-authorization (§"Gate pre-authorization") the driver lives through the whole pre-authorized stretch — several phases, crossing each recorded gate on the human's standing authority — and exits at the next attended stop. Nothing runs when no phase is active; there is still no resident daemon, no GUI, no webhook listener. An intelligent orchestrator must hold its session open *across* the many routed turns inside a phase — but gates remain process exits, which is what keeps the semi-AFK shape (answer a gate from any terminal, hours later). An **interactively-orchestrated** run has no `_drive` during the planning stage at all — the human's interactive orchestrator session holds it open and `duet continue` crosses the gate inline; the detached driver starts only at the stage boundary — planning's last gate, derived rather than declared (`handoffGateOf`: full: plan; blueprint and relay: spec; short: Direction) — into the AFK delivery stage.

## Design history — the 2026-06-11 pivot

The 2026-05-26 design stated, as an explicit non-goal: *"Use an LLM as the routing judge. The orchestrator is a state machine that drives subprocess CLI calls… It is not a third agent."* That decision is reversed. Three strands of evidence drove the reversal:

1. **The old design was already approximating judgment with mechanism.** The `needs_human`/`disagree` schema fields approximated "noticing something is off"; string-matching `disagree.point` across rounds approximated "this argument isn't resolving"; fixed iteration caps approximated "this loop converged"; the `ORCHESTRATOR_RESUME_FROM_PROPOSAL` token approximated "knowing where we are in a skill." Each compensation existed because the router had no judgment. **(observed in this repo's own design docs)**

2. **The real workflow has variance a fixed state machine cannot absorb.** A 22-session corpus scan of the user's planlab project (2026-05-29 → 2026-06-11, `~/.claude/projects/-Users-qiushi-dev-planlab-main/`; see `docs/observed-pattern.md` §"Corpus scan: planlab") found multi-PR pivots inside one session, a parallel worktree session run concurrently, review polling started and stopped by hand, a recurring human-as-environment-proxy loop (migrations, smoke tests), and the user evolving the snippet library itself mid-session. **(observed)**

3. **The routing tax is heaviest exactly where judgment is needed.** The same scan: 41 `/copy` invocations, ~84 sub-60-char glue messages ("go ahead", "continue with the rest"), keyboard touches every 7–15 minutes during spec/plan loops. **(observed)**

**The cost of the reversal, named:** routing becomes nondeterministic (mitigated: every sent prompt is logged with its source snippet tag and delta; gates are un-skippable in code); token cost rises materially — the orchestrator reads all inter-agent traffic, and Anthropic measured orchestrator-worker systems at ~15× chat-level token use (mitigated: per-invocation budget caps, orchestrator self-compaction); debugging "why did it route that" is harder than reading a state machine (mitigated: the orchestrator's transcript *is* the explanation); and v1 is larger than the old Slice 1.

What did **not** change: the human gate list, the snippet protocol as the substance of the workflow, every augmentation principle, the worker plumbing (CLI resume, JSONL transcripts), and the personal-tool non-goals.

## The voices

A **voice** is any speaking party of a run — the umbrella noun for the mechanical surfaces (bindings, sessions, logs, panes, health). Three kinds, deliberately not equivalent:

| Voice | Writes? | Job |
|---|---|---|
| **Orchestrator** | **Never** — enforced by tool surface, not instruction | The machinery's voice — carries no duty, never a `send_prompt` target. Drives the protocol: picks the next snippet, adapts it, routes worker output, judges loop exits, triages questions, flags the human |
| **Workers** — each stage's two **duty** voices: planning's **architect** (maker) + **analyst** (checker); delivery's **builder** (maker) + **critic** or **judge** (checker, per the workflow's review posture) | Makers yes — the architect writes the documents, the builder the code. Checkers review only (a prompt-level convention, not a sandbox; 2026-06-22) — except relay's **judge**, whose fixer posture grants **action-scoped** write authority (`writeAuthorityFor`: the `review-and-fix` round and the tails it owns, never a midpoint read) | The commanded, artifact-producing voices: specs, plans, code, handoffs, summaries on the maker lane; critique at the right altitude on the checker lane (relay's judge also fixes findings in place) |
| **Consultant** *(optional)* | No (review only) | An optional advisor — a low-context, cross-family voice that questions the *bet* (assumptions, product fit), not the build. Off by default; bound per run. Checkpoint kinds, never a duty. |

**Duties are the protocol addresses and the runtime keys.** The vocabulary is closed and globally stage-unique — a duty alone names its stage — and it is what every mechanical surface speaks: `send_prompt(duty, …)`, `duet takeover <duty>`, the `<duty>.log` files, sessions keyed `"stage.duty"`, bindings per duty. The orchestrator carries no duty and is never addressable, yet stays a full operational voice — its log, session, status row, and takeover work like any voice's (the augmentation principle). The consultant is addressable but ephemeral: checkpoint-scoped, never a duty. Cross-stage statements use the **lane** words — every stage pairs a **maker** and a **checker** — while per-stage statements name the concrete duty.

The orchestrator is not a worker and not a tiebreaker: **it does triage, never substance**. It never answers a product, design, or technical question with its own opinion — it decides *who* should answer (the worker itself, per protocol, or the human, via a flag). The structure anticipated a fourth voice, and the **consultant** (below) realizes a bounded form of it — *one optional advisor*, not arbitrary specialists; a third *maker* duty stays out of scope (`docs/future-directions.md`).

The **consultant** answers the question the embedded checker is structurally blind to. A persistent checker accumulates the whole run's context — full's critic continues its analyst's planning session over a continuity edge — which is what makes it strong on *is this well-built* and invested in the framing it helped shape, so it rarely challenges the *bet*. The consultant supplies that missing altitude: a deliberately **low-context**, **ephemeral** (a fresh seeded session each time, so it never decays into a second embedded checker), **read-only**, **cross-family** voice — a different model family being the one thing a single checker working harder can never provide. It is **additive, never substitutive**: it never counts as a review round and never replaces the embedded checker. It fires at gate-adjacent **checkpoints** (§"Consultant checkpoints"), is bound per run (§"Voices are decoupled from providers"), and a `high` finding it surfaces can **hold** a pre-authorized crossing (§"Gate pre-authorization"). Its three asymmetries — ephemeral session, read-only, discard-and-reseed on an orphaned turn — live as data in one policy table (`src/voices/policy.ts`; `docs/engineering.md`), not as scattered conditionals. Implemented and test-verified (663 tests at its landing); first live exercise came on the composed `deep-relay` run — gateless, so the framing read and the contract/verify backstop ran while the bet audits stayed off **(observed: run `20260705-1731-58a5`)**; the value question stays open (`open-questions.md` §"The consultant's value").

### Voices are decoupled from providers

Settled 2026-06-11, restated by the remodel: **a duty is a capability contract; a provider is an implementation that can serve one or more of them.** No voice is hardcoded to a vendor — orchestrator-on-codex with the checkers on claude is a legal configuration, not a fork. This generalizes the earlier worker-swap decision to every voice.

Exactly two providers exist. Their *defaults* differ — claude names a model per binding, codex inherits one from the user's config — but the binding vocabulary is symmetric: any voice may pin a model, a normalized reasoning effort, and provider-native passthrough.

- **`claude`** — Anthropic models via the Agent SDK / `claude` CLI. Configured **per-model**: each binding may name a model ID (`claude-opus-4-8`, `claude-fable-5`, …), because choosing the Anthropic model per voice is a knob the user actually turns.
- **`codex`** — the Codex CLI. The model **defaults to the user's `~/.codex/config.toml`** — the config-first philosophy, where reasoning effort, profiles, and sandbox already live and duet never duplicates them; absent an override duet passes no `-m`. A binding **may also pin a model inline** (`codex:gpt-5-codex`) when a run wants a specific one — config by default, overridable per binding.

**Beyond the model, a binding carries two more knobs, under one discipline.** A normalized **effort** (`low|medium|high|xhigh`, plus claude's `max` and codex's `minimal`) maps to each provider's native reasoning-effort setting (`--effort` / `modelReasoningEffort`); and a config-only **native passthrough** hands raw provider arguments through unchanged — `claude_args` appended to the `claude` argv, `codex_config` fed to codex's `-c` overrides — the escape hatch for anything duet doesn't model. The discipline is the line between duet's *own* vocabulary and the *provider's*: the model default and the effort enum are duet's, so it **validates them fail-closed** at the manifest freeze — an illegal `(provider, effort)` pair (codex `max`, claude `minimal`) is rejected at `duet new`, because claude's CLI *silently* falls back to default on a bad effort and a silent-default overnight run is exactly the drift duet refuses. The native passthrough is the provider's vocabulary, so duet is a pure conduit — it never parses, filters, or denylists the arguments (no safety net second-guessing which flags are dangerous). What keeps that honest is a **preflight** at `duet new` (`src/voices/preflight.ts`), scoped to the bindings carrying an explicit model or a native override: it runs one throwaway worker turn per such binding and disposes on the provider's own verdict — a rejected argument or an unusable model **aborts run creation** with the provider's error, while anything transient or ambiguous warns and proceeds (a create-time gate must never block a healthy run on a hiccup; a case it can't positively identify degrades to fail-at-first-use, never a silent mid-build failure). So a bad binding fails *at creation, with the human present*, never hours later mid-build. Model and effort are **per-turn**, so they never enter a session's continuity compatibility — only provider (and claude transport) can degrade an edge.

**Capability contract per voice.** The worker duties need session resume and streamed output; both providers satisfy these today (claude via the SDK/CLI, codex via `resume`). Workers run with **full permissions** — claude headless via `--permission-mode bypassPermissions`, codex by deferring entirely to the user's `~/.codex/config.toml` (no `--sandbox` flag) — so duet's coding agents are no more restricted than the user's own manual workflow (2026-06-22). This superseded a per-duty OS sandbox: codex `read-only` is a Seatbelt profile that denies *all* local writes and network, which broke even a read-only checker's own evidence tooling (a `tsx`/Node tool's `$TMPDIR` IPC socket dies with `listen EPERM`; outbound reads are blocked) *and* overrode the user's config. A checker's review-only behavior is now a **prompt-level convention** (the `review-*` snippets ask for critique, not edits), not a sandbox. The **orchestrator** demands more: custom harness tools (`send_prompt`, `ask_human`, …), read-only enforcement, and pause/resume at a tool call. The claude provider satisfies this natively (Agent SDK in-process tools + `canUseTool`). A local MCP server exposing the harness tools now **exists** — the kernel is host-neutral and served over standard stdio MCP (above) — so the harness-side half of the codex bridge is no longer hypothetical; what remains unbuilt is the codex-side wiring and its two open verification questions (pause/resume at a tool call, tool-call faithfulness), which remain open (open-questions.md §"Codex as the orchestrator").

**Configuration.** Config holds **account-level binding defaults** — the one config duet ships, scoped to voice→provider bindings (model, effort, native passthrough) **plus account posture** (`transport`, `budget`, and the opt-in `[corpus] dir` — a central, analysis-only archive every run's record mirrors into, fail-soft and default-absent; `docs/corpus-runbook.md`) and nothing else. The run-long voices are top-level tables; the duties get `[duties.<duty>]` tables:

```toml
# ~/.config/duet/config.toml — account-level binding defaults + billing posture.
# Project knowledge never goes here; that's the framing turn's job.
# A run's manifest may re-bind any voice (flags > framing bind.* > config > these defaults).

budget = "off"                # opt-in per-turn cost caps: "off" (default — unbounded),
                              # "default" (the per-phase profile), or a positive
                              # multiplier (e.g. 0.5, 2). The --budget flag wins.

[orchestrator]
provider = "claude"
model = "claude-opus-4-8"     # any Anthropic model ID; e.g. claude-fable-5

[duties.architect]            # planning's maker
provider = "claude"
model = "claude-opus-4-8"
effort = "high"               # normalized: low|medium|high|xhigh (+ claude's max)

[duties.analyst]              # planning's checker
provider = "codex"            # model/effort/native optional; absent ⇒ ~/.codex/config.toml governs

[duties.builder]              # delivery's maker; bind codex here for a
provider = "claude"           # plan-on-claude / build-on-codex run
model = "claude-opus-4-8"
# claude_args = ["--fallback-model", "claude-opus-4-6"]    # native passthrough (claude only)

[duties.critic]               # delivery's checker on full, blueprint, and short…
provider = "codex"
# model = "gpt-5-codex"       # optional inline codex model (else ~/.codex/config.toml)
# codex_config = { model_reasoning_summary = "detailed" }  # native passthrough (codex only) → -c

# [duties.judge]              # …and relay's — the writing checker only relay uses
# provider = "claude"
# model = "claude-opus-4-8"

# Optional — the ONE binding absent from the shipped default. Add it to enable
# the consultant (§"The voices"); a different family from the delivery checker
# is the point. Read-only by policy, so transport="interactive" is rejected here.
[consultant]
provider = "claude"
model = "claude-opus-4-8"

# Optional telemetry posture — presence turns on the corpus mirror: every run's
# record (logs, state, gzipped transcripts) also lands here, fail-soft, so it
# outlives its worktree (docs/corpus-runbook.md).
# [corpus]
# dir = "~/duet-corpus"
```

Per-run, one repeatable flag overrides any of it: **`--bind <address>=<provider[:model][@effort]>`** (e.g. `--bind builder=codex:gpt-5-codex@high --bind judge=claude:claude-fable-5`; the native passthrough is config-only, never inline). A duty alone names its stage — duty names are globally stage-unique, enforced by `validateRegistry` (an explicit `stage.duty` long form is reserved for a future collision, documented but not built) — and the run-long voices ride the same grammar: `--bind orchestrator=…` (claude-only in v1), `--bind consultant=…` (binding one implies it is on; `--no-consultant` disables a bound one for one run and wins). The file above is also the **shipped default** when absent: the maker lanes and both run-long claude voices on claude/Opus 4.8 (updated 2026-06-15 from the earlier Fable-5 default), the checker lanes on codex — the cross-family review is the shipped posture. A costlier model like Fable 5 (~2× Opus) binds to any single address per run when an artifact-heavy feature warrants it.

These sources — flags, the framing's `bind.*` frontmatter keys, config, shipped defaults — resolve into the **run manifest**, once, at `createRun` (`resolveRunConfig`, `src/voices/bindings.ts`). Precedence is **per key**: each address resolves independently through flags > framing > config > defaults, so a framing that binds only the judge leaves the builder on config/defaults. The result **freezes on the run state** and `duet new` **echoes it** — workflow, each stage's duty bindings, consultant, degraded continuity edges, gate posture — so a run can never freeze bindings nobody saw **(observed: run `20260703-1444-717d`, created with silently-frozen defaults and abandoned)**.

What connects the two stages is not a binding band but a **continuity edge** — registry data on each workflow declaring that a delivery duty *continues* a planning duty's session, with the seed ritual that carries it. full, blueprint, and short declare both lanes: `builder ← architect` carries the planning session across via the build's entry seed (full's boundary compact; blueprint's compact plus its doc re-anchor; short's direct entry from the decisions), and `critic ← analyst` continues directly — the checker persists across the whole run, kept deliberately. relay declares **no edges**: its whole delivery stage is born fresh, whatever the bindings. A duty with no inbound edge simply starts fresh — nothing resets, because nothing was shared; this one concept subsumes the retired post-handoff `build` overrides, the phase-band binding resolver, and the session-reset ledger. Because a session can never resume across providers, an edge whose two duties' *frozen bindings* cross providers **degrades to fresh at manifest freeze** — never an error (binding `builder=codex` on full is a legitimate plan-on-claude / build-on-codex run), never silent (echoed by `duet new` and recorded on the run state), and the ritual adapts: a degraded edge seeds from the committed document instead of compacting a session the duty doesn't have. `voiceBindingFor` is the **one** "who runs this turn" resolver — a frozen-manifest lookup by address, no band logic, no phase parameter (a duty names its own stage) — read alike by worker construction, session identity, the context-pressure scope, stats, and takeover; a duty's session resolves its own `"stage.duty"` slot first, then walks its continuity edge, else seeds fresh (`sessionRecordFor`).

## Architecture: three layers

### Layer 1 — Harness (deterministic code)

A statechart: each **phase** is a state that runs the orchestrator agent; each **gate** is a state in which no agent runs and which transitions only on human events. The two event vocabularies are kept disjoint: a phase completes by emitting an internal `phase.advance`/`phase.flag`, while a gate transitions only on a `human.*` authority event. A gate has no `phase.*` handler, so `advance_phase` can park a run at a gate but can never cross it — gate-skipping is unrepresentable, not merely forbidden. No tool emits `human.*` — whether the orchestrator runs in-process or in a separate process over the tool boundary — so that guarantee holds across the process boundary too. (Implemented in XState v5 at `src/run/machine.ts`; the states are built from the run's **compiled workflow** — frozen at creation, the shipped standard library at `src/registry/workflows.ts` — the single source for its stages, duties, continuity edges, phase order, caps, budgets, and gate copy. How the code uses XState — tags, persistence, the test seam, the event vocabulary — is `docs/engineering.md` §"XState usage".)

The harness also owns:

- **Worker subprocess plumbing** — spawn/resume worker sessions, completion detection, output capture, graceful kill (SIGTERM→SIGKILL escalation; the one bug *not* to inherit from prior art is sandcastle's missing `proc.kill()`). Prior art is vendored at `references/sandcastle/` (MIT — copy with attribution): exact CLI invocations in `src/AgentProvider.ts`, stream-line parsers for both CLIs, idle-vs-completion dual timeouts in `src/Orchestrator.ts` + ADR 0019, session-file lookup by id in `src/SessionStore.ts`. See `references/README.md` for the full per-repo borrowing guide.
- **Read-only enforcement** — the orchestrator's tool surface contains no write/edit/bash tools. Its read-only nature is a property of the harness, not a promise in a prompt.
- **Gate interception** — `ask_human` and `advance_phase` are harness-owned tool handlers: the handler persists the question/phase-exit at the moment of the call (the human-visible artifact exists before the model regains control), then instructs the orchestrator to end its turn; the harness exits when the turn ends. The interception is the handler side effect, not the permission system — the SDK's mechanical pauses corrupt resume (repros: `src/spike/repro-*.ts`).
- **State persistence** — the machine snapshot is written **only at quiescent states** (gates, flag-waits, done — states with no live actors). Mid-phase crash recovery comes from the JSONL transcripts, which is where it always came from.

### Layer 2 — Orchestrator (LLM agent)

A read-only agent whose system prompt is the workflow protocol operationalized — phases, snippet usage rules, altitude lenses, compaction discipline, triage rules — plus the per-run framing the user supplies. The voice is provider-decoupled (§"Voices are decoupled from providers"); when bound to the **claude provider** — the default, and the only orchestrator-capable provider in v1 — the substrate is the Claude Agent SDK (read-only via tool configuration — `tools: []` hides all built-ins, custom tools via `tool()` + `createSdkMcpServer()`; session JSONL on disk in the standard location, so the orchestrator's session stays manually resumable with `claude --resume`); confirmed by the substrate spike (`src/spike/q11.ts`), **with one correction**: the AFK pause at `ask_human` is *cooperative*, not mechanical — the tool handler queues the question, persists state, and instructs the orchestrator to end its turn; the SDK's mechanical pause options (hook `defer`, `canUseTool` deny+interrupt) both corrupt session resume in SDK 0.3.170 (repros at `src/spike/repro-*.ts`). The SDK source is vendored for API study at `references/claude-agent-sdk-typescript/` (proprietary license — consume as an npm dependency, don't copy code; see `references/README.md`).

The tool surface is **host-neutral**: the base tools live in one registry independent of any SDK, hosted by thin adapters — the in-process Agent SDK server (the default), a standard stdio MCP server, and the run-scoped server the interactive orchestrator connects to (`docs/engineering.md`, the "Host-neutral kernel" and "Interactive orchestrator host" patterns). The same handlers and rails serve all, so the orchestrator behaves identically wherever it runs. On that footing the **interactive CC session is itself an orchestrator host** over the planning stage (`duet orchestrate` / `duet new --interactive`): the human's own session drives the planning phases up to the stage boundary, steering and gate conversation happen in chat, and the run hands off to the headless driver there. That session is opened fresh by default, or **warm-started from an existing one** (`--resume-session <id>`) — the discussion the framing grew out of, so the orchestrator inherits that shared understanding rather than meeting the problem cold, and its first turn is a transition kickoff into the orchestrator identity instead of the cold-start one. The session id is persisted, so a dropped session reconnects to the *same* one (`duet orchestrate`) rather than restarting cold. On this host `send_prompt` is **fire-and-collect**: it dispatches the worker turn into the background and returns at once — so the session never freezes for the minutes a turn runs — and a ninth tool, `check_turns`, delivers the result when it lands. The headless driver keeps its blocking `send_prompt` and has no `check_turns`, so this is a host switch in the one registry, not a fork. A single-writer lease on the run-scoped server stops a superseded session from writing over the live one, and a turn orphaned by a session quit is detected on disk and recovered with `duet takeover`. (This async interactive path is live-verified — the interactive host is the author's daily driver for planning stages **(observed: daily use, 2026-07)**.) Gates are still structural — `advance_phase` only parks — and the one safety setup is a single `ask` permission rule on `duet continue` (`Bash(duet continue:*)`) that survives the human's bypass-permissions default, since no tool can emit `human.*` regardless of host.

**Tool surface** (definitions and the rails they enforce: `src/orchestrator/tools.ts`):

| Tool | What it does |
|---|---|
| `get_task()` | Read the current phase's entry brief — documents in scope, branch policy, attendance, worked examples — returned in full every call. The interactive host's way in: read at phase start, after a gate, or to re-anchor after compaction; it folds a staged human input (approval rider / reject feedback / answer) in once. Not read-only — marks the phase started on first call; reports the park (no side effects) once the phase is at its gate/flag. |
| `list_snippets(all?)` | Read the **effective** snippet library (the shipped defaults with any user/project overrides merged in — §"What the MVP should *not* do"), **phase-focused by default**: this phase's templates and the anytime helpers in full, other phases indexed by key, annotated with what's already been sent this phase. `all: true` returns every body — the cross-phase escape hatch. |
| `send_prompt(duty, tag, body)` | Send a prompt to a worker — one `duty` (the enum is the phase's live duties plus `consultant`), or a **duty array** to fan one identical body to several at once. `tag` names the source snippet (`"custom"` when composed from scratch); `body` is the final text, logged with the tag so adaptation drift is auditable. The array is the framing analysis pass — one address-neutral read to `["architect","analyst"]`, each analyzing independently and in parallel (the consultant's framing read is deliberately different, so it stays its own send); independent single-duty turns to different duties also overlap, and a second turn to a duty in flight is refused (one session is one conversation). **Host-divergent completion:** headless blocks and returns the worker's response (a fan-out runs the turns concurrently and returns one duty-labeled result); the interactive host dispatches into the background and returns at once, collected later with `check_turns`. |
| `check_turns()` | **Interactive host only.** Collect the results of turns dispatched by `send_prompt` — the worker's text (or a failed turn's prescribed recovery), with the same bookkeeping a blocking turn would have done, plus any pending steers. Instant: it delivers whatever has settled, names any duty still running, and reopens a collected duty; a phase cannot advance while a dispatched turn is uncollected. (`duet status --wait` wakes the moment a turn settles.) |
| `ask_human(question, context?)` | Flag something for the human. Always the cooperative pause: the handler persists the question, the run exits at quiescence, and the human answers via `duet continue --answer` — in attended phases they're at the terminal and answer in minutes; during AFK the question waits. |
| `advance_phase(summary, artifacts, spec_path?)` | Declare the phase complete. Legal only when the phase's exit criteria are plausible; lands on the phase's human gate (every workflow gates every phase, so an advance always parks at one — full's last is `finish`, which opens the PR before its Open-PR gate). `spec_path` reports where the spec file landed when the phase produced it (framing-only entry). |
| `create_branch(name)` | Create and switch to the run's working branch (§"Branch policy"). Harness-executed; structurally legal only before the first worker prompt. |
| `propose_snippet_edit(snippet_key, proposed_body, rationale)` | Queue a persistent snippet-library change for the human's end-of-run review. Never applied mid-run. |
| `write_note(observation)` | Append a friction observation to `.duet/runs/<run_id>/notes.md` — the dogfooding journal, written by both the human and the orchestrator. Allowed even while parked at a gate or flag (F2): a pure `notes.md` append has no statechart effect, so the quiescence rule that refuses work tools at a stop doesn't apply — an observation gets recorded the moment it crystallizes. |

#### Prompting and tool-surface conventions

Adopted 2026-06-11 from Anthropic's published guidance, first applied in the substrate spike. The full reference — duet's house patterns and observed evidence over the general rulebook, plus the source links — is **`docs/prompting-and-tool-design.md`**; consult it whenever writing or revising a prompt, tool definition, or tool result. The binding rules:

1. **Artifacts first, task last, XML-tagged** — longform content at the top in `<documents>` tags, instructions in a `<task>` block at the end.
2. **Thinking framework over prohibition** — positive instructions carrying the *why*; no aggressive emphasis (current models overtrigger on it).
3. **Tool descriptions surface the implicit, load-bearing facts** (e.g. `send_prompt`: a duty's session persists across turns; worker turns are slow).
4. **Errors prescribe the recovery path** — name the failure layer, say what to do next, and prescribe only what the system can prove; never bare tracebacks.
5. **Results that change the agent's next step say so explicitly, with the reason** (the `ask_human` queued-response nudge that makes the cooperative pause work).
6. **One world per rendered prompt** — no knob-conditionals in prose; the renderer branches and selects dedicated fragments per knob value (§"The workflow vocabulary").
7. **No duet vocabulary in model-facing text** — run the familiar-term test on every workflow, duty, gate, and checkpoint name before it ships; the process's shape in plain words helps a worker, its internal names do not.

### Layer 3 — Workers

Unchanged in shape from the 2026-05-26 design: resumed CLI sessions, transcripts in the standard locations, invoked per turn by the harness on the orchestrator's instruction. Driving mechanics verified 2026-06-11 against the locally installed CLIs:

- **Codex-bound workers** (the shipped default for the checker lanes) — duet passes **no `--sandbox` flag**, deferring the sandbox and approval posture entirely to the user's `~/.codex/config.toml` (the `@openai/codex-sdk` adds `--sandbox` to the CLI argv only when `sandboxMode` is set, so omitting it lets the config govern). This reversed a derived `-s read-only` override (2026-06-22): codex `read-only` is a Seatbelt profile denying *all* local writes and network, which broke a read-only checker's own evidence tooling (`tsx`'s `$TMPDIR` IPC socket → `listen EPERM`, outbound reads) and ignored the user's config — review-only is a prompt-level convention now. Resume is a verb (`codex exec resume <id>`) and **`--output-schema` works on resume** in codex-cli 0.133.0 (upstream issue fixed May 2026 by openai/codex#23123 — live-verified locally with a two-turn schema-enforced smoke test). Gotcha: an open stdin pipe makes `codex exec` block waiting for EOF — close stdin or pipe the prompt through it deliberately. Preferred wrapper: `@openai/codex-sdk` (thin spawn-the-CLI wrapper; rollouts still land in `~/.codex/sessions/`, so augmentation holds), pinned to the same release as the CLI, with the raw flags as known-working fallback. SDK source + docs vendored at `references/codex/`.
- **Claude-bound workers** (the shipped default for the maker lanes) — a spawned `claude -p --output-format json --resume <id>`, writing the standard `~/.claude/projects/` transcripts and drawing from the subscription credit pool (headless usage is metered separately from interactive sessions since 2026-06-15 — hence the per-invocation budget rails). An opt-in **interactive transport** (`transport = "interactive"`) drives the interactive `claude` TUI instead, so the worker's turns bill the *flat* subscription quota rather than that metered pool — built as a spike, maker-duties-only (bind it on `[duties.architect]` or `[duties.builder]`), transcript-as-truth (`docs/interactive-transport.md`). Headless permission posture: **`--permission-mode bypassPermissions`** (the user's 2026-06-11 decision) — the AFK builder edits files, commits, and runs project commands (tests, typecheck, builds) with nobody at the keyboard, and the user accepts the unprompted-execution tradeoff on their own repos. Explicit deny rules still apply, and the CLI refuses to run as root. (The interactive transport shares this bypass posture, which is why it serves the maker duties only — a read-only interactive checker would need a posture of its own.)

### Worker compaction

Two maker-lane `/compact` moves, each at a boundary:

- **Plan→build (`compact-for-impl`)** — the seed ritual of full's `builder ← architect` continuity edge: the `implement` phase's first act, after the plan commits, compacts the inherited planning session down to what the build consumes. Deliberately *not* at spec→plan: exploration and planning share one substrate (reading the code to design against it), so a cut there only forces a reread before a line-cited plan — whereas the committed plan file already carries the design across the plan→implement seam, and the slices reread fresh anyway. (`compact-for-plan`, the manual after-spec variant, stays in the library for a judgment-timed early cut when a long spec phase bloats context — not the default; context-fill telemetry is the signal.)
- **Build→review (`compact-for-review`)** — before the review cycle, orchestrator-timed by the context gauge (once the fill crosses 75%, the next slice boundary; the natural fallback is after the last slice): drop the build journey, keep the mental model, decisions, and test state.

Per provider: **claude** compacts in place — a `/compact …` prompt body (same session, instructions honored; the provider substitutes a synthetic confirmation for the empty turn) — then `reread-context` re-anchors it. **codex** auto-compacts near its window ceiling, so it is never commanded and `~/.codex/config.toml` is never touched (its context-window overrides are the one way to break exec-mode auto-compaction); it gets the `reread-context` re-anchor alone. Either way **the plan must be a repo file**: compaction drops the journey, so the committed plan + spec are the re-anchor. Timing is instrumented, not felt: every worker result carries the voice's context fill, compaction is due from 75%, and past 85% the harness refuses non-compact sends and cuts running turns — the pressure design (metering, bands, salvage) lives in §"Resilience for the AFK window".

## Question triage

The orchestrator's flagging rules, stated as instructions it must follow. Questions from workers come in three kinds:

1. **Product / direction questions** ("should this be billing-gated?", "is breaking compatibility acceptable?") — **always flag** via `ask_human`. No exceptions.
2. **Environment questions** ("do you need me to run the migration?", anything touching DB/Slack/deploy credentials) — **always flag**; only the human can act. **(observed: planlab b7487993 12:10:23Z, e9607005 10:34:53Z)**
3. **Tactical questions the worker can answer itself** ("do I need a migration step for this schema change?") — the orchestrator answers with **process, not substance**: "decide per the plan and record the decision; if it's actually a product call, say so and I'll flag it."

The orchestrator never supplies a technical opinion of its own — answering would make it an invisible third opinion-holder whose influence bypasses the human gates. Whether these rules over-flag or under-flag in practice is an open calibration question (open-questions.md §"Triage precision"). The triage outcomes are also surfaced as structured signals for a supervisor reading from outside — a gate packet's `humanDecisions[]` and a queued question's `cause` (`human` vs `infra`) — so the concierge or interactive orchestrator decides hold-vs-relay and escalate-vs-resume mechanically; both are signal-only and described under §"Supervising a run from outside".

## Phases and gates

duet is **workflow-aware**: a run picks one workflow at start (`--workflow`, default `full`; a `workflow:` framing key by another door) and carries its compiled spec from creation on (§"The workflow vocabulary" — the freeze), so every workflow-shaped fact resolves through one source per run. Four workflows ship, and a project can compose more from the same vocabulary. Three of the shipped set form a ladder by how much ceremony the work warrants — **full** (spec and plan each get their own loop and gate), **blueprint** (full minus the plan phase — the spec is the whole design), **short** (no document at all — the research decisions are the design) — and the fourth, **relay**, redistributes the *duties* rather than the ceremony: blueprint's shape with a criss-crossed build, where a cheap builder executes and a strong judge fixes findings directly and owns the finishing tails.

### The workflow vocabulary

The workflows are not four hand-built machines. Each is an **expression in a small composition vocabulary** — the hierarchy **workflow → stage → phase → duty** — and the shipped set is an opinionated standard library over it. A workflow is an ordered list of **stages**; every workflow has two, **planning** and **delivery**, partitioning its phase list. Planning is the attended thinking stretch — a workflow with no document still has one (short's research alone is its planning); delivery is the AFK stretch (the build and the PR open); and the **stage boundary** between them is where continuity edges apply and where an interactive run hands off to the headless driver (its gate is *derived* as planning's last phase — `handoffGateOf`, one source, no stored field). A stage is one holistic thinking flow carried by two **duty** voices, a maker and a checker: planning's **architect** + **analyst**, delivery's **builder** + **critic** or **judge** — which checker duty a workflow uses is its review-posture knob (relay uses `judge`). The duty vocabulary is closed and globally stage-unique, growing only with a shipping workflow. Inside a stage, each **phase** is an instance of a **block** with knobs. The split that keeps composition safe:

**Grammar — fixed rules of the language, never composable.** Every phase exits through a human gate and only `human.*` crosses it; cooperative pause, the terminal-marker discipline, state-file-is-a-hint; one branch per run; framing as the single project-knowledge seam; the orchestrator does triage, never substance, read-only by tool surface; prompts are duet-authored (the per-key snippet overrides stay the one sanctioned customization channel — composition selects and arranges blocks, it never authors prose). `machineFor` builds any phase list into the same loop/flag/gate idiom, so the grammar is composition-independent by construction — a composed workflow cannot compose its way past a gate.

**Vocabulary — the composable inventory, closed by rule.** Four blocks — **frame** (parallel analysis → synthesis), **doc-loop** (draft/review rounds on one artifact), **build** (the AFK implementation), **finish** (the PR open) — each with the knobs the shipped workflows actually need and no more: the doc-loop's artifact kind (spec | plan), round cap, and consultant checkpoint; the build's entry seed, review posture (critique | writable | fixer), midpoint, verify checkpoint, ship packet, and build-tail owner; the finish owner. **A workflow's documents are ordered** — the first is always the spec, any later one a plan — checked at load, so a plan that would reread a spec nobody wrote is unrepresentable. Everything else a doc-loop needs, the compiler *derives from position* rather than from the artifact's name: whether its gate hands the run off to the AFK build (it is planning's last phase) and where the acceptance contract seeds from (a committed document precedes it, or its own draft is the only one). Stages carry the rest of the registry data: each stage's duty pair and the workflow's **continuity edges** — full, blueprint, and short declare both lanes (`builder ← architect` via the boundary compact / doc re-anchor, `critic ← analyst` direct); relay declares none (§"Voices are decoupled from providers"). A knob value exists only when duet ships hand-written prompt support for it *and* a shipped workflow exercises it — enforced at load, not by convention: `validateRegistry` rejects a combination whose snippet family or brief fragments don't exist (and checks the topology: stages partition the phases in order, duty names stay globally stage-unique, edges run planning→delivery only), and each block's snippet lists are *derived* from the knob values rather than hand-listed per phase (`docs/engineering.md` §"Patterns that carry the design"). Speculative knobs — parameterizing anything that doesn't vary across the shipped workflows — are refused on sight.

Two consequences bind everything downstream. **Every rendered prompt describes exactly one world**: a worker or orchestrator never reads knob-conditional prose ("if the posture is fixer, …") — the compiled semantics decide and the renderer selects dedicated fragments per value (the single-world rule, a binding convention in `docs/prompting-and-tool-design.md`). And **a new workflow is an expression, not code**: relay landed as one composition plus its snippets — no statechart change, no contract-machinery change.

**The authoring surface is a TypeScript SDK, and the standard library dogfoods it.** A workflow definition is `defineWorkflow({ name, title, phases, attend?, presets? })` over four block constructors — `frame`, `doc`, `build`, `finish`, imported from `duet/workflows` — and the shipped four are themselves these expressions (`src/registry/workflows.ts`), so a user composes in exactly the grammar the standard library is written in (the equivalence is pinned: each shipped workflow's SDK rebuild compiles byte-identical to its registry row). The author states only the phase list and the gate posture; the compiler (`src/registry/define.ts`) derives everything else from the phase semantics — the stage partition, duty pairs, continuity edges, entry seeds, prose worlds, gate copy, round caps — and validates the result against the closed vocabulary above, so a composition outside shipped prompt support is rejected at load with the valid worlds named, never briefed vaguely at run time.

**Definitions resolve from two authoring layers and freeze per run.** `duet new --workflow <name>` resolves the name across shipped / project (`.duet/workflows/<name>.ts`) / user (`~/.config/duet/workflows/<name>.ts`) — a name defined in more than one layer is a collision error, never a silent shadow — compiles it once, and `createRun` freezes the compiled workflow to `.duet/runs/<id>/workflow.json`; every later process reads that artifact (`workflowFor(state)`), so a live run cannot be corrupted by editing, deleting, or retuning any workflow source. Structure and membership freeze; prose stays live by key (snippets and brief worlds), so a snippet-library improvement still reaches a mid-flight run. The authoring dirs are provisioned with a `tsconfig.json` and a typed SDK stub (no per-project npm dependency); the pre-run `duet workflows` inspector lists, compiles-and-checks, and scaffolds definitions without starting a run (§"Invocation and lifecycle"); and worked definitions — the shipped relay and full rebuilt from the blocks, plus a novel hotfix lane — ship with the duet-frame skill (`skills/duet-frame/references/workflow-definitions.md`). The path is live-verified end to end: a project-composed workflow ran gateless to an open PR **(observed: run `20260705-1731-58a5`)**.

The **full** workflow — the thorough path: a three-phase planning stage, a two-phase delivery (the old nine-phase machine survives as nested steps inside them):

```
PLANNING (the attended stage — architect + analyst)
  onboard → frame (both, parallel) → synthesize
    ── GATE: Direction ──
  spec draft → review/update rounds
    ── GATE: Commit spec ──
  plan draft → review/update rounds   (planning keeps full spec-exploration context)
    ── GATE: Plan approval ──            ← the stage boundary: interactive→headless handoff; under the default `overnight` posture the human has already walked away (after the spec)
DELIVERY (AFK — builder + critic; both continue the planning sessions over the continuity edges)
  implement: commit plan → compact-for-impl + reread → single implementation pass (one midpoint checkpoint only if large)
  → compact-for-review (judgment) → implementation-handoff
  → review/respond rounds → fixes → re-review
  → reconcile-docs (update + commit — the last build step, so Ship reviews code + docs)
  → ceo-summary (builder drafts) → [consultant verify, last]
    ── GATE: Ship ──                     ← auto-crosses by default (overnight); env verification shifts to PR-review time. Attended (skip-plan) → human returns, verifies (migrations, smoke tests), approves
  finish: pr-description → open the PR   (docs already on the branch; finish is PR-only)
    ── GATE: Open PR ──                  ← AFTER the open: the PR is already open. Auto-crosses to done by default; gates_at: finish adds a post-open review stop
```

| Gate | Boundary | What the human decides |
|---|---|---|
| **Opening framing** | start of run | Provides issue text, product context, scope. The input, not a pause. |
| **Direction** | inside PLANNING | "Does this direction match what I meant?" |
| **Commit spec** | inside PLANNING | "Spec is solid; commit and move on." |
| **Plan approval** | planning → delivery (the stage boundary) | "Plan is workable." The interactive→headless handoff; the walk-away point only under a posture that attends plan — under the default `overnight` the human has already walked away after the spec. |
| **Ship** | inside DELIVERY (implement → finish) | Reads the final-gate packet (below); runs environment verification (migrations, smoke tests — the human as environment proxy acts *here*, before deciding); "ship" / "another round" / specific changes. |
| **Open PR** | end of `finish` (end of run) | **The PR is already open** when this gate is reached: `finish` writes the description and runs `gh pr create` *before* advancing, so the gate reviews an opened PR (open-then-review), not a pending one. Docs were already reconciled at the tail of `implement` (reviewed at the Ship gate) and ride the branch; `finish` never touches them. The open is idempotent — a pre-existing PR on the branch is amended (`gh pr edit` / more commits), not re-created. Auto-crosses to done by default (opening a PR is non-destructive; the human owns the merge). The run ends with the PR URL leading its summary; the PR body leads with a `Verification (pending)` checklist, the standing pre-merge reminder when the Ship gate auto-crossed unverified. List `finish` in `gates_at` for a post-open review stop — the human reads the opened PR and approves (done) or rejects with feedback, which re-enters `finish` to *amend* it (`gh pr edit` / more commits), never to re-open. The merge is the human's either way; it is never automated. |

Plus **in-phase exception gates** whenever the orchestrator calls `ask_human`. The machinery is identical in every phase — the question is persisted, the process exits at quiescence, `duet continue --answer` resumes. What differs is the human: attended means they're at the terminal and the pause lasts minutes; AFK means the question waits hours until they return (with a desktop notification fired either way).

The **blueprint** workflow — **full minus the plan phase**, for serious work on a trusted frontier-model builder, where a separate plan would overlap the spec heavily and two review loops buy little over one:

```
frame (attended machinery, auto-crossed by default)
  onboard → think-holistic (both, parallel) → compare-notes synthesis
    ── GATE: Direction ──                  ← auto-crosses under the default posture (severity hold intact)
spec
  spec draft → one review loop (section-scoped altitude) → [consultant authors the contract, last]
    ── GATE: Commit-spec ──                ← the workflow's one attended stop by default; ratification + the stage boundary (interactive→headless handoff); contract freeze
implement (AFK)  — full's implement, reused: build (implement-spec seeds it) → review loop → reconcile-docs → ceo-summary → [verify, last]
    ── GATE: Ship ──                       ← auto-crosses by default
finish — full's finish, byte-for-byte:  pr-description → open the PR
    ── GATE: Open-PR ──                    ← after the open; auto-crosses to done
```

Nothing about the spec changes because the plan is gone: every workflow's spec is the same half-technical document with the same internal altitude gradient — product sections on top (goals, behaviors, non-goals), technical sections below (module boundaries, seams, the target shape, and test standards; full code bodies, test-case lists, fixtures, and commit order are deferred). What changes is who inherits the deferred detail: full hands it to the plan, blueprint hands it to the build. The document's structure is the review lens's structure — `review-spec` holds each section to its own tier, so a loop can't re-grow the plan-depth rounds this workflow deletes; its cap is an explicit `rounds: 2`, the fast-convergence premise made a rail. Because the spec is every workflow's first document, `--spec` enters here with a draft spec and the contract path derives unchanged. The build seeds from `implement-spec` — the committed spec is the authority for *what and why*, the snippet carries the *how* (vertical slices of the builder's own choosing, the same vendored methodology) — not short's `implement-direct`, whose body assumes no document exists. The default posture is the workflow's product promise: **one interruption** — the Direction gate auto-crosses, the human reads one document, taps once at the Commit-spec gate, and walks away (§"Gate pre-authorization").

The **relay** workflow — blueprint's shape with the build criss-crossed, for the plan-smart / build-cheap / judge-strong economy: expensive judgment at the ends, fast labor in the middle, and a judge that *acts* on its findings rather than filing critiques back:

```
frame → ── GATE: Direction ── → spec → ── GATE: Commit-spec ──   (identical to blueprint,
                                          ↑ the one attended stop; the stage boundary; contract freeze)
implement (AFK)  — the whole delivery stage is born fresh: relay declares NO continuity edges
  builder starts FRESH from the committed spec (implement-spec seeds a new session)
  → implementation-handoff (the builder authors the map)
  → ONE review-and-fix round: the judge critiques AND fixes in place
  → judge: reconcile-docs → ceo-summary → [consultant verify, last]
    ── GATE: Ship ──                       ← auto-crosses by default
finish (AFK) — the JUDGE opens the PR:  pr-description → gh pr create
    ── GATE: Open-PR ──                    ← after the open; auto-crosses to done
```

What distinguishes it, piece by piece:

- **The criss-cross is four bindings and zero edges.** The workflow's economics come from per-duty bindings (§"Voices are decoupled from providers"): planning runs architect=claude vs analyst=codex; delivery binds `--bind builder=codex --bind judge=claude[:model]` — fast labor, strong judgment. The freshness is registry data, not a binding side effect: relay declares **no continuity edges**, so both delivery duties seed fresh from the committed spec whatever the providers — and the accepted cost is that the judge never saw the planning loop; the document is its authority.
- **The fixer's discipline** is one dedicated snippet, `review-and-fix`: the full review lens plus the assess-validity / fix-in-place / push-back-with-reasons discipline, with an **escalation valve** — ordinary valid findings are fixed directly, but a product or design disagreement, unclear intent, or broad directional drift escalates via the orchestrator (`ask_human`) rather than being patched over, because a direct fix must never hide a pivot. Self-fix is the default, not an absolute. `implementation-handoff` stays with the builder — whoever wrote the code authors the map.
- **Write authority is action-scoped, never a phase blanket** (`writeAuthorityFor`, §"The voices"): `review-and-fix` and the tail actions may write; a `review-midpoint` turn under the fixer posture stays guidance-only — mid-build the builder is the sole writer, and early correction is folded in by the builder, never patched under it.
- **One writable round** (cap 1, short's discipline): the review-and-fix round is the loop. A follow-up fix request into the same judge session — a failed verify assertion routed back — steers by delta and needs no new round.
- **Verify matters more here.** Under the fixer posture the maker-vs-checker adversariality collapses into sequential build-then-judge, and the judge grades work it then edits — so the consultant's contract verify (a fresh session, neither builder nor judge) is the one fully independent pass, and binding a consultant on relay buys more than on any other workflow. The verify self-heal routes failures to the workflow's fixer duty (`fixerDutyFor`: relay's judge, every other workflow's builder); the independent re-verify chain is unchanged. The rails stay structural only (write authority, `verifiedAt` invalidation, verify-freshness) — no rail classifies whether a finding was "too substantive to fix"; that judgment lives in the snippet and the brief.

The **short** workflow — the lighter path, for small, well-understood work where the spec-and-plan ceremony costs more than it returns (research → implement → finish; no document):

```
research (attended)
  onboard → think-holistic (both, parallel) → compare-notes synthesis
    ── GATE: Direction ──                  ← the research decisions ARE the design; the stage boundary — human walks away / hands off here
implement (AFK)
  build directly from the decisions → implementation-handoff
  → ONE writable review round (review-direct → apply-review, fixes applied in place)
  → reconcile-docs (update + commit — the last build step, so Ship reviews code + docs)
    ── GATE: Ship ──                       ← "is the code good?" (auto-crosses under afk; attended → verify env, then approve)
finish (AFK)
  pr-description → gh pr create            (docs already on the branch; finish is PR-only)
    ── GATE: Open-PR ──                    ← AFTER the open; auto-crosses to done by default, run ends at the open PR
```

It drops spec and plan, not the PR: the synthesized research decisions stand in for the spec, so the builder builds from them directly — and because there is no plan phase to carry it, `implement-direct` itself carries the plan's engineering discipline (vertical slices, deep modules, what-to-test, the same vendored methodology), so the lighter workflow is not a lower bar. Its planning stage is `research` alone — no document, but still a stage, with both continuity edges declared like full's. Its finishing tail is `finish` — the same name and phase spec every workflow shares (workflow-scoped identity), same `openPrGate` machinery and entry brief (`openPrPhaseEntryPrompt`): write the description → `gh pr create`. Docs reconcile at the **tail of `implement`** in every workflow (the last build step, reviewed at the Ship gate) and ride the branch into the PR, so `finish` is a mechanical open that touches no docs. Its review loop is a single **writable** round (the critic critiques once, the builder fixes in place) rather than full's reflect-then-`-again` loop. The Open-PR gate sits *after* the open and auto-crosses to done by default; a reject re-enters `finish` to *amend* the PR (`gh pr edit`), never to re-open it. Because the `afk` posture auto-crosses the Ship gate before the human verifies the environment, the PR leads with a `Verification (pending)` checklist — the same pre-merge reminder full's `finish` carries. Pre-authorizing all three of its gates is the `afk` preset (below): the walk-away-after-research flow that returns to a finished run with the PR open. The workflows share their machinery: the same gate/flag/steer idiom, the same statechart skeleton built per workflow, the same registry-derived per-phase facts.

Inside a phase the orchestrator drives; the human's channels in are the gates, the `ask_human` flags, and — into a live phase — the steer channel below.

### Consultant checkpoints

When a consultant is bound (§"The voices"), the workflow consults it at **gate-adjacent checkpoints**, encoded as registry data (`src/registry/workflows.ts`) so "where it fires" stays in the single source, never scattered through prompts. Each workflow maps the modes onto its own phases: every workflow opens with a **third independent analysis** at framing (`frame`/`research`); full adds a **bet audit** before the Commit-spec gate (`spec`) and short one before its Ship gate (`implement`); the document-bearing workflows (full, blueprint, relay) carry the acceptance-contract pair below. blueprint and relay have **no bet audit anywhere** — a stance, not a gap: those workflows exist for work where the owner trusts the direction after framing and wants only the correctness floor kept. At framing the consultant's read is a synthesis input to the direction, handed to the architect as one of *two anonymized peers* (the architect never learns which is the analyst; the embedded checker and the consultant stay blind to each other — information hiding holds both ways). At a bet-audit checkpoint the orchestrator folds the consultant's findings into its gate packet and echoes each finding's severity into `advance_phase`'s `human_decisions`, where a `high` can hold the crossing (§"Gate pre-authorization"). It runs through the existing worker `send_prompt` seam with a fresh seeded session each time, and never counts as a review round — so a review-loop phase still owes its embedded checker's round regardless.

**Three kinds, by walk-away compatibility.** Each checkpoint has a *kind* (registry data, `CHECKPOINT_KIND` in `src/registry/workflows.ts`) that decides whether a walk-away keeps it — and the cut is *holding* vs *non-holding*, not *questions-the-bet* vs not. The `generative` frame (`frame`/`research`) questions the bet but never *holds*: it has no severity echo into `human_decisions` (unlike a bet audit, just above), so it can only enrich the direction, and a walk-away loses nothing by keeping it — a free perspective at the moment before any code. The `challenge` bet audit (`spec`, short's `implement`) holds via a `high`, and is the friction a walk-away opts out of. The `backstop` (the run-spanning `contract`+`verify` modes below) also holds, but it's the correctness floor a walk-away wants kept. The split is registry-derived, not scattered: one predicate — `consultantCheckpointLive(phase, {consultant, gateless})` — answers "does this checkpoint fire for this run?", read by **both** the orchestrator briefs and the `list_snippets` surface, so they can never disagree about what runs. A **gateless** run (§"Gate pre-authorization") keys on exactly this: the owner has pre-decided the bet, so it drops only the holding `challenge` (`survivesGateless` = `kind !== 'challenge'`) — the `generative` frame still enriches the direction and the `backstop` still guards the build.

**The acceptance contract (the document-bearing workflows: full, blueprint, relay).** On those workflows that backstop is a frozen, consultant-verified definition of success — two further checkpoint modes (`contract` at the workflow's contract-author phase — full's `plan`, blueprint's and relay's `spec` — and `verify` at `implement`, registry data like the others; short authors no contract). The consultant *authors* an **acceptance contract** — a short list of falsifiable, EARS-shaped behavioral assertions, each with a `Verify by:` probe. Its job is to catch runtime drift from the settled design that the builder's own tests would miss, not to re-judge "the right thing". **Placement is derived from topology, and it trades one blindness deliberately.** A contract-author phase with a *committed document upstream* authors **early** — dispatched immediately after that document commits, before the phase drafts its own artifact, seeded with the upstream document only. Full's `plan` is the case: the contract is blind to the plan's tactics and to the code. A phase whose own artifact is the *only* document has nothing upstream to seed from and no phase between its gate and the build, so it authors **late** — the final step after its review loop converges, seeded with the near-final spec (the same runs-last pattern verify uses). Blueprint and relay are that case. What late authoring gives up is blindness to the technical approach; what it keeps is blindness to the code (nothing is built yet), the fresh independent session, and author-never-commits — and it gains a contract that is **human-ratified by default**, since that spec gate is the workflow's one attended stop (full's `overnight` freeze happens at an auto-crossed plan gate nobody read). The blindness full retains is narrower than it sounds: its spec already carries the module shape, the target shape, and the test standards, so an early-authored contract is blind to the *plan*, not to the technical approach. Either way the consultant *writes* the file (a sibling of the spec-slot document, `<stem>.acceptance.md`) but **never commits** it — single-writer-by-construction holds (the discard-and-reseed orphan premise needs the consultant to touch no git history). A consultant turn at the contract checkpoint records a durable **draft marker** (`acceptanceContractDraft`, set in `settleTurn`) — the proof *this run* authored, which freeze and the rail below both require, so a stale contract file from a prior run is never silently ratified (a late-author phase records the marker before the document's path is even registered; the freeze verifies the file at the path it derives at crossing time). Crossing the **contract gate** *freezes* it: a harness step (`freezeContractAt`, keyed on the registry's contract-author phase) commits the file path-scoped — capturing any edits the human made while ratifying it at that gate, and recording `{path, commit}` on the run state — and this happens even on a pre-authorized (auto-crossed, unratified) gate. At **implement**, the `verify` mode supplants the open-ended bet audit: a fresh session re-reads the frozen contract and verifies it by **running the built system and citing evidence per assertion** (execute-to-observe — run tests/CLI/curl, read logs; never edit, commit, or re-enter duet), returning a per-assertion pass/fail. It runs as the phase's **final step, after `reconcile-docs` and the CEO summary** (both code/doc-changing worker turns), so it certifies the exact state being shipped and no later turn leaves the verification stale. A **failed** assertion routes to the workflow's **fixer duty first** (`fixerDutyFor` — the builder everywhere but relay, whose writing judge owns fixes) — fix → a *fresh* consultant session re-verifies → a bounded loop — and is recorded as a `high` `human_decision` (riding the severity hold) **only if it still fails after that**, or if verification could not run at all. This **self-heal is universal** (attended and gateless alike): the human sees a summary of what self-healed, not every fix, and the still-stuck `high` is the load-bearing AFK protection that stops a run rather than shipping past a broken target. The conscious softening of "a failed assertion holds" degrades safely — worst case is still a hold, never a silent ship — because the re-verify is an *independent* session the fixer cannot game (an assertion it wrongly judges "wrong" and leaves unfixed simply re-fails and holds at the bound — and the inverse is live-observed: an assertion the fixer *rightly* judged mis-authored re-failed and held the gate for the human **(observed: run `20260705-1731-58a5`)**).

**The chain is enforced mechanically, not by prompt** (`advance_phase` rails, the same shape as the existing review-round rail): on a consultant run of a contract-bearing workflow, the contract-author phase will not advance without an authored contract (a draft marker) *or* a recorded `high`, and `implement` will not advance past a frozen-but-unverified contract without a `verifiedAt` stamp (set when a verify turn settles) *or* a `high`. The rail enforces that verify **ran and is fresh**: a code-changing (non-read-only) worker turn at `implement` — a self-heal fix, but also `reconcile-docs` or the CEO summary — *clears* `verifiedAt` (`settleTurn`), which is why verify runs last (after docs and the packet); a routed fix then structurally forces a fresh, independent re-verify before advance — the loop's "re-verify after the fix" is structure, not prompt-trust. What stays orchestrator-recorded is whether that final verify *passed*: a still-failing assertion is a `high` on the gate packet — the same trust model as triage everywhere — and the re-verify is always an independent consultant session (never the worker that fixed). The `high` escape-hatch itself holds the AFK crossing, so the run can never *silently* proceed past the chain — the worst case is a flagged stop, never a no-op. If authoring genuinely failed and the human proceeded on a `high`, the `implement` checkpoint is a *noted skip* (no frozen contract to verify). The whole feature is **workflow-scoped**: short authors no contract, and a bound short run sees no contract/verify text at any tool surface (identity prompt, `list_snippets`). Read-only relaxation here is **prompt-level**, like the checkers': the author write and the execute-to-observe surface are scoped by the `consultant-contract` / `consultant-verify` snippets, not an OS sandbox (which the codebase deliberately omits — the integrity that *is* structural is the path-scoped freeze, which commits only the contract regardless of what else the author touched).

### The steer channel

The human's voice has a channel for every run condition: gates take decisions (an approval may carry a rider — agreement plus adjustments, gate feedback in approving form), flags take answers, and a **live phase takes steers** — `duet steer "<note>"`, the editor-in-chief's voice mid-flight. A steer is processed, not answered: it reaches the orchestrator appended to its next *phase-continuing* tool result (one phase is typically one long orchestrator turn, so turn boundaries are too rare to ride; tool results arrive every few minutes all phase long and are already the harness's steering surface), tagged as human guidance that outranks a checker's opinions and counts toward no cap. The orchestrator folds it into its routing — relaying into worker prompts at its judgment, reflecting it in the next gate packet — and a steer is never by itself a reason to `ask_human`: the human chose the non-pausing channel deliberately.

Two boundaries keep the channel honest. Results that end the orchestrator's turn (a recorded phase advance, a queued question) never carry steers — guidance delivered into a dying turn lands and dies — so those steers wait and ride the next harness prompt instead, tagged with provenance, staleness judged by the orchestrator (a steer that misses its phase is carried, never dropped). And at a quiescent stop the CLI refuses the steer outright, naming that stop's own channel — gate decisions and flag answers stay explicit, never smuggled in as notes.

Storage is file-per-steer under `.duet/runs/<id>/steers/`, consumed by rename into `delivered/` — steers arrive while a live driver holds and continuously saves its in-memory state, so they can never live in `state.json`. The crash trade is deliberate: deliver-then-consume, so a crash redelivers a steer rather than losing one (a repeated instruction is benign where a lost one is not). Staging and delivery both land in the voice logs, and `duet status` lists what is still pending — the channel is auditable end to end.

In the harness, each workflow's two stages decompose into machine phases, each on the same loop/flag-wait/gate idiom. full's planning stage is `frame` (onboard → think-holistic in both planning workers → compare-notes synthesis → Direction gate; runs only on framing-only entry) then `spec` (draft on framing-only entry, then review rounds → Commit-spec gate) then `plan` (→ Plan-approval gate, the stage boundary); its delivery stage is `implement` (build → review rounds → `reconcile-docs` as the last build step, commit, no gate → Ship gate) then `finish` — draft `pr-description` → push + `gh pr create` → the Open-PR gate, which sits *after* the open (open-then-review). The workflows share the `implement` and `finish` phase names (workflow-scoped identity). blueprint decomposes as full's `frame` and `spec` (draft, or a `--spec` draft entry, then the one review loop → Commit-spec gate, which is its stage boundary) then full's `implement` and `finish` reused. relay decomposes as blueprint's `frame` and `spec` unchanged, then `implement` (fresh-seeded build → one review-and-fix round → judge-owned `reconcile-docs` + `ceo-summary` → Ship gate) and `finish` (the judge's PR-only tail). short decomposes as `research` (→ Direction gate, the walk-away / stage boundary) then `implement` (build → one writable review round → `reconcile-docs` → Ship gate) then `finish` — the same PR-only tail (same `openPrPhaseEntryPrompt`). Docs reconcile at the `implement` tail in every workflow and ride the branch, so `finish` opens the PR and touches no docs. The review-loop phases (`spec`, `plan`, and each workflow's `implement`) must run at least one review round before `advance_phase`; the others (`frame`, `research`, `finish`) may advance without one — their substance is synthesis or mechanics, and the checker is available but optional. Backstop caps: spec 3 by default (blueprint and relay set an explicit 2 — the fast-convergence premise), plan 3, full/blueprint `implement` 3, frame/research/finish 2; short's and relay's `implement` are 1 — the single writable round is the loop, not a runaway backstop. (The registry, `src/registry/workflows.ts`, is the source; these are the sizing decisions, kept near the round counts real runs need.)

### Gate pre-authorization (`gates_at`)

Added 2026-06-12, after the first real run. A gate bundles three functions — the human's **authority**, **steering** (early-correction leverage), and a **quiescent stop** — and pre-authorization gives up only the steering: the authority is granted in advance, the stop still happens and is recorded.

A run pre-authorizes a subset of its gates at `duet new`: `--gates-at <list|preset>` or a `gates_at:` key in the framing file's frontmatter (the flag wins) names the phases whose gates the human will attend — the rest auto-cross. The gate set, the presets, the **default posture**, and the force-attended gates are all **workflow-scoped** (they live in the registry per workflow). full's presets, named for the human's posture: `overnight` (= `frame,spec` — attend nothing after the spec), `skip-plan` (= `frame,spec,implement` — walk away at spec approval, return at the Ship gate), and `afk` (= attend nothing — every gate pre-authorized from the start, the consultant's nets intact), completing the launch ladder `overnight → skip-plan → afk → gateless`. **`overnight` is full's default** (2026-06-26): plan, Ship, and the Open-PR gate all auto-cross unless listed, so the sleep posture is the out-of-the-box behavior; the env-verification forcing function that the Ship gate carried relocates into the opened PR's `Verification (pending)` checklist — an advisory pre-merge reminder rather than a structural block (the merge is the human's manual act regardless). blueprint and relay share the default **attend the spec gate only** (a new run materializes `gatesAt: [spec]`): the Direction gate auto-crosses, the human reads one document, taps once, and walks away — the one-interruption promise those workflows exist for, with the severity hold below still converting a contentious direction into an attended stop; each one's preset is `afk` (attend nothing). short has the same `afk` preset (= attend nothing — all three of its gates auto-cross, straight to done with the PR open), and no pre-authorized default (it leaves `gatesAt` absent ≡ attend-all). At an auto-crossed gate the harness persists the gate packet, fires the notification, sends `human.approve` on the standing authority, and records the crossing in `state.json` (`autoApprovals`); `duet status` lists the crossings in a "while you were away" section for the morning review. Force-attended gates can never be pre-authorized — but currently *no* workflow force-attends anything: opening a PR is non-destructive (the human owns the merge), so every workflow's Open-PR gate is **pre-authorized by default** (the PR auto-opens; §"What the MVP should *not* do"), attended only when the finishing phase (`finish`) is listed. The mechanism (`forceAttend`) remains, the way `defaultPreAuthorized` (its inverse) does; a gate may not sit in both, enforced at load. The statechart is untouched — gates still transition only on `human.*` events; pre-authorization changes *when* the approval is uttered, never *who* may utter it.

**The severity hold.** A gate packet may carry `human_decisions` — a structured echo of genuine product calls the orchestrator deliberately did *not* make (each a title + severity). A `high` decision **withholds a non-explicit crossing**: a pre-authorized gate will not auto-cross over it, and a one-tap `duet afk` handoff is refused — both convert to an attended stop so the human weighs the call before it ships. An **explicit** human approval (`duet continue --approve`, an interactive crossing) always crosses; blocking the human's own tap would fight the gate model. This is the channel through which a bound consultant's bet audit (§"Consultant checkpoints") can stop an overnight run — a `high` finding rides the packet and holds the gate — but the mechanism is general: any `high` entry holds, consultant-sourced or not. The one deliberate exception is **`duet afk --gateless`** (the explicit walk-away-from-here full-send): it crosses the bet/product `high`s the owner has pre-decided, as an explicit approval would — but still preserves the correctness backstop, refusing to hand off at the contract gate when no contract was authored, so a *missing* backstop is never crossed unattended (the headless `duet new --gateless` path holds there on the same `high` through the untouched severity hold).

Two facts about the posture itself bite if forgotten. **`gates_at` is the complete attend set, not a delta**: it names every gate the human attends and the rest auto-cross. The footgun: `--gates-at finish` attends *only* the Open-PR gate — everything else (frame, spec included) auto-crosses; to keep the usual stops *and* add a post-open review stop, list the whole set, not just `finish`. And a new run **materializes** its posture at creation: a default full run persists an explicit `gatesAt = frame,spec` (the gate phases minus the default-pre-authorized set), a default blueprint or relay run `gatesAt = spec`, and the gate-posture line rides the `duet new` manifest echo — while a workflow with nothing pre-authorized by default (short) leaves `gatesAt` absent, byte-for-byte the pre-feature attend-all. An **empty** `gatesAt: []` is distinct from absent: it is attend-*none* (every gate pre-authorized), where absent is attend-*all* — the `afk` preset (any workflow) and `duet afk` (bare) produce it. Posture is otherwise fixed at `duet new`; the lone mid-run exception is `duet afk` (§"Invocation and lifecycle"), which re-sets the downstream posture as it hands an interactive run off to the headless driver.

**Gateless** is the walk-away-*from-the-start* posture (`--gateless` or `gateless: true`), sugar over two orthogonal axes for an owner who has pre-decided the direction: the **posture axis** materializes `gatesAt: []` (the same attend-none full's `afk` preset now expresses — the difference is the consultant axis, not the gates), and the **consultant axis** narrows it by *kind* (§"Consultant checkpoints") — dropping the holding `challenge` bet audit while keeping the non-holding `generative` frame and the `backstop`. It needs no change to the severity hold itself: it changes *what produces holds* (the bet-audit `challenge` doesn't fire) plus the one `enterAfk` backstop-preserving refusal above. So the only stops left are a verify-stuck `high`, a missing-contract `high`, or a genuine `ask_human` — and the merge, never automated. Gateless conflicts with a non-empty `gates_at` (it pre-authorizes everything) and with `--interactive` (which drives the planning gates in-session — the opposite of walking away from the start); with no consultant bound it is simply attend-none.

The orchestrator never interprets gate posture from prose. Frontmatter is parsed deterministically by the CLI, stripped from the framing body, and rendered into the phase entry prompts and the `advance_phase` result as harness-authored instructions — including the escape hatch: product calls that would have waited for a live gate are encoded as recommendations and carried forward, *unless* proceeding unanswered would make most downstream work throwaway, in which case `ask_human` (which still pauses the run; pre-authorized ≠ uninterruptible).

The rework path deliberately compresses: a deep error discovered at the next attended gate is handled by reject-with-feedback there (the orchestrator routes the rework) or by abandoning the run — no re-open-an-earlier-phase machinery. Whether overnight runs' encoded recommendations hold up is watched in each run's notes (open-questions.md §"Settled, still watched").

**The frontmatter boundary rule** (also at `src/surfaces/framing.ts`): a key earns frontmatter only when its practical expression is a **fixed value** and the **harness consumes it without judgment** — if either side is soft, it stays prose. The frontmatter is the machine-parsed half of the **run manifest**: with the flags and config it resolves — per key, flags > framing > config > shipped defaults, once at `createRun` — into the frozen answer to "what run will this be", echoed back by `duet new` (§"Voices are decoupled from providers"). Current keys: `gates_at`; `spec` (a draft-spec path); `workflow` (a workflow name — shipped, or a project/user definition resolved and frozen at creation); `retry_infra` (the infra-retry budget); `gateless` and `interactive` (fixed postures the harness acts on); the `bind.<address>` keys (`bind.builder: codex`, `bind.judge: claude:claude-fable-5`, …) — the framing tier of the binding resolution; and a `consultant` **on/off toggle**. Admitting `bind.*` deliberately **reverses the 2026-06-22 toggle-vs-binding line** (which kept bindings config-only): a binding is *workflow intent*, not only billing posture — relay's criss-cross is part of what the run *is* — while the boundary rule itself survives, because a binding spec is a fixed value deterministically consumed. The toggle and the binding compose: `consultant: off` beats any `bind.consultant`; both in *one* source is a rejected contradiction; `bind.consultant` alone implies bound. Each key also has a CLI flag, which wins (`--gates-at`, `--gateless`, `--interactive`/`--no-interactive`, `--bind`, `--no-consultant`). Pre-approved if a run-level budget model lands: `budget_usd` (open-questions.md §"Run-level budget"). Spec/plan locations, verification posture, skills: prose, always — the planlab run's framing gave a spec dir that was wrong relative to the worktree root and judgment resolved it; a deterministic consumer would have enforced the error.

### Branch policy

A run works on **exactly one branch, fixed before the first worker prompt** — created either by the human before `duet new`, or by the orchestrator. The harness reports the repo's current branch in the first phase's entry prompt; the orchestrator judges whether it already looks like the working branch for this problem (a feature branch whose name fits the framing) and proceeds on it, or — when the run sits on the default branch or an unrelated one — calls `create_branch` with a name it chooses. The git side (`git switch -c`) is harness-executed; the tool is structurally legal only before any worker session exists, so mid-run branch switches are unrepresentable.

Workers take the branch as given: the orchestrator names the working branch in its first prompt to each worker, with the instruction that branch management is settled outside their sessions. Branch creation has exactly two owners — the human before the run, or the orchestrator before the first routed prompt — and is never a worker's call.

### The final-gate packet and the CEO summary

When the AFK phase's review loops converge, the orchestrator reconciles the docs (`reconcile-docs`) and then drafts the packet — sending the `ceo-summary` snippet to the tail's owner (the builder; relay's judge owns these tails). On a consultant run the `verify` checkpoint runs after both, as the last step before `advance_phase`. The Ship gate then presents, in order:

1. **CEO summary** — the lead artifact. Product-first: what the PR does from a product perspective, bugs fixed, features added, what problems it solves; then the technical approach at CEO/CTO altitude. Written for the user *and* for explaining the PR to a colleague without walking them through the diff. **(general — and directly observed as a recurring free-form move: "give me a more CEO-facing description…" in planlab b7487993 07:22:37Z, a463ad80 07:12:21Z, e9607005 05:12:52Z)**
2. **Implementation handoff** — the review-aligned map (what/why, change map, decisions, deviations, tests, where-to-look-hardest).
3. **Review history** — rounds run, points raised/resolved/disputed, disagreement summary.
4. **Diff stats and round counts vs. backstop caps.**

The snippet's body lives in the shipped library (`snippets/build.toml`; rationale and evidence in `docs/workflow-model.md` §"The `ceo-summary` snippet"), and any tabtype twin stays in sync by hand (duet owns its shipped `snippets/` library; the tabtype config is the human's to update). `ceo-summary` is distinct from `pr-description`: the former is for the human gate and colleague-facing explanation (CEO/CTO altitude), the latter for the PR body (technical colleague who won't read the diff). Both run; `pr-description` follows inside `finish`.

## Prompt agency

Two-tier, settled 2026-06-11:

- **Per-turn: free.** Each routed turn, the orchestrator adapts the snippet to the run at hand — collapsing the template's deliberate generality onto the actual task while keeping its discipline intact, never steering the solution (`docs/prompting-and-tool-design.md` §"Snippet adaptation") — or composes a custom prompt when nothing fits. Every `send_prompt` logs the source tag and the delta from the template — drift is auditable in the orchestrator's transcript.
- **Library: gated.** Persistent snippet changes are proposals (`propose_snippet_edit`), accumulated and presented at the end-of-run gate for human approval. The library only changes with the user's editorial sign-off.

Rationale: the user already evolves snippets mid-session by hand **(observed: planlab b7487993 08:10–08:28Z, revising `.tabtype.local.toml`)** — so evolution is a real workflow behavior, but a bad adaptation that persists silently would compound across every later run, the same early-correction-leverage logic the `review-midpoint` snippet encodes.

### Template economy

A snippet is a durable **behavioral frame** plus an ephemeral **per-turn payload**, and worker sessions are persistent — so a full template goes to a given worker **once per phase**, with every later turn steered by the delta (`-again` variants for review loops; short frame-referencing follow-ups otherwise). Re-sending a full template makes the worker restart the exercise instead of continuing it **(observed: the first planlab run re-sent `think-holistic` after gate feedback)**. Enforced at three altitudes, none of them a hard block: the principle with its motivation in the orchestrator's system prompt, per-phase send-history annotations on `list_snippets` (`already_sent_this_phase_to`), and a **warn-once-then-allow** gate on `send_prompt` — a duplicate base-template send gets one steering refusal naming the delta alternatives; repeating the identical call passes, so judgment can still override (a human re-scope at a gate is the legitimate case) but the choice is deliberate and auditable.

## Loop semantics

Loop exit (another review round vs. converged) is **orchestrator judgment** — the thing the human currently does by reading the checker's response and feeling whether the remaining points are minor. Two deterministic backstops remain in the harness:

- **Hard per-phase round caps** as runaway protection, not as the exit mechanism — tight backstops kept near the round counts real runs actually need (the values live with the phase mechanics, §"Phases and gates", and in the registry). Hitting a backstop is itself an `ask_human` event.
- **Budget caps** are **opt-in and off by default** (the `--budget` flag or the config `budget` key — account/billing posture, the `transport` family): absent ⇒ no cap (the flat-quota maintainer's posture); on ⇒ the per-phase profile scaled by a frozen multiplier (off ≡ absent, never `0`). One resolver, `budgetFor`, feeds every cap site — the worker's `--max-budget-usd` and the orchestrator cap. The caps stay **per worker turn** — a fresh `send_prompt` carries a fresh ceiling — and the prompts and `send_prompt`'s description say so explicitly, after the first real run showed the rail silently shaping a scope decision (the slice-5 descope cited "~$7 of budget left" mid-turn). A hit cap is a **resumable checkpoint, not a crash**: a worker turn that settled with a session id is flagged budget-truncated (resume for the remainder), a session-less cutoff is a typed `BudgetCutoffError` (no settlement, never the infra-retry path), and an orchestrator cap queues a `cause: 'budget'` stop (raise the budget / resume — not an infra failure, not a product question). Whether an explicit **run-level** budget model is needed is open (open-questions.md §"Run-level budget"); this per-turn knob is not that model.

The old mechanisms this replaces: severity-label parsing (never built), `disagree.point` string-matching across rounds (the orchestrator now *reads* the disagreement and judges whether it's persistent and substantive — flagging via `ask_human` when it is), and fixed caps as the primary exit rule.

Implementation runs as a **single pass** by default: the orchestrator instructs the builder to build the whole settled design end to end (full: the plan's slices; blueprint: the spec, through `implement-spec`; relay: the same document through the same snippet, seeded into the fresh session its edge-less delivery starts with; short: the decisions, through `implement-direct`), and crosses worker turns only because a turn is budget/time-bounded (resumption, not a review rhythm) — the review loop runs once, after the full implementation, never between slices. Splitting the build into implement-a-slice → review → implement-more cycles is the waste this guards against (observed in the first runs: a 3-slice plan driven as two implement turns with a needless inter-turn hold). The **midpoint checkpoint** is the one judgment-gated exception, for a genuinely large build — more than ~6 slices is a rough signal where a plan fixes the slices, but the orchestrator judges by real size and structural risk, not the count. It is a *single* pause: the builder takes the checker's midpoint guidance, applies the now-fixes, and folds the rest into the remaining slices, then continues to the handoff — it pauses once, not per slice, and is skipped entirely for small or moderate work. It is *not* a mandatory human gate (per the user's 2026-06-11 decision); if the midpoint triage surfaces a product question, that flags like any other.

## Worker structured output — demoted, not removed

The 2026-05-26 design made `schemas/agent-response.json` the protocol contract: `needs_human` and `disagree` were how a judgment-free router detected exceptions. With an orchestrator that reads prose, the schema is not load-bearing — workers currently run schema-free and the orchestrator reads their final messages. Whether a minimal `{response_text}` envelope earns its way back is open (open-questions.md §"Worker output schema"), decided from dogfooding evidence. Two operational notes if it does: the schema must remain OpenAI-strict-compliant, and `--output-schema` on `codex exec resume` works on the pinned CLI (verified).

The framing input is a single markdown file: an optional machine-parsed frontmatter block — the run manifest's framing tier: `gates_at`, `spec`, `workflow`, `retry_infra`, `gateless`, `interactive`, the `bind.<address>` keys, and the `consultant` toggle, parsed deterministically by the CLI and stripped before the orchestrator sees the framing (§"Gate pre-authorization" carries the boundary rule and the manifest) — followed by prose sent verbatim, structure by convention not contract. The prose is also the orchestrator's project briefing — the only place the project's own *knowledge* enters the system, as distinct from the tool-customization artifacts (the seed templates below, the snippet override layers) that tune duet's prompts across runs without telling it about the project (§"What the MVP should *not* do"). A shipped `/duet-frame` skill authors this framing — a CC session that sharpens a rough problem into the framing document (the project's real names, structure, gate posture) without changing intent or proposing solutions, then emits the `duet new --interactive` command (coherence-pinned by `tests/skill.test.ts`).

**Seed templates.** The framing is mostly project-stable — onboarding skill, conventions, verification, doc rules — and only the problem changes run to run, so a project can pre-bake framings under `.duet/templates/` (location and self-ignore policy in "State persistence" below) and seed the editor draft from one. `duet new --template <name>` reads `.duet/templates/<name>.md`; a bare `duet new` prefers `.duet/templates/default.md` over the built-in skeleton. A template is a *full framing* — the same frontmatter-plus-prose shape — so each kind of work can carry its own posture: a `feature.md` that pre-sets `gates_at: skip-plan`, a `bug.md` that names a different onboarding skill or a lighter verification section, with `# Problem` left as the per-run blank. The name is a plain slug (`bug` → `bug.md`); a typo'd `--template` aborts with the available list rather than silently seeding the wrong run, and `--template` is the bare-entry path only — it conflicts with `--spec`/`--framing`, which supply the framing outright. Bootstrap one by copying the built-in skeleton (left in `.duet/framing-draft.md` by a bare `duet new`) or a past run's archived `framing.md`, then clearing the problem. A template is pre-baked framing, not config: it is parsed and archived as the framing itself, so the framing turn stays the single entry seam for project knowledge (§"What the MVP should *not* do" carries the rule, under "Bundle project conventions in config").

**Ending a run.** Between quiescent stops no duet process exists, so a run never *needs* terminating — leaving it is simply never calling `duet continue` again; the run dir stays an inert record (keep `notes.md`, the dogfooding evidence) and a later `duet new` supersedes it as the default. `duet abandon [run_id]` is the explicit form: it stops the live driver if one is running (SIGTERM→SIGKILL — only the driver pid, so an in-flight worker turn finishes harmlessly into its own transcript) and marks the run abandoned, so `probeRunPosition` reads a deliberate stop rather than a crash. Abandonment stays reversible: the session transcripts are untouched, so `duet continue` revives the run (clearing the marker) and `takeover` opens the session unchanged. `duet abandon --purge` is the destructive form — it deletes the run dir and every session transcript (the orchestrator's and each duty's, located by exact session id, `src/voices/sessions.ts`). That is the one place duet reaches outside `.duet/` into the user's `~/.claude` / `~/.codex`, so it is opt-in and echoes every path it removes; on a finished run there is no driver to stop, which makes `--purge` the post-PR cleanup too.

State persistence: the run dir `.duet/runs/<run_id>/` holds `state.json` (the human-readable hint: state value, session ids, queued flags, rounds, costs, proposals, auto-crossed gates), `machine.json` (the statechart snapshot, written **only at quiescent states** — gates, flag-waits, done), `framing.md` (the verbatim framing archive), one append-only log per voice, `driver.log` + `driver.pid` (the detached phase driver's stdout and liveness), and `notes.md`. The JSONL transcripts are the source of truth.

Duet's runtime artifacts live under `.duet/`, never at the repo root: the directory self-ignores (`.duet/.gitignore` containing `*`, written on first creation — the user's own `.gitignore` is never touched, and `git add -f` still allows committing a run record deliberately), the bare-`new` framing draft edits at `.duet/framing-draft.md`, a project's own framing seed templates live in `.duet/templates/<name>.md` (self-ignored like the rest — a template is the human's authoring convenience, not a tracked artifact of the host repo; carve `!/templates/` into `.duet/.gitignore` to share them across worktrees), and the `implement` entry prompt points workers at this run's own scratch dir (`.duet/runs/<id>/scratch/`, gitignored and torn down with the run) for throwaway verification harnesses — no cleanup step — and forbids deleting anything under `.duet/`, which holds the live run state (a worker's `rm -rf .duet` while cleaning scratch once killed a run mid-build, ending the phase with no advance and no flag; `ensureRunDir` now self-heals a vanished run dir on the next harness write so a stray deletion degrades to a recovered write, not a silent death). Specs, plans, and docs are project files and never live here.

### Visualization: tmux is a viewer, never the runtime

Settled 2026-06-11. Duet owns its subprocesses and writes **one append-only log file per voice** — `orchestrator.log`, one per duty (`architect.log`, `builder.log`, …), `consultant.log` when bound — under `.duet/runs/<run_id>/`, with a harness-written boundary line where a continuity edge carries a session forward. Without tmux, the same lines stream to duet's stdout with colored `[tag]` prefixes (the concurrently/turbo idiom; picocolors auto-disables off-TTY). With `--tmux` on `duet new` / `duet continue` — or `duet view` for a run already going — (`src/surfaces/view/tmux.ts`), duet shells out a handful of tmux commands via execa (no library) to open **one titled pane per voice** — the orchestrator plus the *current stage's* duty pair (and the consultant when bound), derived from the registry enumeration rather than a hardcoded voice list and retitled at the stage boundary — each running `tail -n +1 -F` on its voice's log: `-n +1` replays the full transcript in a late-opened pane, and BSD tail's `-F` waits for logs that don't exist yet. The arrangement is chosen from the width the layout will be **displayed** at: wide gives the 2-column layout — orchestrator narration over the checker's critiques on the left (55/45), the maker full-height on the right since it produces the longest content; a narrow pane stacks every voice full-width instead, so log lines stay readable. That width is read from a surface a client is already showing — the current window, or the `--here` pane — never the freshly-created `-d` window, whose size is stale until it is first displayed (the percentage splits rescale when it is, so only the arrangement *choice* needs the true width; the cutoff is `TWO_COLUMN_MIN_WIDTH`). Three render targets: inside tmux, a `duet-<run_id>` window inserted **immediately after the current one** without stealing focus; `duet view --here` instead **replaces the current pane** with the viewer (ephemeral — the multi-voice sibling of `duet logs`' inline follow); outside tmux, a detached session with a printed attach command. Re-invocations reuse the window/session viewer (`--here` is one-shot); any tmux failure degrades to a one-line note (the `view/notify.ts` philosophy — a viewer must never affect the run).

**Context fill is first-class run telemetry.** Each voice's context-window percentage is captured at turn boundaries — never polled: claude-bound voices report usage in-band (the last request's input + cache reads + cache creation + output against `modelUsage`'s context window, the same formula Claude Code's own statusline uses), and codex turns end with one tail-read of the session rollout (`last_token_usage.total_tokens` against `model_context_window`). The reading lands in `state.json` (a hint, like everything there — stale after manual takeover turns, refreshed on the next driven turn), in the voice-log response headers (`· context 41%`), in `duet status` and the `--json` model's `context` field, and in the tmux pane titles via a plain-text sidecar (`.duet/runs/<id>/context/<voice>`, e.g. `41%`) that the border format `#(cat)`s at its refresh interval. Numeric percentages only, by decision; capture is best-effort and fail-soft — a missing reading is an absent line, never a failed turn.

**Color is view-time only** (added 2026-06-12): the log files stay plain text — they are the inspectable-without-duet artifacts — and each pane pipes its tail through `duet _colorize <voice>` (`src/view/colorize.ts`, picocolors), which renders timestamps in the human's local zone (dimmed — the stored log keeps raw UTC, as does `status --json`; only the view localizes), paints header lines in the voice's color (orchestrator cyan ◆; the maker lane blue ■, the checker lane yellow ● — lanes share glyph and color across stages; the consultant magenta; errors red), and PROMOTES the `⋯` live-activity line to a `[read|edit|search|run] <subject> <HH:MM>` form — action tag in the voice's color (the most emphasis), subject secondary, the action's local time dimmed; the line is colorized once as it streams, so it trails the wall-clock time the action was logged rather than a relative age (which would read ~0 and freeze) — while bodies pass through untouched. The promotion is deliberate and coherent: the `⏳` heartbeat stays dim ambient telemetry (content-free), but an activity line names a concrete action, so it earns emphasis. Pane titles carry the voice glyphs, colored via a `pane-border-format` branch on the full `glyph voice` title (lanes share a glyph across stages; tmux has no per-pane border style). `duet logs` applies the same `[tag]` palette to the driver narration. Because worker turns are non-streaming and can run 30+ minutes (observed in the first real run), `send_prompt` keeps its pane alive on two cadences off one timer pair (`startHeartbeat`): every 5 minutes a `⏳` heartbeat (elapsed + transcript recency/retries) so a pane never looks hung — and because the orchestrator reads no files and, on a headless turn, is blocked awaiting the worker, that heartbeat also mirrors a `⏳ awaiting <duty> — Nm` line onto the orchestrator pane so the control-plane pane reads as alive too — and every 30 seconds a `⋯` **live-activity line** naming the worker's current action (`⋯ reading src/foo.ts`, `⋯ editing src/foo.ts`, `⋯ searching src`, `⋯ running git diff`) so a healthy worker grinding for 30 minutes reads differently from a stalled one. The action is read from the same transcript tail the heartbeat's last-activity age uses — located by THIS turn's session id, which both providers announce at/near turn start (`RunTurnOptions.onSessionId`, staged onto the `activeTurns` hint by `recordTurnSessionId`) rather than the settled session-slot record learned only at settle; that early id is what makes the trace universal — every turn from its start, for every voice and provider, including a worker's FIRST turn (FRAME is all first turns) and every ephemeral consultant turn (whose settled id is always the *prior* session). headless claude predeclares a minted id with `--session-id` (known before spawn); codex reads it off the first `thread.started` event of a `runStreamed()` turn; the interactive-claude transport (which takes no `--session-id`) reads it from the nonce-bearing transcript record once it lands, and a resume on any transport announces its id immediately. `src/voices/sessions.ts` → `readTranscriptTailForSession` does the exact-id locate (never a directory sweep, so the purge contract holds), then `readTranscriptTailAtPath` re-reads the cached path so the 30s poll never re-scans. The action is extracted by a pure, tested parser (`src/voices/activity.ts` `latestActivity`, sibling of `voices/health.ts`'s health probe): claude's `tool_use` carries a structured `file_path` (read/write); codex's work is shell commands, classified into a bounded **read / search / run** vocabulary — a known read command's first file (`sed`/`cat`/`head`/`tail`/`nl`), an `rg`/`grep`/`find`/`ls` target, or a `<tool> <subcommand>` run phrase — taking the FIRST segment of a pipeline/chain as the sourcing action (`nl f | sed` → reads `f`). Because the goal is LIVENESS, not a precise audit trail, codex now surfaces its searches and runs (it used to surface almost nothing — ~6 lines a run against the claude maker's 116); it stays honest-but-low-fidelity, never the raw command, and a redirect, a command substitution, or an unknown tool still surfaces no line. The read/write path is normalized to repo-relative at produce-time (the poll holds the run's cwd, so the activity parser stays pure) — the canonical artifact form, like git's; the local time shown is view-time only. codex writes (when codex serves a maker duty) come from an `apply_patch` custom_tool_call, from whose patch text the first file *header* path is read, never a hunk. It is emitted only when the action changed since the last tick (so it never floods), and is fail-soft like every viewer concern: silent only in the brief window before the provider has announced this turn's id, or on any read/parse failure, never throwing into a turn. No changed-line count — neither provider hands one over for free. A *full* streaming sink (message text, tool inputs, diffs) remains the eventual fix; this is the lightweight slice of it.

The properties this buys: killing tmux doesn't kill agents; killing duet doesn't corrupt tmux; one code path produces lines and two dumb sinks consume them; and the log files are themselves inspectable-without-duet artifacts. The rejected alternative is the claude-squad architecture (agents live *inside* tmux sessions, state read back by `capture-pane` screen-scraping) — vendored as the anti-model at `references/claude-squad/` (AGPL — read-only inspiration, no code reuse).

Separately from the viewer, every quiescent stop fires a best-effort macOS notification (`src/view/notify.ts`) — gate reached, question queued, or run complete — because the AFK phase's whole point is that the human is elsewhere when those land. Notification failure is silently swallowed; `duet status` carries the same information.

### Supervising a run from outside

Supervising a run — by the human, the concierge, or the interactive orchestrator — is mostly answering one recurring question: **is this run healthy, waiting on my decision, or recoverably broken — and if it's waiting, what do I type?** The *position* half is the `status` model and its discriminated `stop`. The *health* half is a pure substrate (`src/voices/health.ts`): an error taxonomy (first-match-wins: login-required → quota-billing → auth → rate-limit → network → dns → server) and a per-voice probe that reads each voice's own transcript and returns a verdict (`idle` / `working` / `long-inference` / `retrying` / `silent-stuck` / `crashed`). Three read-only surfaces share it — never three parsers: `duet doctor` (the on-demand health view plus a connectivity probe), the `send_prompt` heartbeat (so a quiet pane reads as thinking-vs-hung without running a command), and the driver's crash classification. Two liveness sources feed the verdict — the duty workers via a persisted `activeTurns` hint reconciled against driver liveness, the orchestrator via driver + phase state — and every read is fail-soft: a missing transcript is an absent detail, never a failed command.

Two triage outcomes are promoted from prose to fields, so a supervisor decides mechanically rather than re-reading paragraphs — both **signal-only**, neither touching gate-crossing:

- **`humanDecisions[]` on a gate packet** — the orchestrator's structured echo of the genuine human decisions it surfaced, each `severity: low | high`. Empty or all-`low` → safe to relay an approve; any `high` → hold and escalate. The statechart cannot see it; only the human's tap crosses a gate (the two-vocabulary guarantee, untouched).
- **`cause` + `errorClass` on a queued question** — an `ask_human` flag is `cause: 'human'` (escalate); an infra-caught failure is `cause: 'infra'` plus the taxonomy `errorClass` (resume / retry territory). The `crashed` *position* (driver death, observed by `probeRunPosition`) is a separate, unchanged signal.

**The default-on auto-retry policy.** A new run's **headless** driver retries transient infrastructure failures within a bounded budget (`--retry-infra <n>` / `retry_infra:`, **default 3** — materialized at `createRun` like the gate posture, so an old/absent `retryInfra` on a loaded `state.json` stays off byte-for-byte, and `--retry-infra 0` is the explicit opt-out): on a caught failure the driver classifies via the same taxonomy and, for a recoverable class (`network`, `server`, `rate-limit`), re-enters the phase through the existing session-resume path after a capped backoff rather than flagging. `auth` retries once, then a second consecutive `auth` escalates as `login-required`; `login-required`, `quota-billing`, `dns`, and `unknown` never retry; exhaustion always falls back to a flag (every stop still has a next command). The policy lives in exactly one place — the headless driver; the classification taxonomy reaches two — the driver and the stdio interactive host — but the interactive host only classifies, never auto-retries, because a human is present to resume. Every auto-retry is **recorded**, never silent: an `autoRetries` ledger (a sibling of `autoApprovals`, not the gate-shaped field) surfaces in `duet status`'s "while you were away" section (`infra auto-retries: N (network ×2, server ×1)`) and as `auto-retried: …` in `--brief`, so a degrading environment shows up in the morning review instead of churning invisibly (the visibility is what makes default-on safe — the property that originally motivated default-off).

### Resilience for the AFK window

The overnight promise — walk away after the spec, return to an open PR — fails on five modes a daemon-less, single-developer tool still has to survive: a stalled stream, an overnight machine-sleep, a hung compaction, a worker session overflowing its context window, and a misleading failure message. The architecture is a deliberate **native-vs-own partition**: lean on the *documented, stable* Claude Code knob for stall detection duet can't cleanly reproduce, and own only the load-bearing backstop a CLI flag can never cover. Facts verified against **claude v2.1.196** — re-check on a CLI upgrade.

- **The forced watchdog (native).** Claude Code ships a byte-stream idle watchdog that aborts a stalled stream after ~5 min; `API_FORCE_IDLE_TIMEOUT=1` forces it on for *every* connection (it is already on by default on duet's direct-Anthropic path, so forcing it is cheap belt-and-suspenders). duet injects it at all three Claude connections — the headless worker spawn, the orchestrator's own SDK session, and the interactive transport's tmux launch (as a shell env-assignment prefix on the launched `claude`, not inherited from a possibly-stale tmux server env). It is **Claude-only** — a Claude API knob, never set on codex. The undocumented `CLAUDE_STREAM_IDLE_TIMEOUT_MS` / `…_BYTE_…` tuning vars stay best-effort, never load-bearing.
- **The wall-clock backstop (owned), the workhorse.** A monotonic timeout (execa's `timeout`, codex's `AbortSignal.timeout`) freezes its countdown with the process during a machine-sleep, so on wake a "90-minute" cap can map to many real hours — the audited `7447` dead-run, where a 60-min cap rode 117 min of wall-clock. The owned `runWithWallClockDeadline` helper (`src/voices/providers/wall-clock.ts`) bounds a turn in REAL (Date) time instead: it re-checks `now()` against a fixed deadline on a timer tick, so the first post-wake tick catches a suspend-frozen overrun and aborts — then *drains*, waiting (briefly, bounded) for the killed turn to actually exit before it hands back the resumable checkpoint, so the orchestrator's resume can't race a still-dying writer on the same session. It wraps both providers' run loops (claude's execa keeps its monotonic timeout for the fast-path kill; codex drives an `AbortController` it owns). The **AFK build caps** are 90 min (`implement`, every workflow) — 3× the longest measured healthy build turn, the high end of the 2–3× band; planning/finishing phases stay 30 min.
- **caffeinate (best-effort, darwin-only).** `spawnDrive` fires `caffeinate -i -w <driverPid>` scoped to the driver's lifetime, preventing the common *idle* sleep (docked / lid-open). Best-effort by design: a closed laptop lid on battery sleeps regardless, and a spawn failure is swallowed — the honest promise is **bounded-waste-then-recover**, not "never waste hours." The wall-clock backstop is the real protection; caffeinate just removes the common case.
- **Two recovery planes.** A **worker** turn that fails is handed an honest, prescriptive tool result and the orchestrator routes its recovery (resume / re-send / flag) — never mechanical. The **orchestrator's own** stalled or dropped session is what the auto-retry policy above governs — caught by the phase host, classified, mechanically retried on the headless host. The split matters because the honest message a worker failure produces is content the orchestrator reasons over, while an orchestrator-session drop is infra the harness recovers without it.
- **The honest failure split.** A turn killed at its cap is now told the truth, keyed on whether *this turn's* prompt was accepted into the session (a transcript record at/after the turn start, or codex's `thread.started` seen this turn — never a minted id, never a whole-transcript scan that a persistent session would false-positive): accepted-then-aborted ⇒ a resumable checkpoint ("resume, don't re-send"); never-accepted (pre-flight) ⇒ an infra error ("retry verbatim"). This replaces the `7447` lie, where a 117-min turn that committed work was told "the worker never saw your prompt, retry."
- **Compaction robustness.** `/compact` gets its own short 8-min cap (well below the build cap), so a hung compaction fails in minutes. On an *accepted-but-failed* compact the harness resets the worker to a fresh session (resuming the un-compacted, bloated one is wrong) and prescribes the `recover-context` snippet — an orchestrator-authored status overview + reread; a pre-flight compact failure does not reset (the old session is still the one to compact).
- **Context pressure (owned).** Headless claude never auto-compacts, so a persistent worker session fills until the API rejects every prompt — the 20260701 wedge grew 17% → 98% of its window inside one build turn and parked the run ten hours behind "Prompt is too long" retried as if transient. duet owns the loop end to end. *Meter:* every settle records the voice's fill and the 30-second activity tick samples it mid-turn from the transcript tail, so a long turn is live telemetry rather than a boundary blind spot; guards act on the **high-water reading since the last compact** (an error echo's zeroed usage is skipped, never read as 0%), and the readers are probed against real transcripts, not assumed (`src/spike/context-probe.ts`: drift under 0.5% vs the CLI's own compact-boundary accounting, rejection observed at ~97.7% of the nominal window — re-run on a CLI upgrade). *Bands* (constants, not config): from **75%** compaction is due — the result footer flags it and a warn-once rail steers the next send, while the orchestrator's standing fuel-gauge instructions carry the proactive habit; at **85%** enforcement is structural — a non-compact send is refused outright (a `/compact` body is the one send that always passes) and a running turn is cut by the context deadline (`src/voices/providers/wall-clock.ts`, the wall-clock backstop's sibling — same abort-then-drain race) before the session can overflow, each refusal or cut prescribing compact-then-resume. *Salvage:* overflow is classified in the taxonomy and never auto-retried — re-sending can never fit — and on the headless host an already-wedged session self-heals: one automatic salvage `/compact` seeded with run facts, then "re-send this same prompt"; a failed or cut salvage, or a second overflow in the phase, resets the session and prescribes `recover-context` (the interactive host classifies and hands back — the same human-present split as auto-retry). *Scope:* claude + persistent + headless only — codex auto-compacts, the interactive transport's TUI auto-compacts, the ephemeral consultant seeds fresh. The scope reads the turn's **frozen manifest binding** (`voiceBindingFor` — the one per-address resolver, no band logic): under relay's criss-cross the claude judge is metered, probed, and salvageable while the codex builder is not, and every policy surface — the bands, the send rail, the heartbeat probes, the salvage ladder, the context deadline — keys on the same per-voice answer, so the scope can't drift per surface. Every intervention — compact, salvage, cutoff, reset — lands in the `contextEvents` ledger and surfaces in `duet status`'s "while you were away", never silent.
- **The quiescence soft-fail.** The outer per-phase bound (`QUIESCENCE_TIMEOUT_MS`, 12 h) used to crash `_drive` on timeout and strand the run; it now soft-fails to crash=flag — parks the wedged phase in flag-wait and queues an actionable infra question, then hard-exits the driver (the hung phase invoke has no cleanup to abort, so leaving it alive would keep the pid running — misreporting the run — and racing a late write over the parked flag) — so even the outer bound ends in a clean stop with a next command.

### Remote interaction: Claude Code is the concierge layer

Duet never builds its own remote, mobile, or notification infrastructure (the standing constraint in `docs/future-directions.md`); Claude Code is the remote layer. `skills/duet-concierge/` ships a skill that teaches any CC session to drive the duet CLI on the human's behalf — so CC's native remote control, mobile push, and `/loop` supervision become duet's reach-from-anywhere for free. The concierge is interaction glue with zero runtime: killable without consequence, and the run is exactly as operable from the terminal as without it (augment-never-lock-in holds).

The skill's substance is discipline, in priority order: **identity** — a relay, not a fourth engineer; it reports, translates, and executes intent, never opines on artifacts (the orchestrator's division-of-labor rule extended one layer out). **Verbatim relay** — the human's words cross unparaphrased into `--reject`, `--answer`, and `steer`; summarize toward the human freely, never editorialize from them. **Channel translation** — `status --json`'s `stop.kind` keys a mechanical table from intent to command. **Turn-ending stop reports** — when a gate, flag, crash, or completion lands, the concierge ends its turn with the report, which is what reliably fires CC's mobile push. **Double-gated gates** — the skill pre-approves read verbs only (`status`, `logs`, `runs`); the recommended permission `ask` rule on `duet continue` means crossing a gate takes the human twice — chat intent plus the permission prompt, on the phone too — so even a rogue concierge cannot cross alone. The skill is invoked explicitly (`/duet-concierge`), never auto-triggered: a session that merely mentions runs and gates — a session developing duet itself is the standing example — must not inherit the relay identity. A coherence test (`tests/skill.test.ts`) pins every verb and flag the skill names to the real command table, and asserts both deliberate frontmatter properties: read-verbs-only pre-approval and explicit-invocation-only.

`duet takeover` stays terminal-only by nature (it opens an interactive CLI); multi-run supervision is tracked in `docs/future-directions.md`, and the interactive-orchestrator host's first-live-session evidence in `docs/open-questions.md` §"Settled, still watched".

## What the MVP should *not* do

- **Auto-*merge* the PR.** Never — merging is the irreversible handoff to human product judgment, and it stays the human's. Auto-*opening* it, by contrast, is now the default (reversed 2026-06-22): opening a PR is non-destructive (the human owns the merge), so a finished full run reconciles docs, writes the description, pushes the branch, and runs `gh pr create` on the standing authority — all inside the `finish` phase. The Open-PR gate sits *after* the open: by default it auto-crosses to done; the opt-in post-open review stop (list `finish` in `gates_at`) lets the human read the opened PR and reject-to-amend (`gh pr edit` / more commits) or approve. The PR opens mergeable, so the bug-review bots fire on it immediately; the env-verification reminder rides the body as a `Verification (pending)` checklist, the human's standing cue to verify before merging. Gate-crossing stays un-forgeable (§"Gate pre-authorization").
- **Let the orchestrator write.** No write/edit/bash tools in its surface — a property of the harness. It commands workers; it never touches artifact content. The single, deliberate exception is `create_branch` (§"Branch policy"): a harness-executed ref creation before any work exists — the orchestrator supplies the judgment and the name, the harness runs the git command, and the tool is structurally unavailable once a worker has been prompted.
- **Let the orchestrator answer substance.** Triage only. Product, environment → human; tactical → bounced to the worker.
- **Apply snippet-library edits mid-run.** Proposals queue to the end-of-run gate.
- **Run a daemon or concurrent runs per repo.** The process lives through a phase, exits at gates; runs stay serial.
- **Support more than two providers.** *(Reworded 2026-06-11 from "be agent-agnostic" — voices are now provider-decoupled by design, but the provider set is exactly {claude, codex}.)* A third provider still means forking the code — an explicit choice, not a gap. No vendor-abstraction layer general enough for OpenRouter/AI-SDK/etc.
- **Bundle project conventions in config.** *(Amended 2026-06-11; scope widened 2026-06-22.)* One config file now exists — the voice-bindings file (§"Voices are decoupled from providers") — scoped to account-level voice→provider/model binding defaults (the top-level `[orchestrator]`/`[consultant]` tables plus the `[duties.<duty>]` tables) **plus account/billing posture** (`transport`, `budget`) and nothing else; a run's manifest may re-bind per run through flags or framing `bind.*` keys, which is workflow intent, not project knowledge. Spec paths, skill names, branch conventions, doc-update rules: still framing-turn territory, never config. If a key that isn't a voice binding or billing posture is about to land in the config file, that's the design failing. *(Two artifacts are the apparent exception that proves the rule — both customize the **tool**, neither is config and neither carries project knowledge. Framing templates (`.duet/templates/`, 2026-06-16) carry conventions across runs but are **pre-baked framing** — parsed and archived as the framing itself. Snippet override layers (a user `~/.config/duet/snippets.toml` and a project `.duet/snippets.toml`, 2026-06-25) replace individual snippet bodies per key, but they layer over duet's own shipped `snippets.toml` — the same kind of artifact, the tool's prompts, not the project's knowledge, which still enters only through the framing (mechanics + the at-your-own-cost guidance: README §"Customizing the snippets"). The heavier "project profile" that would auto-merge such pre-context is still shelved; see `docs/future-directions.md`.)*

(Removed from this list, by reversal: "Use an LLM as the routing judge" — see §"Design history".)

## Success criteria

1. **Planning:** a fully attended planning stage where the human's only keyboard touches are the framing, the gates, and `ask_human` answers — zero copy-paste routing.
2. **AFK:** a delivery stage the human leaves for 1–3 hours, returning to either a Ship-gate packet (CEO summary on top) or a well-formed queued question — never a silently stuck or runaway loop.
3. **Auditability:** for any routed turn, the orchestrator's transcript answers "why this snippet, why this adaptation" without asking anyone.

If duet achieves that on three features of varying size in the user's own projects, the design has earned further investment.
