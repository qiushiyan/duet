# Engineering notes — the codebase's mental model

How the implementation is shaped and why. Companion to `automation-design.md` (the system design: voices, phases, gates, policies). Read that before changing *behavior*; read this before moving *code*. Audience: an engineer — human or agent — touching `src/` for the first time.

## The trust gradient

One sentence holds the architecture: **deterministic code constrains an intelligent orchestrator, which commands two workers — trust flows one way.**

```
statechart (when)   →   tool handlers (what's allowed)   →   prompts (judgment)
hard guarantee          enforced rail                        steerable
```

Placement rule for any new rule: violating it would break the human's authority or the run's integrity → statechart or tool handler. Violating it would merely waste tokens or quality → prompt. The design history (automation-design §"Design history") is one long lesson about this line — the pre-pivot router put *judgment* in code (string-matching disagreements, caps as exit rules) and failed; the pivot moved judgment up into an LLM and moved *guarantees* down into structure. Never drift back: no code that parses worker prose for meaning, no prompt that is the only thing between an agent and a gate.

## Module map

The trust gradient grounded in code — and since the remodel, grounded in the directory tree itself: **the import direction is the trust gradient**. Each layer imports downward only (`view ← registry ← run ← voices ← orchestrator ← surfaces`, view being a leaf utility layer); the four remaining upward imports are erased type-only shape references (RunState's binding/usage/retry fields, colorize's `Voice`), and anything genuinely spanning `run/` + `voices/` composes on the voices side or in `surfaces/` (purge, doctor). Modules cluster by domain; each line names what the module owns and the one fact that bites, *italicized* where it's load-bearing. Deep per-module mechanics live in the source — this is the way in, not a catalogue.

**`registry/` — the pure domain model** (only registry-internal imports; nothing writes it)

- `src/registry/vocabulary.ts` — the **closed workflow vocabulary**: block/duty types, brief worlds, snippet attachment maps, and `validateRegistry` / `validatedWorkflowSpec`. It imports nothing and is the leaf both the SDK compiler and shipped registry read, so workflow compilation has no mutable install step or import-order requirement. *A workflow's documents are ordered* — the first doc-loop is the spec, later ones plans, enforced by `validateRegistry`. The doc-loop's one knob is `artifactKind`: the topology a renderer needs (is a document upstream, is this the handoff phase) is asked of the frozen phase list on demand, never stored on the phase, so a frozen workflow cannot contradict its own shape.
- `src/registry/define.ts` — the **workflow SDK compiler**: `defineWorkflow` plus the four block constructors (`frame`, `doc`, `build`, `finish`) and `compileWorkflow`. It is the deep module that derives stages, duties, edges, prose worlds, gate copy, caps, checkpoints, and default gate posture from the authored expression, then validates the compiled result through `vocabulary.ts`. *Derive from position, never from an artifact's name:* the compiler writes the hand-off-to-AFK gate hint for whichever block ends the stage (planning's last phase), and a knob check that needs topology (`contract`, doc order) lives here, where the phase list is visible; `doc()` sees one phase and cannot judge it. The same topology the renderers read later is asked of the frozen list, not baked into it — see `workflows.ts`. The public subpath `duet/workflows` re-exports this surface; no project gets a wider vocabulary than the shipped workflows exercise.
- `src/registry/workflows.ts` — the **workflow registry** (`WORKFLOWS`): the shipped standard library as four SDK expressions compiled through `define.ts`, plus the served lookup/resolver functions. *The single source for shipped workflows.* Per-phase snippet lists are **derived** from the knobs through `vocabulary.ts`; `validateRegistry` enforces the closed vocabulary at load — including stage topology, duty stage-uniqueness, edges running planning→delivery only, and the acceptance-contract chain. Phase identity is workflow-scoped — `phaseSpec(workflow, phase)` is the one per-phase lookup, no global `PHASE` map, and every topology/policy helper takes a workflow spec or name. The stage/duty resolvers everything reads live here: `stagesOf` / `stageOf` / `dutiesOf` / `makerDutyOf` / `checkerDutyOf` / `fixerDutyFor` / `continuityEdgeFor` / `handoffGateOf` — and beside the last, `isHandoffPhase` / `hasUpstreamDoc`, the doc-loop's topology asked of the frozen phase list rather than stored on it — plus `consultantCheckpointLive`, the one gateless gate *both* the orchestrator briefs and `list_snippets` read (and its render-facing sibling `consultantCheckpointView`, which folds the private checkpoint-kind map into `{ mode, kind, live }` for `duet graph`, mapping the internal `challenge` → `bet-audit` inside the registry so no surface re-encodes the taxonomy).

**`run/` — one run's truth** (persisted-state codecs and the statechart grammar; never imports `voices/`)

- `src/run/store.ts` — `.duet/runs/<id>/` persistence, atomic. *`state.json` is a HINT — the transcripts are truth.* Home of the terminal marker, the interactive lease/markers, the `gateAttended` / `highDecisionsAt` / `budgetFor` resolvers, the **stage.duty-keyed session records** (`sessions["delivery.builder"] = {provider, id}`, plus the consultant's checkpoint-scoped slot), and the additive **`grades` calibration ledger** (`upsertGrade`, absent ⇒ every surface byte-for-byte unchanged — the same shape as `autoApprovals`). `workflow` is materialized at creation, so past the load boundary it is always present. Pre-remodel state (seat-keyed `workerSessions`) and retired workflow names refuse to load with a manual-resume pointer — a typed rejection the listing surfaces *report* (`scanRuns`), so a post-upgrade `duet status` never reads as "no runs" while a corrupt dir still skips quietly. *Every mutation funnels through `mutate()`* (fresh-load → apply → save → re-apply to the caller's copy), so a CLI write can't clobber a live driver's concurrent saves.
- `src/run/workflow.ts` — the **frozen workflow resolver**: `workflowFor(state)` reads `.duet/runs/<id>/workflow.json` when present, validates it, and falls back to the shipped registry only for pre-feature runs. `createRun` writes every new run's compiled workflow there, shipped or external, so cross-process hydration never re-reads a source `.ts` workflow file. *A frozen workflow speaking a retired vocabulary is refused, never translated* — an `UnloadableRunError` naming the era and the way out, the same load-boundary discipline `store.ts` applies to pre-remodel state files (`docs/corpus-runbook.md` records which cohort that removes from the analysis surfaces).
- `src/run/machine.ts` — the statechart GRAMMAR, built per-workflow by `machineFor`. *A phase emits `phase.*`; a gate crosses only on `human.*`.* The machine ships with a **driver-less `phaseDriver` slot** (starting it bare throws → the phase's flag-wait): each host provides its actor through the `machine.provide` seam — `drivenMachineFor` (the in-process runPhase, `orchestrator/hosts/driver.ts`), `stdioPhaseMachine`, and the inert `interactiveMachineFor` the interactive host rests on. `PhaseInput` (the actor's input type) lives here.
- `src/run/phase-events.ts` — the `phase.*` / `human.*` vocabularies, and the one place the persisted marker is read back as an event.
- `src/run/position.ts` — the **position probe**: `probeRunPosition` / `RunPosition` / `aliveDriverPid` / `phaseLoopOf` / `describeStop`. Pure disk derivation (snapshots restored without starting an actor), read downward by the hosts and every surface.
- `src/run/steers.ts` — the human's mid-phase steer channel, its own module: file-per-steer staging under `steers/`, deliver-by-rename into `delivered/`. *Never `state.json`* (a CLI write there would race the live driver). `listPendingSteers` reads staging only (the live delivery path); `listStagedSteersForTrace` reads *both* dirs for the trace's history — so a delivered steer isn't lost — and validates each body's shape, dropping a malformed one rather than letting a bad timestamp surface downstream.
- `src/run/corpus.ts` — the **opt-in corpus sidecar**: fail-soft mirror primitives (append-through logs, whole-file copies, the quiescence `reconcileRecord`, the record's era stamp), hooked from the store's write helpers and the lifecycle's quiescent saves into the account-configured archive. *Never load-bearing:* every write swallows failure, absent `[corpus] dir` is byte-for-byte off, and a record is an analysis archive, not a backup (`docs/corpus-runbook.md`).

**`voices/` — execution: models actually speaking**

- `src/voices/bindings.ts` — the binding grammar and the **manifest freeze**: the one binding-spec parser (`parseBindAddress` / `parseBindingSpec` (`provider[:model][@effort]`) / `parseBindingTable`) validating against `PROVIDER_CAPS` — the per-provider capability table (model default-vs-defer, the effort enum, transport, the native-passthrough field) where the scattered `if (provider === 'codex')` rejections collapsed; the load-boundary guards; `resolveRunConfig` (per-key precedence flags > framing > config > shipped defaults, resolved once at `createRun`, frozen on state — a same-provider override carries a configured transport/native/effort forward); `degradedEdgesFor` (the provider-crossing edge degrade, decided at freeze, echoed and ledgered — model and effort are per-turn, so they never degrade an edge); and `voiceBindingFor(bindings, voice)` — the one "who runs this turn" resolver; no phase parameter, because a duty names its own stage.
- `src/voices/preflight.ts` — the create-time **binding preflight**: for each binding carrying an explicit model or a native override, one throwaway worker turn (through the `WorkerProvider` seam, headless even for an interactive binding), dispositioned by `preflightDisposition` — a positively-identified provider rejection (bad flag / unusable model) aborts `duet new`, while anything transient or ambiguous warns and proceeds (never block a healthy run; a miss degrades to first-use). *duet stays a conduit for native args* — it never parses them; the provider judges them, just early, so a bad binding fails at creation, not mid-build. The composition (loop the bindings, abort-or-echo into the `duet new` manifest echo) lives in the surface; the primitive is here.
- `src/voices/policy.ts` — the **voice-policy module**: lane-based policy as data (`policyFor` — makers write, checkers read-only, both persistent; the consultant ephemeral/read-only), the duty-keyed session helpers (`sessionKeyFor`, `liveContinuityEdgeFor`, `sessionRecordFor`, `sessionSlotsToReset`, `sessionIdFor` — the single resume-site read on both hosts, deriving fresh on a provider mismatch so a cross-provider resume is unrepresentable, and walking the live continuity edge so full's builder continues the architect's session while a degraded edge walks nothing), `writeAuthorityFor(state, phase, address, action)` — *action-scoped*, the lane policy beneath it, widened only by the fixer posture's grants and the checker-owned tails — the enumerations (`phaseAddressesFor` for protocol surfaces, `voicesFor` for display surfaces), and the **action catalog** (`ACTION_CATALOG`) — snippet-key behavior metadata as a *code map*, deliberately never TOML fields, because snippet-body overrides must not be able to change behavior. The "deletion test" module: drop it and per-duty checks regrow at N sites.
- `src/voices/sessions.ts` — locating provider transcripts by exact session id, the cheap session map (`resolveSessions`, stage.duty-keyed), and the run/ + voices/ compositions living on the voices side so `run/store` never imports upward: `purgeRun` (transcript + run-dir deletion) and `captureRunTranscripts` (the corpus's gzipped transcript capture — run at done/abandon, and at the top of purge, before deletion). *The one module reaching outside `.duet/`* — always an exact `<id>.jsonl` match, never a directory sweep.
- `src/voices/health.ts` — the **pure** health substrate (taxonomy, `probeRole`, `retryDecision`). *Imports no fs/clock/lifecycle — purity is load-bearing,* or a `status → health → lifecycle → status` cycle closes.
- `src/voices/activity.ts` — its pure sibling: the live-activity line from a transcript tail; liveness, not path-precision.
- `src/voices/context.ts` — the context-pressure substrate: the 75/85 bands, the transcript fill parser, the salvage-compact instructions. *Pure like `health.ts`* — no fs/clock; the tail read lives in `sessions.ts`, the wiring in `orchestrator/tools.ts` and the claude provider.
- `src/voices/providers/` — the worker seam: claude + codex adapters + factory, and the `WorkerProvider` contract (the resumable `WorkerTurn` vs the typed `BudgetCutoffError`). *Exactly two providers by design;* the claude provider's interactive TUI is a second *transport*, not a third provider. `createWorkers` builds the phase's stage duty pair (+ the consultant when bound), each duty's binding a frozen-manifest lookup resolved *before* the provider branch — so relay's codex builder and claude judge fall out per duty. `wall-clock.ts` hosts the Date-based deadlines.

**`orchestrator/` — judgment's cage: the kernel and its hosts**

- `src/orchestrator/tools.ts` — the host-neutral `KernelTool` registry and every protocol rail. *The deepest enforcement module: all rails here, no Agent SDK import.* `send_prompt(duty)` is host-switched — blocking headless, dispatch-and-collect (`check_turns`) interactive; its enum is the phase's live addresses (`phaseAddressesFor`).
- `src/orchestrator/briefs.ts` — the system prompt + per-phase entry/resume briefs + the steer block (governed by `prompting-and-tool-design.md`, incl. the single-world rule). *One block-dispatched renderer, no per-workflow composers:* `buildPhaseBrief` switches on the registry row's `semantics.block` into per-block renderers fed by per-world data records; briefs read the duty resolvers (`makerDutyOf`/`checkerDutyOf`/`fixerDutyFor`) and derive the doc-loop's topology on demand (`isHandoffPhase`/`hasUpstreamDoc`), never hardcoded duty or workflow names — a new workflow adds data entries, zero functions. The consultant's two doc-loop injections are two functions rather than one dispatch because they render at different anchors: the contract's prose says *"immediately before your advance_phase"* and rides the convergence step; the bet audit rides the advance step.
- `src/orchestrator/library.ts` — the served snippet library + the override layers (user/project merges over the shipped base) + `runtimeLibraryContext`.
- `src/orchestrator/hosts/host-runner.ts` — the **host-neutral phase run loop** (`runHostedPhase`) + the `PhaseHost` seam: the rails every host shares (entry replay, nudge-once, twice-ended, crash → flag + bounded auto-retry — default-on for new runs).
- `src/orchestrator/hosts/driver.ts` — the **in-process host**: one phase = one orchestrator SDK session (`streamTurn`), plus `drivenMachineFor` (the grammar provided with this host's runPhase actor). *`retryable: true` — the one headless place auto-retry runs.*
- `src/orchestrator/hosts/stdio-host.ts` + `mcp-server.ts` — the **out-of-process & interactive hosts**: the same kernel over stdio MCP (`duet _mcp`). The run-scoped server holds the single-writer lease (`mcp-owner.json`) and refuses once a run is no longer interactively hosted.
- `src/orchestrator/hosts/turn-dispatcher.ts` — the interactive host's pending-turn engine (dispatch → settle → collect). *Non-throwing / total:* a faulting turn flips to a collectible `failed`, never strands a duty `running`.
- `src/orchestrator/hosts/orchestrate.ts` — the `duet orchestrate` launcher (the run-scoped `_mcp`, the identity prompt, the one gate-safety `ask` rule) and the warm-start/reconnect resume (`--resume-session <id>`, persisted as `interactiveOrchestratorSessionId` — *deliberately distinct* from the headless driver's `orchestratorSessionId`).

**`surfaces/` — humans reading and typing**

- `src/surfaces/cli.ts` — command wiring only; parses under `import.meta.main`. Hides `_drive` and `_mcp`. *Genuinely thin:* the one command with real branching, `continue`, gathers facts and hands the decision to a pure planner.
- `src/surfaces/continue-planner.ts` — that planner: `(run state, restored facts) → ContinueAction`, no IO, exhaustively unit-tested.
- `src/surfaces/lifecycle.ts` — the process arm: the detached `_drive` spawn, `killDriver`, `driveToQuiescence` (*the only place machine actors run for real* — driving with `drivenMachineFor`), the `gates_at` auto-cross + spent-marker guard, the inline interactive crossings, `freezeContractAt`, `enterAfk`, and the notification wiring. A surface-level composer by design: it reads position, machine, driver, and notify downward.
- `src/surfaces/framing.ts` — the framing's journey (seed → editor → frontmatter parse, incl. the `bind.*` pre-pass); the machine/prose boundary rule lives here.
- `src/surfaces/workflow-source.ts` — external workflow resolution *and* the pre-run discovery seam, over **one** collision rule (`candidateLayersFor` — the ordered shipped/project/user candidate list, kept private). Read two ways: `resolveWorkflowSource` *loads* the chosen layer (one-time Node import of `.duet/workflows/*.ts` or `~/.config/duet/workflows/*.ts` via the `duet/workflows` resolve hook, then compile) and throws on collision/not-found; `discoverWorkflowSources` / `definedWorkflowSources` return the same layers as *data* — no import, no write — so `duet workflows` lists and `init` refuses-to-shadow without executing a definition. Loading splits over a shared no-provision core: `resolveWorkflowSource` provisions the workflow dir first (the editor scaffolding — `tsconfig.json` + version-stamped `duet-workflows.d.ts`), while `resolveWorkflowSourceReadOnly` skips it, so `duet graph --workflow` renders a blueprint that writes nothing (read-only-by-construction — two entry points, not a flag; compiling a project definition still *executes* its code on import, the irreducible boundary). The definition-file predicate excludes the generated `*.d.ts` stub across enumeration and lookup. Project files live under self-ignored `.duet/`; sharing carves `!/workflows/` into `.duet/.gitignore`, matching templates. Resolution feeds `createRun` a compiled value and never participates after the run is frozen.
- `src/surfaces/workflows.ts` — the `duet workflows` inspector: the display/JSON models and the list / check / init renderers over the loader + registry resolvers. *The bare list executes and writes nothing* (it reads the discovery seam above); `check` is the one compile boundary (`resolveWorkflowSource`, loader/compiler errors surfaced unwrapped), rendering its structural summary — plus the config-resolved default bindings and per-phase consultant checkpoints — over the *shared workflow-spine* (`graph-model.ts` below), the same projection `duet graph --workflow` draws, so the two never re-derive the pipeline independently; `init` scaffolds a minimal compiling starter, refusing any name that resolves in any layer. The `duet snippets`-shaped read surface for the workflow-definition layer.
- `src/surfaces/status.ts` — RunState + position → the status model and its renderers (text, `--json` verbatim, `--brief`). Pure; *the JSON schema is additive-only, pinned by test* (sessions keyed `stage.duty`, context entries per `voice`, pendingTurns per `duty`). The `duet graph` run view renders *over* this model rather than forking a second one.
- `src/surfaces/graph-model.ts` + `graph.ts` — the `duet graph` visualization surface. `graph-model.ts` owns the **workflow-spine**: `structuralSpine(CompiledWorkflow)` projects the pipeline (phases, gates, stages, duty pairs, caps, continuity edges) into one shape the blueprint view, the run view, and `workflows check` all compose over — delete it and each re-joins the raw resolvers by hand. Two overlays discriminate a `GraphModel`: `blueprint` (config-resolved default bindings + live consultant checkpoints, over `resolveWorkflowSourceReadOnly`) and `run` (live position + gate outcomes + rounds + state-derived drift, over the pinned `StatusModel` + raw state, with continuity degraded through the *frozen* bindings). `graph.ts` holds the renderers (ANSI pipeline / `--json` / `--mermaid`, blueprint-only; Mermaid ids are index-derived so a project phase name can't break the diagram). *Read-only throughout, and honesty-bounded: the run view renders a passed gate `crossed`/`auto-crossed` but never a claimed human `attended`, and an abandoned run marks a gate crossed only with sequential proof (a later phase started) — never from a merely-`phaseStarted` phase.*
- `src/surfaces/doctor.ts` — `duet doctor`'s composer (position + health + transcript tails + connectivity); cli-only, so composing across `run/` and `voices/` here closes no cycle.
- `src/surfaces/stats.ts` — `duet stats`'s effort model from the voice logs (the per-phase **maker model** column resolved from the frozen manifest); the log-reading sibling of `doctor`, fail-soft. *Its parse core is the exported pure log-parsing primitives* (turns, windows, interval unions, gaps, heartbeats) that `scripts/corpus/` and `duet stats --trace` both compose — log-format knowledge lives once, here, pinned by tests. `--trace` adds the interleaved per-phase timeline (`buildTraceModel`) over those same cores — no graph-owned regexes: the still-running phase's open window is synthesized (real start for a headless phase, inferred for interactive, closed at an injected `now`), interventions overlay at their timestamps, and a narrow ordering-drift heuristic (a checker review with no maker turn between) flags the bug that once needed a hand-read transcript. Also hosts the optional **grades section** over the decision-point core (coverage + confusion-matrix counts + precision), populated only when the `grades` ledger exists so an ungraded run renders byte-for-byte as before.
- `src/surfaces/decision-points.ts` — the **decision-point discovery core**: `decisionPoints(state, log)` reconstructs a finished run's whole human-stop history — auto-crossed / held-high / attended gates and queued questions — from the state ledgers first and `orchestrator.log` only where state is silent (question text, per-round packets, the answer), returning the points *and* its degradation notes so a missing log never silently shrinks coverage. Pure; *one point per gate* (a held-then-crossed gate stays one `held-high` point, never a second `attended`) and *reuses stats.ts's timestamp anchor with its own body-aware block parser* (it needs prompt bodies, not just windows). The single core `duet grade`, the stats grades section, and `grade-precision.ts` share — `gradeMatrix` derives the confusion-matrix from `(polarity, verdict)` — the deletion test the corpus runbook prescribes.
- `src/surfaces/grade.ts` — `duet grade`, the end-of-run calibration ritual over that core: resolve the run, *refuse the verdict write while a live driver owns `state.json`* (`--list` still reads), then the interactive walkthrough — each point presented with its context and a polarity-phrased verdict ("was stopping here right?" / "should this have stopped you?") — or the non-TTY `--set` / `--note` / `--missed` path, upserting the `grades` ledger by structural key. *Coverage notes ride every path, never only `--list`*, so no path presents a shrunken point set as complete.
- `src/surfaces/framings.ts` — `duet framings`: the framings browser over the corpus archive merged with the local `.duet/runs` scan (deduped by runId, corpus copy wins), scoped to the current repo by the `RunState.repo` identity stamp — derived fail-soft at `createRun` by `run/repo.ts` (primary-checkout root + origin remote), *the durable group key once a worktree cwd is a dead path*; unstamped records fall back to cwd equality. Read-only and fail-soft like `stats` (an absent corpus degrades to the local list with a note); `show` prints the archived framing verbatim.
- `src/surfaces/view/tmux.ts` — the stage-aware tmux viewer: panes are the orchestrator + the *current stage's* duty logs (+ consultant when bound), derived from the registry enumeration.

**`view/` — leaf view utilities** (importable from any layer; no local value imports)

- `src/view/colorize.ts`, `src/view/timefmt.ts`, `src/view/notify.ts` — the palette/glyph tables (`VOICE_GLYPH`, one hue per lane), local-time helpers, and desktop notify. Below the gradient because the in-process driver colorizes its own console stream at view time.

**Evidence & shipped prompts**

- `skills/` — the shipped skills (duet-concierge, duet-frame with its worked manifest and workflow-definition examples); zero runtime, coherence-guarded by `tests/skill.test.ts`.
- `src/spike/` — the substrate spike, the SDK pause/resume repros, and the context-accuracy probe (re-run on a CLI upgrade); executable evidence, not tests — do not modernize.
- `scripts/corpus/` — dev-only corpus analytics (the backfill and the timing/waste tools): thin composers over the tested cores above, never their own parsers (the rotted `.duet/telemetry` lesson); recipes in `docs/corpus-runbook.md`. Never shipped in the package.

## Seams

A seam = a place behavior swaps without editing code in place. The deliberate ones — tests fake **only** at these:

| Seam | Adapters | Why |
|---|---|---|
| `WorkerProvider` (`voices/providers/types.ts`) | claude, codex, tests' `FakeWorker` | Duty–provider decoupling (design) doubles as worker scripting (tests) |
| `RunOrchestratorTurn` (`orchestrator/hosts/driver.ts`) | Agent SDK, scripted sessions | The in-process SDK boundary; a fake session receives the real tool handlers and may invoke them |
| `Orchestrate` (`orchestrator/hosts/stdio-host.ts`) | scripted client (tests), interactive CC session | The out-of-process sibling of `RunOrchestratorTurn` — drives the kernel over a real stdio MCP boundary; the seam the interactive orchestrator runs through |
| `phaseDriver` actor (`run/machine.ts`) | `drivenMachineFor` (runPhase), `runPhaseOverStdio`, inert (`interactiveMachine`), `machine.provide` scripts | XState's own substitution mechanism — and since the remodel the grammar ships driver-less, so EVERY host provides its actor here; the lifecycle is reused unchanged |
| `PhaseHost` (`orchestrator/hosts/host-runner.ts`) | in-process driver (`makeInProcessHost`), stdio host (`makeStdioHost`), tests' scripted host | One level *under* the two real `phaseDriver` adapters: the shared phase run loop (`runHostedPhase`) drives a `PhaseHost` whose only variation is how a turn is driven, how a failure is classified, and whether it retries — so the rails are tested with a 5-line fake session, not a full SDK or a real `_mcp` subprocess |
| Environment (`$EDITOR`, config path, notify fn, `ClaudeLauncher`, `isTTY`, connectivity `fetch`, transcript `home`) | real / stubbed / recording | OS boundaries — incl. the `duet orchestrate` process spawn (`orchestrate.ts`, a recording launcher in tests), the non-TTY write path, and the doctor connectivity / transcript reads |
| `PaneController` (`voices/providers/pane.ts`) | `TmuxPane`, tests' `FakePane`, owned-pty (later) | The injection/process sub-seam *inside* the interactive claude transport — keeps the transcript parser transport-independent so owned-pty swaps in unchanged (`interactive-transport.md`) |

Rule: a new abstraction earns a seam only when a second adapter exists or a test needs one (`PaneController` earned both — a test now, pty later). Otherwise call directly — pass-through layers get deleted on sight.

## Patterns that carry the design

- **Workflow registry and compiler.** Adding or tuning a shipped phase starts as an SDK expression in `registry/workflows.ts`; `registry/define.ts` derives the explicit registry shape. Adding a workflow is still data, not statechart code: one `defineWorkflow` expression plus any missing snippets/prose worlds, with validation rejecting combinations duet cannot brief. A `Record<PhaseName, …>` appearing anywhere else means the field belongs in the compiled workflow. The phase `semantics` sub-object remains the compile target: renderers, snippet derivation, write authority, and tail routing all read the knobs — a behavior conditioned on a workflow *name* instead of a knob is the drift to refuse.
- **Single-world rendering.** Prompt text never branches on configuration: the renderer selects a dedicated fragment per knob value (`buildPhaseBrief`'s block dispatch; the workflow-scoped judge clause appended to the system prompt), and no rendered prose says "if the posture is…". The test-side enforcement is the **parity harness** (`tests/parity/`): file-snapshot pins for every brief/system-prompt/snippet-list/machine-shape across the run-state matrix, held byte-identical through refactors — a red pin means behavior changed, and wording improvements are deferred, never folded into a refactor.
- **Workflow-scoped phase identity.** A phase is identified by `(workflow, name)`, not a global name — so every workflow names its build phase `implement` and its finish phase `finish`, and their specs still differ per workflow. `phaseSpec(workflow, phase)` is the one per-phase lookup; there is no global `PHASE[name]` map (a shared name would collapse it to one arbitrary entry), and `validateRegistry` enforces uniqueness *within* a workflow. The run-state maps stay `Record<PhaseName, …>` — a run lives on one workflow and only ever keys its own phases, so the shared-name union is unambiguous per run. Every topology/policy helper takes the workflow (`machineFor(workflow)`, `phasesOf`, `phaseOfGateState`, `stageOf`, the consultant cluster); a phase accepted from outside (`_mcp`) is validated against the run's workflow. The mistake to avoid: a bare-name lookup that assumes global uniqueness (the pre-refactor `PHASE[name]` / `workflowOfPhase`).
- **Voice policy as lane data; address vs voice.** A voice's asymmetries live once in `voices/policy.ts`, keyed on the LANE (makers write, checkers read-only) plus the consultant's ephemerality — never as per-duty checks sprinkled across the hosts (the deletion test: drop the table and the conditionals re-grow at N sites). Run-aware policy goes through the resolvers, not around them: every harness path that mutates correctness state asks `writeAuthorityFor` (the `verifiedAt`-staleness key in `settleTurn`, the `readOnly` turn hint), so relay's writing judge stales a verification exactly like the builder — the static lane policy alone would leave a stale verification certifying pre-fix code. Behavior keyed on a snippet tag reads the action catalog, never the tag's spelling (`countsReviewRound` is catalog membership, not a `review-` prefix). The split that threads every enumeration surface: **protocol addresses** (the phase's stage duty pair + the bound consultant — `phaseAddressesFor`) drive routing, the send-prompt enum, branch-fixing, orphan recovery; **voices** (`voicesFor` = orchestrator + every stage's duties + consultant) drive display/log/health, which must keep the orchestrator an address-routing surface would drop. Picking the wrong one is a silent bug — a voice surface routed through `phaseAddressesFor` loses the orchestrator; a protocol surface through `voicesFor` tries to prompt it. And the optional consultant is **default-off byte-for-byte**: absent its binding, every surface (config, tool schema, the snippet library, the phase briefs) reads exactly as before — the run-facing guarantee, tested at the tool altitude, not just the helper's.
- **Rails as named, ordered tool results.** Every rail is a small named function `(input, ctx) → refusal | null` that *refuses with steering text*: template-economy warn-once-then-allow, review-round backstop caps, branch-fixed-after-first-prompt, the phase-exit gate, the contract/verify checkpoints. A handler composes its rails with `firstRefusal` (first to refuse wins), and the **order is load-bearing** — the same-address-in-flight check precedes orphan-recovery, so a live turn refuses before the recovery seam fires its one side effect. A rail isn't real until its result text tells the orchestrator what to do instead (prompting doc, convention 5). Two supports keep them clean. (1) Result-envelope **builders** (`block` / `ok` / `error` / `refuse`) collapse the repeated `CallToolResult` shapes onto one taxonomy and make a text-less refusal a *compile* error — keeping a rail's `refuse` typed apart from a worker/tool `error`. (2) Two **boolean host oracles** on the rail context, `inFlight(address)` and `orphanedOnDisk(address)`, are the single place the blocking-vs-async host divergence lives, so a rail reads one registry and never branches on host. The invariant the oracles must preserve: the **phase-exit gate is async-host-only** — on the blocking host a `send_prompt` runs to completion before any terminal call, so no uncollected turn can exist, and the gate must not let the in-memory in-flight set (which the same-role guard legitimately reads there) strand a phase exit.
- **Host-neutral kernel, three hosts.** The tool surface is one `KernelTool` registry (`tools.ts`), independent of any SDK; thin adapters host it — the in-process Agent SDK server (`driver.ts`'s `toSdkTools`), the standard single-phase stdio MCP server (`mcp-server.ts`, reached via `duet _mcp <runId> <phase>`), and the run-scoped phase-less server the interactive orchestrator connects to (`duet _mcp <runId>`). The same handlers, rails, and steer delivery serve all, so an out-of-process orchestrator behaves identically to the in-process one — proven by a parity test driving a real `_mcp` subprocess. The single dependency this added, `@modelcontextprotocol/sdk`, is pinned to the one version the Agent SDK already resolves, so every host shares one `CallToolResult` type.
- **Host-neutral run loop, two phase hosts.** A second host axis, distinct from the tool kernel above: the *phase run loop* (`runHostedPhase`, `host-runner.ts`) owns the four rails every host shares — entry marker-replay, nudge-once, the twice-ended flag (a second turn-end with no advance or question ⇒ the run is stuck), crash → flag + bounded auto-retry (default-on for new runs) — behind the small `PhaseHost` seam. Its two adapters are the `phaseDriver` actor's two real implementations: the in-process Agent SDK driver (`driver.ts`, `makeInProcessHost`) and the stdio MCP host (`stdio-host.ts`, `makeStdioHost`); each supplies only what legitimately differs — how a turn is driven (`HostedSession.driveTurn`), how a failure is classified (`classifyFailure`), whether it retries (`retryable`). The interactive run-scoped server is *not* a third here — its loop is the turn-dispatcher and the machine rests inert. The drift this collapsed: the stdio host had silently diverged to a cheaper crash classification and its own copy of the twice-ended / crash-flag wording — lesson #8 (one shared rule, not one per surface) applied to the host rails.
- **Interactive orchestrator host.** The human's own CC session is an orchestrator host over the planning stage, up to the workflow's handoff gate (full: through PLAN; blueprint/relay: through DESIGN; short: through Direction). Its server is *run-scoped*, not phase-scoped: a long-lived session can't keep swapping a static phase arg, so it resolves the live phase from disk per call and refuses once the run is no longer interactively hosted (`orchestrationHost`), closing the two-writer gap against a handed-off headless driver. The **rails-only cache** is the load-bearing tactic: the tool surface is rebuilt per call against *fresh* disk state — so a cross-process `duet continue` (a same-phase reject/answer) is seen immediately, not served stale — while only the per-phase rails (the same-address in-flight guard, the warn-once set) and providers are cached and rebuilt at a phase boundary. The machine rests inert (`interactiveMachine`): a non-quiescent phase-loop snapshot is a legitimate rest, and `crossInteractive` advances it inline (consume the marker's `phase.*` to reach the gate/flag, *then* apply `human.*` — a phase loop ignores `human.*`, only the gate/flag takes it) with no `_drive` until the handoff gate. Gate safety is structural as everywhere (`get_task`/`advance_phase` only park), plus one `ask` rule on `duet continue` that survives the human's bypass-permissions default — the colon form `Bash(duet continue:*)`, matching the concierge's read-verb rules.
- **Fire-and-collect worker turns (interactive host).** A CC assistant turn can't yield while a `tool_use` is outstanding, so a blocking `send_prompt` would freeze the session for the minutes a worker runs. On the interactive host an `async` dep flips `send_prompt` from blocking to *dispatch-and-return* and exposes `check_turns` to collect later — a host switch in the one registry, not a fork (the headless driver keeps the blocking path and never leaves a turn in flight). The `turn-dispatcher.ts` engine owns the pending-turn lifecycle (`dispatch` → settle → `collectReady`), running the *same* settle/render/heartbeat steps a blocking call does, spread across time; it reads fresh disk state at each step because it outlives the dispatching call. Three invariants carry it: (1) a **single-writer lease** (`mcp-owner.json`) fenced at two boundaries — `toolsFor`'s synchronous gate covers every dispatch-time write, the background settle keeps its own non-throwing lease check — so a superseded server's late settle writes nothing; (2) the background lifecycle is **non-throwing / total** on every exit: a faulting setup, launch, or settle flips the duty to a collectible `failed` rather than stranding it `running` (which would hang `check_turns` / `status --wait` forever under AFK), and the heartbeat is always stopped; (3) a turn orphaned by a session quit is a **durable record with no live owner** — detected on disk, never from a transcript guess — which refuses a same-duty resend and blocks phase-exit until `duet takeover` clears it. The slice ordering is load-bearing: the lease lands before the async writer, and the orphan invariant holds on disk from the writer's first commit, so every committed tree is self-safe under AFK. Test-verified and live-verified — the interactive host is the daily driver for planning stages (observed: daily use, 2026-07).
- **AFK resilience — native-vs-own, two recovery planes.** The seams that keep the overnight window honest (the design + the verified Claude facts live in `docs/automation-design.md` §"Resilience for the AFK window" — single source of truth; this names where each seam is). The native stall-watchdog rides an env knob injected at all three Claude connections (`claudeExecaOptions`, `buildOrchestratorOptions`, the extracted `claudePaneLaunchCommand`) — Claude-only, never codex. The owned wall-clock backstop is `runWithWallClockDeadline` (`providers/wall-clock.ts`, Date-based, injectable `now`/`schedule`), wrapping both providers' run loops; the per-turn cap rides the `RunTurnOptions.timeoutMs` contract every provider honors. The honest accepted-abort split lives at the provider failure seam (`recoverClaudeFailure` + the pure `transcriptShowsPromptAccepted`; codex's `recoverCodexAbort` keyed on a `thread.started`-seen flag, never `onSessionId`) and settles through `settleTurn`'s `aborted` branch (no round, no consultant marker) — render stays presentational. The two planes diverge by *what fails*: a worker turn → orchestrator-routed via the result text; the orchestrator's own session → the mechanical `retryDecision` plane (`--retry-infra` governs, headless-only). The lifecycle owns caffeinate + the quiescence soft-fail (`lifecycle.ts`); the `/compact` reset rides the shared `settleTurn` path.
- **Context pressure — one scope gate, a high-water reading.** The design is `automation-design.md` §"Resilience for the AFK window"; the shape that bites when moving code: `contextPressureApplies` (`orchestrator/tools.ts`) is the **one** scope predicate every consumer shares — the turn's context cap, the send-side rail, the footer's band marker — so the claude-persistent-headless scope can't drift per surface. It answers per ADDRESS off the duty's own frozen binding — a duty names its stage, so no phase parameter exists (relay's claude judge is metered; its codex builder is not). Guards read the **high-water** fill since the last compact (`contextSafetyPercent`), never the display percent: an error turn can't lower the safety reading, a completed compact or session reset **clears** it rather than recording it (a compact turn's own usage measures the summarization request — the very size just removed), and a window change restarts the mark. `voices/providers/wall-clock.ts` hosts both deadlines over one shared abort-once-then-drain race (`raceCut`); the context deadline samples the transcript tail, and an undefined sample never cuts. In the rail order, context pressure sits after orphan-recovery and before the review cap; a `/compact` is detected from the literal body, never the tag, and is the one send the emergency band lets through. The salvage ladder is blocking-host-only (the auto-retry human-present split), and every intervention is ledgered (`contextEvents`) through the same `settleTurn` path.
- **Cooperative pause.** `ask_human` persists the question at call time, the result text says "end your turn", the process exits at quiescence. Mechanical SDK interrupts corrupt resume — proven, with executable repros (`src/spike/repro-*.ts`).
- **Parallel worker turns.** The claude CLI runs MCP tools serially unless `annotations.readOnlyHint` is true (its scheduler's concurrency test for MCP tools — verified 2.1.175, undocumented; full note: `docs/prompting-and-tool-design.md` §Concurrency). `send_prompt` carries the annotation as a concurrency hint, not a purity claim, so independent turns to different workers overlap; the genuinely unsafe case — two concurrent turns into one session — is refused by the handler's same-address in-flight rail. If parallel sends stop overlapping after a CLI upgrade, re-verify that mapping first.
- **Staging handshake.** Human input crosses the CLI→driver process boundary via `stageHumanInput`/`consumeHumanInput`, consumed exactly once so a retried driver can't replay an answer. Known edge, chosen deliberately: a crash after consume loses the staged text — the crash question asks the human to re-supply, which beats risking double-delivery into a session that may have already used it.
- **Steer channel.** The human's mid-phase voice rides tool results: file-per-steer staging under `steers/` (never `state.json` — a CLI write would race a live driver's saves), delivery appended to every phase-continuing result, carry-forward through the next harness prompt otherwise. The crash trade inverts the staging handshake's: deliver-then-consume, so a crash *redelivers* rather than loses (a repeated instruction is benign where a lost one is not). Turn-ending results (advance recorded, question queued) never carry steers — guidance delivered into a dying turn lands and dies — and the delivery path is fail-soft: a steer bug must never corrupt a tool result.
- **Position probe.** Where a run is cannot be read from the snapshot alone — for a pure-headless run persistence is quiescence-only, so mid-phase the snapshot shows the *previous* stop. `probeRunPosition` joins driver liveness, the parked snapshot, and the state evidence the driver writes continuously (`phaseStarted`, `pendingQuestion`) into running / gate / flag / crashed / abandoned / done; a crashed position names how its dead crossing is re-uttered (`approve` / `answer`), so bare `duet continue` recovers every crash shape. The one non-quiescent snapshot a headless probe meets is a leftover **phase loop** (e.g. `implementLoop`) after an interactive→headless handoff — `crossInteractive` rests the machine at the next phase's loop, then `orchestrationHost` is cleared — so the headless branch maps a `<phase>Loop` value to that phase (a live driver → `running` there, a dead one → a mid-phase `crashed` resumed from the loop snapshot); without it a handed-off mid-implement run misreported against the entry-phase fallback. The `abandoned` short-circuit comes first: `duet abandon` kills the driver and writes a marker, so a deliberate stop reads as abandoned rather than crashed — and stays reversible, since `continue` clears the marker and the transcripts are kept. Steer gating, crash recovery, and the status model all derive from this one probe.
- **Crash = flag.** Any infrastructure failure lands the run on an actionable queued question, never a silent state; a question the orchestrator already queued is never overwritten by a crash question. The stdio host shares this across the process boundary: a dead `_mcp` peer becomes the same persisted question, so crash = flag survives the boundary, and a silent turn gets one nudge before flagging. Parity is structural, not duplicated — the nudge-once, twice-ended, and crash-flag rails live once in the shared run loop (`host-runner.ts`), so both hosts emit the one wording.
- **Infra classification & bounded auto-retry (default-on for new runs).** One pure rule decides "is this run broken right now": `currentTerminalError` — a classified terminal error that is recent *and* not superseded by later activity — shared by the `crashed` verdict and the driver's infra classification so the two can't drift. The retry *policy* (`retryDecision`) is consulted in one place — the shared run loop's catch — but gated on the host's `retryable` posture, which only the in-process driver sets; the classification *taxonomy* reaches both hosts as their `classifyFailure` capability (the in-process driver's staleness-aware `classifyInfraError`, the stdio host's bare `classifyError` — it does not retry, so it needs no transcript refinement). Only the retryable headless path acts on a class (a human is present on the interactive host, so it classifies and hands back). Default 3 for a new run (materialized at `createRun`, an old/absent budget off byte-for-byte); transient classes back off and retry, `auth` retries once then escalates as `login-required`, the rest flag; exhaustion always flags.
- **Opt-in rails, safe defaults.** Run-policy resolvers read run state against the frozen compiled workflow and fall back to legacy behavior when the knob is absent: `gateAttended` (absent `gatesAt` ⇒ attend all; an empty `gatesAt: []` is attend-*none*, distinct from absent) and `budgetFor` (absent `budget` ⇒ no caps; off ≡ absent, never `0`). Bindings follow the same freeze discipline: every voice resolves per key once at `createRun` and is frozen. The workflow structure itself now joins that pattern: `createRun` writes `workflow.json`, so later processes resolve through `workflowFor(state)` and cannot be affected by source-file edits or registry retunes. The **gateless** posture (`state.gateless`, absent ⇒ off byte-for-byte) rides the same shape over two axes: it materializes `gatesAt: []` and narrows the consultant by *kind* through the `consultantCheckpointLive` predicate — dropping only the holding bet-audit `challenge`, keeping the non-holding `generative` frame and the `backstop` — changing *what produces holds*, not the severity-hold mechanism, which is untouched (the lone exception is `enterAfk`'s one backstop-preserving refusal). And a rail that can *stop* a run degrades to a resumable checkpoint, never an error: a budget cutoff is a settled `budgetTruncated` turn or a typed `BudgetCutoffError` (worker), or a `cause: 'budget'` flag (orchestrator), each with a resume path and none routed to infra-retry.
- **Phase decision via a persisted marker.** `advance_phase`/`ask_human` record a terminal marker `{phase, kind}` written atomically with the gate packet or queued question it carries — the one cross-process channel for "which `phase.*` event to emit," read back through the pure, phase-matched `markerToEvent` (`phase-events.ts`) by both hosts. The lifecycle clears it deliver-before-clear (after the quiescent snapshot is durable, before any `gates_at` auto-cross). The subtlety that bit: the marker survives the crash window between the snapshot save and the clear, and a same-phase re-entry is *not* inherently harmless — a stale `flag` re-entered by an answer, or a stale `advance` by a reject, would replay the old decision and swallow the human's input. The **spent-marker guard** closes it: on entry the lifecycle reads the *restored snapshot* and clears the marker iff it resumed at that marker-phase's own gate/flag-wait (the transition already applied); a crash *before* the transition restores at a prior state, so the live marker still replays as intended. The same marker is honored in the driver's failure **catch**, before any classify/retry/flag: a terminal marker written just before a post-`advance_phase`/`ask_human` stream throw is this turn's real decision (markers are phase-scoped), so honoring it there strengthens first-terminal-wins instead of letting a late infra error overwrite a recorded decision.
- **View-time color.** Log files are plain text always, and the stored timestamp is always raw UTC ISO — they are the inspectable-without-duet artifacts (so is `status --json`); only the *view* localizes. One palette (`colorize.ts`), applied only where a human is watching. The `⏳` heartbeat / `⋯` activity / `✗` error markers are a producer→colorizer contract: the producer writes the leading marker into the plain-text line, the colorizer keys on it. The `⏳` heartbeat and `✗` error are styled in place (dim, red); the `⋯` activity line is **promoted** to `[read|edit|search|run] <subject> <HH:MM>` — action tag in the voice's color, subject secondary, the action's local time dimmed (deliberately louder than the content-free heartbeat). Header stamps render a local clock; the activity line trails the action's wall-clock time rather than a relative age, since a line is colorized once as it streams (a relative age would read ~0 and freeze). `timefmt.ts` holds the pure local-time helpers; the human-text renderers in `status.ts`/`doctor.ts` localize too, while `--json` stays UTC.
- **Atomic writes** (temp + rename) for everything crash recovery reads: `state.json`, `machine.json`.

## XState usage

The machine is deliberately small; the discipline is in what it refuses to represent:

- **Two event vocabularies, kept disjoint.** A phase state completes by emitting an internal `phase.advance`/`phase.flag`; a gate or flag-wait transitions only on a `human.*` authority event (approve, reject, answer). A gate has no `phase.*` handler and a phase state has no `human.*` handler, so `advance_phase` can *park* a run at a gate but can never *cross* it — that's a property of the vocabulary, not a prompt. No tool emits `human.*`, in-process or over the MCP boundary, so gate-skipping stays *unrepresentable* even for an out-of-process orchestrator.
- **Tags are API, not decoration.** `quiescent` = the lifecycle may persist a snapshot here (no live actors); `gate` / `flag-wait` / `phase` drive CLI copy and event validation. The tag sets are pinned exactly by tests (`tests/machine.test.ts` coherence suite) because a mis-tagged state would persist a snapshot that restore cannot resume.
- **Persist only at quiescence; restore never resumes an invoke.** Mid-phase crash recovery re-enters the phase loop; position truth is the JSONL transcripts. `state.json.machineState` is display-only — reconstructing machine state from it is the anti-pattern, and the spent-marker guard (below) keys off the *restored snapshot* (`machine.json`), never that mirror, for exactly this reason.
- **The snapshot is typed at the store boundary** (`Snapshot<unknown>` in `run-store.ts`), so hydration is `createActor(machine, { snapshot })` with no casts anywhere.
- **Context is input, not state** (`runId`, `cwd`, `hasSpec`). Anything that changes during a run lives on disk, owned by the run store.
- **`snapshot.can(event)` before side effects** — the CLI validates a gate decision against the restored machine before staging input, so a wrong flag errors instead of silently no-oping.
- **Test through `machine.provide`** — script the actor, never reach into machine internals.

## Testing strategy

Standalone `tests/`, not co-located: the test surface is the public interface, and the interfaces here span process boundaries — co-located files invite testing internals. Fixtures compose via `test.extend` (`tests/helpers/fixtures.ts`: tmp project dir → run on disk → fake workers, one run fixture per shipped workflow ± consultant); the scripted statechart lives in `tests/helpers/scripted-machine.ts` (including `restInteractiveAt`, the lightweight way to park a snapshot at any gate/flag/loop/done without running a phase driver), and the replay suite's scaffolding in `tests/helpers/replay.ts`.

**The bar is the vendored methodology** — `lessons/testing/` (`test-quality.md` for what earns a place in the suite: the five low-quality shapes, tokens-and-relations over byte pins, the mutation check, deleting safely; `tdd-loop.md` and `mocking-and-fixtures.md` for the discipline beneath it). Read it before writing or removing tests; duet's own builders are handed the same files by the PLAN and build snippets. This section carries only what is *duet-specific*: the seams, who owns which behavior, and the contract suites.

- Behavior through real interfaces: tool handlers, store functions, machine events, rendered strings.
- Fake only at the seams table above. Filesystem and git run real, in tmpdirs. Time via fake timers (heartbeats only).
- Never mock our own modules; when tempted, write a third adapter for the seam instead.
- Deliberately untested: the tmux viewer and notify glue (their designed failure mode is already "degrade to a one-line note"), the thin codex SDK wrapper, and the `scripts/corpus/` composers (their logic lives in the tested pure cores they call). The view layer's two real parsers are tested oracles, not glue: colorize's activity-line promotion, and `timefmt`'s localization — the sole independent oracle, since the render suites use `localStamp()` as their own expected value.
- **Prose discipline:** byte-level prose pins live in `tests/parity/` (model-facing surfaces) or an explicit schema/contract pin (`status --json`, the skill↔CLI coherence scans, the health taxonomy's error-string table, a refusal's named next command). Everywhere else a test asserts structural tokens and relational claims — presence/absence flips, `toBe` between two renders (gateless ≡ attended), snippet-key and path tokens, `indexOf` ordering — never full sentences, so a pure wording improvement moves pins deliberately and breaks nothing else. *Relational claims are what parity cannot state* ("unbound IS the base constant", "this knob leaves that surface byte-identical"), which is why they stay in the behavior suites rather than migrating to pins.
- **Wiring guards are mutation-checked.** A test that claims a wrap exists — `runWithWallClockDeadline` and `runWithContextDeadline` around each provider's run loop — must be proven to fail when the wrap is deleted (delete it, watch it go red, restore). Both carry a comment naming the production line whose removal turns them red; a wiring guard without that sentence is decorative, since the suite passes without the code it "guards". Write them to fail on the observable side effect (the child was killed, the ledger has the entry), never on a promise merely settling.

### One owner per behavior

The anti-echo map: adding a test starts by finding the behavior's owner here and asserting your *delta* there — never a second proof in a second file. A behavior with two owners fails twice for one production change and drifts when only one is updated (the pre-consolidation state: host rails proven in three files, the decision-point core in three, workflow-compile pins in three).

| Behavior | Owner | Everyone else may assert |
|---|---|---|
| Shared host run loop (entry replay, nudge-once, twice-ended, crash→flag + retry) | `host-runner.test.ts` | driver/stdio: a wiring smoke, plus their own SDK/transport specifics |
| Statechart grammar (gate/flag no-ops, event vocabularies, tags) | `machine.test.ts` | — |
| Position verdicts (running/gate/flag/crashed/interactive/done) | `position.test.ts` | `continue-planner.test.ts` owns the *decision* over a position |
| Tool handlers + rails | `tools.test.ts` (handler altitude) | the rails describe holds only handler-*unreachable* cases: composition order, host-split gates, side-effect discipline |
| Model-facing prose bytes | `tests/parity/` | behavior suites: tokens + relations only |
| Decision discovery + confusion matrix | `decision-points.test.ts` | `grade`/`stats`: that they *wire* it (points presented, section renders) |
| Health taxonomy + per-voice verdicts | `worker-health.test.ts` | `doctor`: composition and the rendered row |
| Binding grammar + manifest freeze | `config.test.ts` | `framing`: only that `bind.*` keys peel onto `meta.binds` |
| Workflow compile / illegal composition | `workflow-source.test.ts` (loader) + `skill.test.ts` (executable fences: relay, full) | `workflows.test.ts`: the CLI framing, and the blueprint/short rebuild pins no fence covers |
| Graph structure (phases, duties, posture, edges) | `graph-model.test.ts` | `graph`/`graph-run`: `--json` schema, Mermaid id-safety, one render smoke |
| Status model + `--json` schema (every stop kind) | `status.test.ts` | — |
| Snippet library + override layers | `snippets.test.ts` | — |
| Log-parsing cores (turns, windows, gaps) | `stats.test.ts` | `trace`/`scripts/corpus/`: compose them, never re-parse |
| Per-provider turn mechanics | `claude-provider` / `codex-provider` / `interactive-claude` / `provider-factory` | `wall-clock.test.ts` owns the deadline guards themselves |

Two corollaries worth stating, both learned the expensive way. **A deletion that turns something red is a finding, not a rebase conflict** — the coverage was load-bearing and misfiled; move it. And **an audit's redundancy list is a hypothesis**: name the twin test and check its *branches* before deleting, because roughly a fifth of any such list dissolves under that check (in the 2026-07 consolidation: the lifecycle continue-predicates owned four branches no planner test covered; `create_branch` already asserted real git state).

### The contract suites

- `tests/snippets.test.ts` guards the hand-edited snippet library (the block-named `snippets/` files, loaded in an explicit order with duplicate keys failing loud) — every snippet key the orchestrator prompts name, every action-catalog key against the library (a behavior-bearing key can't silently drop out), plus that the `{{lessons_dir}}` references resolve to a shipped vendored file and no personal path leaks back in — so a broken library or a missed re-vendor fails a five-second test, not a $90 run. The same suite owns the override-layer contract: `snippets.ts` serves the *effective* library — the shipped base with optional user (`~/.config/duet/snippets.toml`) and project (`<cwd>/.duet/snippets.toml`) overrides merged over it (pure `mergeSnippetLayers`: per-key whole-body, fail-closed on an unknown key, byte-identical when no override file is present; `runtimeLibraryContext` is the one OS-home read, isolated across the suite via a `$HOME` setup file so no test picks up the developer's own override).
- `tests/parity/` is the **pin harness**: every prompt surface a model reads — phase briefs, the system prompt and its variants, effective snippet lists, served library renders, machine shapes — snapshot-pinned across a deterministic run-state matrix (consultant on/off, gateless, contract states, provider splits, gate postures). The bar is byte-identical, stricter than green: a refactor commit must not move a pin; a feature commit adds pins or changes them deliberately, never incidentally.
- `tests/skill.test.ts` guards the shipped skills the same way: every duet verb and flag a skill names must exist on the imported command table, and read verbs must be the only pre-approvals — a renamed flag fails in five seconds, not in a phone session. The frame skill's worked references are **executable**: every fenced framing in `skills/duet-frame/references/manifest-examples.md` runs through the real frontmatter parse and manifest freeze, pinning each example's claims — including the omitted keys, so "omission is part of the grammar" stays teachable — and every fenced definition in `references/workflow-definitions.md` compiles through the real SDK, with the shipped-workflow rebuilds pinned byte-identical to the registry rows. A grammar change breaks the examples in seconds, not in a user's first post-change framing.

## Build & publish

Dev has no build step: Node 24 runs `.ts` directly, and the global `duet` command (`pnpm add -g .`) is a symlink whose bin points at `src/surfaces/cli.ts` — every edit is live. Publishing is the one place this cannot hold: Node refuses type stripping for files inside `node_modules` (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`), so an npm-installed copy must ship JavaScript.

The split lives in `package.json`: `bin` → `src/surfaces/cli.ts` for dev; `publishConfig.bin` → `dist/cli.mjs`, rewritten by pnpm only in the published tarball. `pnpm build` (tsdown, config in `tsdown.config.ts`) bundles the CLI to `dist/cli.mjs` and emits the SDK subpath as `dist/workflows.mjs` / `dist/workflows.d.mts` for `duet/workflows`; publint validates the result. `prepack` chains typecheck → tests → build, so a tarball can't be cut from a broken tree. `dist/` is gitignored and never used in dev.

Facts the setup depends on: `snippets/`, `skills/`, `lessons/`, and `prompts/` are listed in `files` because all are resolved package-relative at runtime — `src/orchestrator/library.ts` reads the `snippets/` directory and resolves the `{{lessons_dir}}` token to the vendored `lessons/` methodology (`LESSONS_DIR`), and `src/orchestrator/hosts/orchestrate.ts` feeds `prompts/orchestrator-identity.md` to the launcher (the `import.meta.url`-relative hops are depth-sensitive — a moved module must re-count them; a missing `prompts/` would point the launcher at an unshipped file). The `_drive` respawn uses `process.argv[1]`, so it is agnostic to which entry was invoked, and the `duet orchestrate` launcher self-references the same way — both the process spawn and the `_mcp` server it bakes into the session use `process.execPath` + `process.argv[1]`, never a bare `duet` on `PATH`, so the session attaches the same duet that launched it. `private: true` stays as the guard against accidental publish; the `license` (MIT), `author`, and `repository` fields are now set, so removing `private` and checking the npm name is the deliberate remaining step when publishing becomes real.

## Condensed lessons

1. **Don't approximate judgment with mechanism.** Every pre-pivot compensation (schema fields, disagreement string-matching, caps as exits) existed because code lacked judgment. When tempted to parse LLM output for meaning, hand the judgment to the orchestrator; keep code for structure.
2. **Guarantee in structure, steer in text.** The same rule usually needs both halves: the cap refuses in the handler *and* the refusal names the legal next moves.
3. **Soft constraints want warn-once-then-allow.** A hard block on a usually-wrong action recreates the dumb-router trap; one steering refusal plus a deliberate identical retry keeps judgment in charge and leaves the choice in the transcript.
4. **Infrastructure parameters leak into product scope unless named.** The per-turn budget rail shaped a descope decision before the prompts said "budget is per-turn; never shrink scope for it".
5. **Fixed value + deterministic consumer → config; anything soft → prose.** The frontmatter boundary rule: a deterministic consumer of a soft value *enforces* errors that judgment would have resolved.
6. **Long silent operations need heartbeats.** Non-streaming worker turns run 30+ minutes; a silent pane reads as a hang.
7. **Every stop needs a next command.** A run state the human can see but not act on is a bug — the crash-without-question gap was exactly this, and the fix (crash = flag) is now a pattern. A stop the run can recover from *itself* goes one step further: model it as a resumable checkpoint with a resume path (the budget cutoff), not an error routed to retry/`errorClass`.
8. **A read across several surfaces wants one shared rule, not one per surface.** `doctor`, the heartbeat, and crash classification read the same transcripts; the "is this error still live" staleness bug recurred because two places judged it independently. Collapsing them onto `currentTerminalError` was the fix — convergence, not a local patch.
